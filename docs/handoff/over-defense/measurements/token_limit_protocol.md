# MAX_COMMAND_TOKENS を外すと失敗が再現するかの確認（実行前に固定）

## 問い

`plugins/claq/src/claq/hooks/shell_tokens.py` の `MAX_COMMAND_TOKENS = 5000` は、3 つの保護フック（block_no_verify・bash_config_protection・pre_bash_commit_quality）の入口と `sh -c` の再帰境界で、5,000 トークンを超えるコマンドを走査せずに BLOCKED にする。判断の基準 2（外すと具体的な失敗が再現するときだけ残す）に照らして、この上限を外したときに hooks.json の timeout（15 秒）を超える入力が作れるかを確かめる。

## 測り方

- `token_limit_bench.py` が、プロセスの中で `shell_tokens.MAX_COMMAND_TOKENS = 10**9` にしてから `runpy.run_module("claq.hooks.<hook>", run_name="__main__")` で各 hook を起動し、起動から終了までの壁時計時間を測る。リポジトリのファイルは変えない
- バイト数の上限（`MAX_COMMAND_BYTES` = 64KiB）と stdin の上限は残す。入力はすべて 64KiB 以下
- 同じ入力を上限ありの状態でも測り、上限が判定を止めているかを rc で見る

## 入力の形（すべて 64KiB 以下で、トークン数を最大にする向き）

1. `git commit -m x && ` の連鎖
2. `git ` の約 1.6 万個、`\` を足して 2 方言にしたもの
3. `a;` の繰り返し（約 3.2 万セグメント）と、`\` を足したもの
4. `git;` の繰り返し
5. `sh -c 'git x';` の大量の束と、`\` を足したもの
6. `> .claude/settings.json ;` の繰り返し（保護名へのリダイレクト）と `> x ;` の繰り返し
7. `cat <<EOF` の heredoc の大量の繰り返し
8. `git -c a=b ` の繰り返し、`git config core.hooksPath ` の繰り返し

## 再現の定義

このマシン（macOS・Python 3.14）で、どれかの hook がどれかの入力で **5.4 秒**を超えたら再現とする。根拠: block_no_verify の同じ最悪形が Linux（クラウド、Python 3.13）で 4.9 秒・このマシンで 1.76 秒で、比は約 2.8 倍。このリポジトリを実際に動かした Linux で 15 秒を超える条件は、このマシンで約 5.4 秒を超えること。Windows は未測定。

## 結論の規則

- 再現したら上限を維持し、コメントの根拠を「どの hook のどの形で何秒か」に書き直す。その hook を線形化するかは提案に回す
- 再現しなければ上限を外す。外すと、5,000 トークンを超え 64KiB 以下のコマンドが止められずに検査されるようになる（判定の変更）

## 段階 1 の結果（2026-11-02、macOS・Python 3.14）

`token_limit_bench.py`（起動を含む）と `token_limit_probe.py`（プロセス内、サイズを 1/4・1/2・1 で振る）で測った。

- 上限を外すと、bash_config_protection が閾値 5.4 秒を超えた: `>x;` の繰り返し + `\` で 13.61 秒、`>x;` + `\` の `sh -c` を 3 つ束ねて 20.52 秒（いずれも 63KiB）。規則どおり、現行コードでは上限を維持する
- pre_bash_commit_quality の `git ` の繰り返しはサイズの 2 乗で伸びる（0.06 → 0.22 → 0.89 秒、`\` を足して 1.77 秒）。64KiB の中では閾値の内側
- **新たに見つかった不具合**: 上限ありの現行コードでも、bash_config_protection は約 4,800 トークンの `sh -c '>x;…a\b'` を 12 個束ねた 58KB の入力で 18.68 秒かかり、timeout（15 秒）を超える。トークン数の上限は `sh -c` 1 つごとに当たるだけで、全体の時間を縛っていない。原因は、書込み先 1 つごとにプロセス内で変わらない値（保護対象の場所・global git config の場所・プラグインのルート）を計算し直していること（1 件あたり約 0.37 ms）

## 段階 2 の手順（修正後、測る前に固定）

1. bash_config_protection の、プロセス内で変わらない値の計算を 1 回にする（上限は足さない）。キャッシュの有無で結果が一致することを、ランダムな入力で確かめる
2. 段階 1 の形に、書込み先の名前を毎回変える形（`>x0;>x1;…`）・深いパス・`~` で始まるもの・`..` を含むものを足し、束ねたものと `\` と組み合わせて、上限を外した状態で測り直す
3. 同じ規則（どれかの hook がどれかの入力で 5.4 秒を超えたら再現）を当てる。再現しなければ上限を外し、再現すれば維持して根拠を書き直す

## 段階 2 の結果（修正後）

bash_config_protection の再計算を使い回す修正（`scan_memo`）の後、`token_limit_bench.py` に名前を変える形・深いパス・`~`・`..`・`tee`・`cp` を足して流した。

- 単一のコマンドでは、上限を外しても最悪 1.80 秒（pre_bash_commit_quality の `git ` の繰り返し + `\`、二次）。bash_config_protection は名前を変えた形で最悪 1.02 秒。閾値 5.4 秒を超える形は無かった
- 上限ありでも、名前を変えた書込み先を約 4,500 トークンずつ `sh -c` に包んで束ねた形は 1.03 秒で通る（上限は全体を縛っていない）

1 回の hook 呼び出しに複数のコマンドを載せる形（`token_limit_multi.py` と、上限ぎりぎりの要素を並べる形）:

| 形 | 上限なし | 上限あり（現行） |
|---|---|---|
| pre_bash_commit_quality、`command` の list に 64KiB の `git` ×14 | 24.62 秒 | 0.05 秒（最初の要素で止まる） |
| pre_bash_commit_quality、4 つのコンテナキーに 64KiB の `git` | 7.12 秒 | 0.05 秒 |
| bash_config_protection、list に名前を変えた 64KiB ×14 | 11.56 秒 | 0.06 秒 |
| pre_bash_commit_quality、list に 4,999 トークンの `git` ×45 | — | 7.45 秒 |
| bash_config_protection、list に 1,600 件の書込み先 ×40 | — | 6.79 秒 |

上限ありの list 形は、末尾の結合文字列がバイト数の上限を超えて最後は block になるが、その手前で各要素を走査する時間で timeout に近づく。

作れる形の分類（脅威モデル: エージェントと、不信テキストに操られたエージェント）:

- 単一の文字列コマンド: 作れる
- list（argv）形: 作れる。`plugins/claq/src/claq/lib/harness.py` の `_commands_from_tool_input` に「argv 配列で渡す host がある」（例 `{"command": ["bash", "-lc", ...]}`）とあり、要素の数と中身はモデルが決める
- 複数のコンテナキー（`tool_input`・`toolArgs` 等）と、`command`・`cmd` の併記: キーを決めるのはホストで、エージェントは作れない。脅威モデルの外

## 段階 3 の手順（測る前に固定）

1. list 形は、グループの全コマンドの予算を走査を始める前に検査する（上限は足さず、順番だけ変える）。結合文字列は `shlex.join` で要素に引用符と空白を足すだけなので、そのバイト数は要素の合計以上になり、結合文字列の検査で要素の合計も縛れる
2. 直した後に、作れる形（単一のコマンド・上限ぎりぎりの要素を並べ結合文字列が 64KiB の手前になる list 形）だけを上限なしで測る
3. 同じ規則（5.4 秒）を当て、超えなければ上限を外し、超えたら維持して根拠を書き直す
