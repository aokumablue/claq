# 書いたものの陳腐化と、実測できないものの扱い

定義文書やコードへ書いた列挙・版・固定値は、外部世界が動くと黙って古くなる。失敗が「例外」では
なく「素通り」として現れるため、検知器を置かない限り緑のまま腐る。

## 共通原則

**陳腐化の検知は fail open の診断であって、注入経路上のフィルタではない。** 取りこぼしは
「発見が遅れる」だけで新たな注入経路を作らないのに対し、誤検知は毎回赤いゲートを生み、赤が
常態化したゲートは読まれなくなる。したがって疑わしきは報告しない側へ倒す。プロンプト境界へ
直接注入されるフィルタ（信頼できない入力の除去など）は逆に fail closed へ倒すべきで、同じ
「未知の語彙」という材料を扱っていても、経路上の位置が違えば向きは逆になる。

**常に走らないものを CI ゲートに見せかけると、ゲートの信頼そのものが下がる。** コーパスは各
利用者のローカルにしか無く、外部ソース取得はネットワーク依存でランタイム依存ゼロ原則に反する。
skip されるだけのゲートはゲートとして機能しない。

**運用注意に委ねる案は採らない。** denylist の更新も版付き標準の突合も、運用注意だけでは
見つからない。

**規約であって強制ではない。** 「版を書く」も「検知器があるか」も、破っても何も落ちない。この
限界は版を見出しへ書く規約も、固定値の検知器規約も、同じ言葉で受容している。

**実測できないものは、直さずに残存として明記する。** 未検証の編集は「その環境で保護が黙って
無効」という最悪の失敗へ倒れうるため、文書化された残存のほうが安全。この却下は「直さない」では
なく「実測できる者が直す」である。

## 足場タグ denylist の陳腐化は実コーパス走査で検知する（fail open の診断）

handoff の足場除去はタグ名のハードコード denylist に依存する。denylist の列挙漏れは例外になら
ず「素通り」として現れる。ホストが新しい足場タグを足しても、テストも CI も緑のまま引き継ぎが
ノイズで埋まる。列挙漏れは定義上「まだ知らないもの」なので、列挙の完全性を静的に検証すること
はできない——テストは書けるが、書けるのは既に知っているタグに対してだけで、漏れは 1 件も
見つからない。

**実 transcript コーパスを走査し、除去処理を通した後にも残る「対を成す未知タグ」を報告する
診断を置く。** 定期メンテの final gate 項目とし、CI には組み込まない。終了コードは `0` =
ドリフトなし / `1` = 検出 / `2` = 走査対象ゼロ。

判定は次の 3 段で誤検知を落とす: 除去後のテキストを見る（生テキストだと内側タグが並び真の
漏れが埋もれる）。対を成すものだけを見る（依頼本文の裸プレースホルダを落とす）。コードスパンを
除く（依頼本文が引用したコード片・正規表現内のタグを落とす）。

この診断は fail open にする。プロンプト境界への注入経路上のフィルタ（handoff の足場除去）は
fail closed であるべきだが、あれは取りこぼしがそのまま次セッションのプロンプト汚染になる。
本節の診断は注入経路上に無く、取りこぼしは「発見が遅れる」だけで新たな注入経路を作らない。
一方で誤検知は毎回赤いゲートを生み、赤が常態化したゲートは読まれなくなる。したがって疑わしきは
報告しない側へ倒す。

denylist の更新を運用注意に委ねる方式、denylist を allowlist に変える方式、検知を pytest / CI に
組み込む方式は採らない——運用注意は実データを見るまで見つからず、allowlist はユーザーが依頼本文
に書ける語が無限で現実的に閉じず、コーパスは各利用者のローカルにしかないため CI では常に `2`
になり `0` と区別されないまま形骸化する。誤検知が出るたびに良性語のリストへ語を足して緑にする
運用は、ホスト足場としてもあり得る語を足すと将来その名前で本当に漏れたとき黙って握り潰すため、
良性 HTML タグに限り、それ以外は原因側（コードスパン除去など）を直す。

良性語のリストという第 2 の列挙が増える。これも陳腐化すると誤検知 1 件として現れ、語を 1 つ
足せば解消する——denylist の陳腐化（無言の素通り）と保守量は同じで、失敗の向きだけが反転して
いる。コードスパン除去により、コードフェンス内で本当に漏れた足場は見えない。コーパスは走査
時点の直近に限るため、古い host の足場は窓から落ちる。タグ語彙による検知はタグを持たない足場を
原理的に見ない。

## 外部の版付き標準を定義へ列挙するときは版を見出しへ書く

汎用知識の列挙は網羅性の担保として残すという判断自体は正しい。しかし残したものが古くなる経路が
開いたままでは、無版の見出しが「常に最新」を騙る。既存の検査は `.md` 参照の切れを検出するが、
外部世界の事実が古くなったことは検出できない。定義に書いた検証規則を CI で実測する原則も、
実測できるのはリポジトリ内で閉じた規則だけである。

1. **外部の版付き標準を列挙するときは、版を見出しへ含める。** 版が見出しにあれば `git diff` にも
   レビューの目にも入り、「いつのものか」を読み手が判断できる。無版の見出しは「常に最新」を騙る
2. **版を書けないもの・書きたくないものは列挙せず、名前で参照する。** 網羅性の担保が要らない
   なら列挙しない。要るなら版を背負う。どちらでもない中間（無版の列挙）を置かない
3. **CI ゲートにはしない。** 外部ソースの取得はネットワーク依存であり、ランタイム依存ゼロに
   反する。オフライン CI では常に skip され形骸化する。検知は定期メンテの web トレンド入力
   （既定 ON・失敗時は「トレンド入力なし」と明記して続行）と、レビュー観点「md の節見出しに
   含まれる年号・版を現行と突き合わせる」に載せる。両経路が実在して初めて成立する
4. **意図的に残すと決めた節には、その判断の出典（ADR のトピック名）への 1 行参照を置く。**
   適用漏れは同じ削除提案を再発させる

列挙をやめて標準の名前だけを参照する方式は、版を指定しない参照がモデルの学習時点の版へ黙って
落ちるため、陳腐化が「見えるところ」から「見えないところ」へ移動するだけで悪化するため採らない
（網羅性の担保が落ちるという理由で列挙の削減自体を既に棄却している）。CI で外部ソースを取得して
差分検知する方式は、ネットワーク依存で依存ゼロ原則に反しオフライン CI では常に skip されるため
採らない。版をコメントや本文末尾に書き見出しは無版のままにする方式は、本文末尾の年号が diff の
文脈行に埋もれてレビューの目に入らないため採らない。定期メンテの運用注意に委ねるだけの方式は、
運用注意が版の取り残しを検出していないため採らない。

版を上げるたびに見出しが変わり、節参照を持つ節では参照側の追従が要る。「版を書く」は規約であって
強制ではなく、無版の列挙を新たに書いても何も落ちない。検知経路は fail open の診断であり、見逃し
は「発見が遅れる」として現れる。版を持たない外部知識（言語慣行・フレームワーク作法）はこの規約の
射程外で、陳腐化を検出する手段が引き続き無い。

## 定義へ書く固定値は「陳腐化の検知器があるか」で残す / 外す

前節が守っているのは「版を書くこと」ではなく「陳腐化が見える位置にあること」である。消したいのは
「書いてあること自体がメンテ負債になる固定値」である。両者が指す集合は重ならない。固定値は
次のように分かれる: 外部の版付き標準（見出しに版を書く。前節）。内部成果物の版（CI 照合がある
なら残す）。実測の採取条件（出典として残す。採取日を伴わせる）。検知器を持たない固定値（外す。
外せないなら役割記述子へ置き換える）。

1. **固定値は「陳腐化の検知器があるか」で残す / 外すを決める。** 版であるかどうかでは決めない。
   検知器とは、CI の機械照合、定義本文に書かれた自己検査、前節が指定した運用検知（web トレンド
   入力とレビュー観点）のいずれかを指す
2. **検知器を持たない固定値は外す。** 外せない（フィールドとして必須である）なら、役割記述子へ
   置き換える。役割は陳腐化しない
3. **実測の採取条件は「固定値」ではなく出典として扱い、常に残す。** ただし採取日を伴わせる——
   採取日の無い「最新」は、再採取の要否を判断できない
4. **前節が指定した 2 経路は、両方が実在して初めて成立する。** 片方だけの実装を成立と扱わない

信頼境界の宣言は「不信な材料を読むか」ではなく「その材料から導いた判断が、ツール権限を超えた
不可逆な効果を生むか」で足す。当てはまらない定義にまで複製しない。書き込み権限を持つ定義すべて
に信頼境界節を一律で足す方式は、判断が読んだテキストではなく実行結果に接地している定義では
該当せず、当てはまらない定義への複製は冗長になるため採らない。エージェント定義とスキル定義の
逐語重複を単一情報源へ寄せる方式は、消費者が異なる（エージェント定義は会話履歴も親の注入も持た
ない fresh subagent が読み、スキル定義は本体セッションへ載る）ため、参照へ落とすと subagent 側
に届かず採らない。

版表記を一律に外す方式、検知器の有無ではなく外部/内部で切る方式、検知器の無い固定値すべてに
CI 照合を足す方式は、いずれも版の取り残し再発・分類軸が失敗モードと不整合・外部の最新をネット
ワーク無しで照合する手段が無いため採らない。外部リソース取得に署名・ハッシュ検証を要求する対応
は、取得先がハッシュを公開していなければ満たす手段が無く、実行不能な勧告は書いても守られないまま
「対応済み」の見かけだけを作るため採らない。

「検知器があるか」は規約であって強制ではない。検知器の無い固定値を新たに書いても何も落ちない。
役割記述子への置き換えは、具体 ID より読み手の解釈幅が広い。「判断が不可逆な効果を生むか」という
判定基準は実測の裏付けが無く、該当しないと判断した経路から注入が実際に起きたら、判定基準ごと
見直す。
