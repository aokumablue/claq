# コードの簡潔さと防御・フォールバックの量

コードと定義文書に、防御・フォールバック・抽象をどこまで置くか。レビューは足りないものと余計なものをどう扱うか。

## 共通原則

**置くのは根拠を引用できるものだけにする。** 入力の拒否・上限の検査は、要件の文・攻撃者と入口・再現できる失敗・外部 API 契約の条項のどれかを引用できるときに置く。失敗の後に続行する経路（握り潰し・既定値・再試行・代替経路）は、続行を決めた文（要件・利用者の指示・外部 API 契約）を引用できるときに置く。失敗が起こりうることは、失敗を検出して伝える理由になり、続行する理由にはならない。

**用語を固定する。** 要件の文は、依頼・仕様・ADR に依頼者の決定として書かれた文を指す。エージェントが自分で書いた参照文書・コメントの「義務」は要件の文に含めない。再現できる失敗は、要件に書かれた振る舞いが崩れることをテストか手順で示せるものを指す（検査が何かを見逃すことは、それだけでは失敗に数えない）。

**書き方と追加を分ける。** 要件の振る舞いを成り立たせる書き方（パラメータ化クエリ、ネットワーク呼び出しのタイムアウト、トランザクションの commit 等）は、最新の推奨で選んで実装する。要件に無い振る舞い（拒否・上限・再試行・代替経路・新しい仕組み）を足す判断は、報告の「提案」に理由と出典を付けて出し、採否は利用者が決める。判定の問いは「それが無いと要件の振る舞いが崩れることを示せるか」の 1 つにする。

**提案は既定で実施しない。** 判定側の BLOCKER 未満の指摘と生成側の改善案は「提案」として報告する。「すべて対応」「ベキ論で対応」は、各項目に実施かクローズかを決めて返す指示として読み、根拠を引用できる項目を実施し、それ以外は理由を添えてクローズする。レビューと監査の範囲は依頼が決め、範囲の説明は未確認の項目として並べない。この区分が無いと、残課題の一覧と包括指示の組み合わせでハードニングが一括実装される。

**消す側にも同じ立証を求める。** 消すのは、型や呼び出し元から到達しない・同じ検証が入口で済んでいると示せるものだけにする。変更前からある通る経路のフォールバックを消すと振る舞いが変わるので、仕様変更として扱う。変更で不要になった旧経路・呼び出し元を失った定義・テスト・互換分岐は、同じ変更で消す。

**攻撃者は対象から特定する。** ネットワーク上の client・他ユーザー・プロンプトへ入る不信テキストを攻撃者とし、ローカル開発者本人と同一 UID のプロセスは数えない。保護フックはエージェント自身の誤操作も止める対象に含める。

## 実装の手順は同梱の定義文書へ逐語で置く

サブエージェントはコンテキストを共有せず、リポジトリの `docs/` はプラグインを使う他のリポジトリでは読まれない。そのため、本番コードを自分で書き換える定義（agent・skill）に「実装の手順」を同じ文言で直接書き、全写しが一字一句同じであることをテストで固定する。正本は tdd-writer に置く。子へ委譲するだけの定義、テストだけを書く定義には置かない。

指示は肯定文の手順と出力欄で書く。禁止の列挙は、名前を出すことでその行動を思い出させる。防御を足したくなる判断は「提案」欄へ流す。否定文は、過剰防御と無関係な硬い境界（テスト改ざん・フックの迂回・元に戻せない操作）にだけ使う。

## レビューの判定

- reviewer の CRITICAL/HIGH は、根拠（呼び出し元の全数確認・実行出力・再現手順・入口の検証位置の引用）を指摘行に書けたものにする。書けないものは INFO に「未確認」と付ける
- reviewer は、消してよい根拠を示せた余剰（到達しない防御・入口で済んだ検証の繰り返し・呼び出し元が 1 つの抽象・テストからしか通らない分岐）と、差分で足された根拠を引用できない検査・続行経路を HIGH にする（要件が渡されないレビューでは WARNING）。書き方として要る検査は対象外
- security-auditor は、「攻撃者 → 入口 → 得るもの」を書けた指摘を BLOCKER にし、修正方針にはその得るものを無くす最小の変更を書く。書けない改善はハードニングとして MEDIUM 以下の提案に置く。止める制御が見当たらない穴は、実行で確かめていなくても下げない
- 関数・ファイルの長さとネストの深さは目安として WARNING に置く
- 自動修正は BLOCKER だけを対象にし、裏取りしたうえで指摘箇所の最小の変更に限る。新しい仕組み（依存・検証層・設定項目）が要る指摘と、続行を決めた文の無い続行経路は提案へ回す
- 既存テストが assert している振る舞いを変える修正は、起動前に仕様変更として人間へ戻す。修正の途中で green だったテストが red になったら、その修正が加えた編集だけを逆適用で取り消す
- 防御を残すときに理由が自明でなければ、引用した根拠を 1 行のコメントで残す

## 記憶と指示文書

- 知識カードには、特定の入口に結び付く学びだけを記録する。入口に結び付かない防御の一般則は、注入されると以後のすべての実装に防御を足させる
- 指示を定義文書へ足すのは、実行で失敗が観測された場合だけにする。1 行足すごとに、効いていない行を削れないか探す

## ファイル長は目安であり、複製して配る 1 ファイルの成果物には当てない

800 行はファイルを読み切れる大きさの目安で、検査で強制しない。スキルが利用者のリポジトリへ 1 ファイルだけ複製して単独で動かす成果物（スキルの手順書が `cp` で 1 ファイルずつ複製する検査スクリプト等）は、複数ファイルへ分けると手順書の複製手順が変わり、束ねる生成工程を置くと二重管理が要る。そのため配布が 1 ファイルに固定された成果物は 800 行の対象外にする。関数の長さ（実行 50 行）とネスト（3 階層）は配布物にも当てる。この例外はリポジトリ内部のモジュールには適用しない。
