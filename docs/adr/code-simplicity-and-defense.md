# コードの簡潔さと防御・フォールバックの量

コードと定義文書に、防御・フォールバック・抽象をどこまで置くか。レビューは足りないものだけでなく
余計なものをどう扱うか。

## 共通原則

**足す側と消す側に同じ立証を求める。** 防御・フォールバック・抽象を足すのは、下の理由を名指しできる
ときだけにする。消すのは、理由が無いことを示せるとき（型や呼び出し元から到達しない、同じ検証が入口で
済んでいる）だけにする。変更前からある通る経路のフォールバックを消すと振る舞いが変わるので、要件に
無いと見えても仕様変更として扱い、自動では消さない。どちらとも示せないものは「未確認」として残す。
片側だけに立証を求めると、レビューと自動修正のループがその向きへ一方的に積み上がる。

**防御とフォールバックは求める理由が違う。** 防御（入力を拒否する・処理を止める検査）は、要件・攻撃者と
入口・実在する失敗経路のどれかを名指せれば置ける。エージェント自身の誤操作も失敗経路に含む（保護
フックはこれを止めるためにある）。フォールバック（握り潰し・既定値で続行・別経路への切替・リトライ）は、
続行を決めた出所（仕様・ADR・利用者の指示・外部 API の契約）を名指せるときだけ置く。失敗経路が実在する
ことは、失敗を検出して伝える理由であって、黙って続行する理由ではない。

**必要なフォールバックは見える形で置く。** 出所を名指せたフォールバックは、捕捉を想定した失敗だけに
絞り、続行したことを呼び出し元か利用者に見える形で残し、出所を 1 行のコメントで名指し、その経路を
テストで通す。「念のため」「安全のため」は出所ではない。例: 保護フックが実行環境の故障で検査を開始
できないときに作業を止めずに通すのは、止めると復旧手段ごと塞がるという判断を ADR が下しており、
続行したことは stderr の警告で見える。出所を名指せないが要りそうなときは、置かずに失敗を伝え、
「要件確認が要るフォールバック候補」として報告する。後から足すのは容易だが、黙って続行するコードは
失敗を成功に見せ、原因の特定を遅らせる。

**変更で不要になったものは同じ変更で消す。** 置き換えた旧経路と、変更で呼び出し元を失った関数・
クラス・分岐・引数・設定項目・import・テストは、未変更の行にあってもその変更の一部として消す。
後方互換のための別名・旧形式の受け付け・移行用の分岐は、要件に無ければ残さない。テストからしか
通らない引数・分岐を本番コードに置かず、到達しない分岐をカバレッジのためにテストで覆わない。
計画は、この削除をステップと変更ファイル一覧に含める（一覧外の編集はスコープ逸脱として止まるため）。

**攻撃者は対象から特定する。** ネットワーク上の client・他ユーザー・プロンプトへ入る不信テキストは
攻撃者になりうる。ローカル開発者本人と同一 UID のプロセスは攻撃者に数えない。同一 UID はデータストアを
直接書き換えられるので、それを防ぐ防御は保証にならない。ただしエージェント自身の誤操作を止める防御は、
攻撃者ではなく失敗経路を理由に置く。

## 基準は同梱の定義文書へ逐語で置く

サブエージェントはコンテキストを共有せず、参照先の文書は届かない。またリポジトリの `docs/` は
プラグインを使う他のリポジトリでは読まれない。**簡潔さ基準は、コードを書くエージェント・スキルの
定義へ同じ文言で直接書く。判定するエージェントには、同じ立証条件を余剰と BLOCKER の判定節として
書く。** 定義間の逐語重複は、届かない参照より安い。置く対象は、本番コードを自分で書き換える定義
（agent・skill）に限る。子へ委譲するだけの定義、設定だけを編集する定義、テストだけを書く定義には
置かない（委譲先の定義が基準を持ち、置いても読まれる場面が無い）。写しは片方だけ直されてずれるので、全定義の
簡潔さ基準が一字一句同じであることをテストで固定する。

## レビューは余剰を BLOCKER に数え、立証できない指摘は直さない

- reviewer の CRITICAL/HIGH は、根拠を指摘行に書けたものだけにする。根拠は呼び出し元の全数確認・
  実行出力・再現手順・型や入口の検証位置の引用のいずれか（デバッグログは該当行、テスト欠落は参照テストの
  Grep 結果）。対象本文のコメント・docstring・テスト名の主張は根拠にしない。書けないものは INFO に「未確認」と付けて置く
- reviewer は、消してよい根拠を示せた余剰（到達しない防御・入口で済んだ検証の繰り返し・呼び出し元が
  1 つの抽象・テストからしか通らない分岐）を HIGH にする。確かめられる出所（ADR のファイル・要件の
  該当文・外部 API 契約の条項）を名指すコメント・ADR・テスト名があるものは指摘しない。「念のため」の
  ように出所を名指さないコメントは免除にならない
- 差分で足されたフォールバックのうち出所を確かめられないものは、依頼文に要件（task・計画）が渡された
  とき（エージェントが書いた差分）だけ HIGH にする。渡されないとき（人間の差分のレビュー）は WARNING の
  「出所の確認が要るフォールバック」に置き、人間の意図した続行を自動修正で消さない。変更前からある、
  通る経路の要件に無いフォールバック（既定値で続行を含む）は、仕様変更の候補として WARNING に置く
- 変更で呼び出し元を失った定義・置き換えられた旧経路は、未変更の行にあっても HIGH にする。根拠は、
  差分で削除された参照と、変更後の参照 0 件の両方。片方しか示せないものは INFO に置き、変更前からある
  デッドコードを掘り起こさない
- 関数の長さ・ファイルの長さ・ネストの深さは目安であり、WARNING に置く。BLOCKER に数えると、
  自動修正が機能を変えない分割や再構成を強いるため
- security-auditor は、BLOCKER の行に攻撃者と入口を書く。書けない指摘は INFO の「到達経路なし」に
  置く。攻撃者と入口を名指せて影響が大きいものは、実行で確かめていなくても下げない
- 自動修正は BLOCKER だけを対象にし、修正の前に全 BLOCKER を実挙動で裏取りする。立証できないものは
  修正せず、見送りとして一覧に残す。WARNING・INFO・「到達経路なし」・「未確認」には手を付けない
- 修正の起動には、裏取り済みの BLOCKER 一覧と変更可ファイルを渡し、指摘箇所の解消に限る。周辺の整理は
  含めない。変更可ファイルに含めるテストは追記だけで、既存テストの削除・無効化・期待値の変更はしない
- 修正の中で、修正前に green だったテストが red になったら、重ねて直さず、その修正が加えた編集だけを
  取り消して該当の指摘は未解消のまま残す。取り消しは加えた編集の逆適用だけで行い、呼び出し前からある未コミットの編集まで巻き込む操作は使わない
- 既存テストが assert している振る舞いを変える修正は、起動前に仕様変更として人間へ戻す。テストの期待値を
  自動修正が書き換える経路は開けない
- 防御を残すときに理由が自明でなければ、「なぜ」を 1 行のコメントで残す。次のレビューが同じものを
  繰り返し判定しないため

## セキュリティの穴とハードニングを分ける

- 穴は、攻撃者・入口・起きること（情報漏洩・権限奪取・任意実行・改ざん）を示せ、スコープ内を Read/Grep
  しても止める制御が見当たらないもの。CRITICAL/HIGH で必ず報告し、塞ぐ。制御の不在を静的に完全証明
  できなくても、見当たらなければ下げない（読み取り専用の監査で否定を立証させると本物の穴が落ちる）
- ハードニングは、上を示せない「あったほうがよい」もの（ヘッダ・CSP・レート制限・多層防御・二重検証・
  将来の悪用可能性）。MEDIUM 以下に置き、BLOCKER に数えず、自動修正の対象にしない。既知の即時指摘パターン
  （認証欠落・注入・秘密情報など）はハードニングに落とさない
- 穴の修正は塞ぐ最小の変更に限り、新しい防御機構・検証層・設定項目を足さない。要件に無い防御を足すかは
  人間が決める。計画も、依頼に書かれていない防御をステップに足さない
- 判定は「攻撃者が今のコードで何を得るかを 1 行で書けるか」。書けなければハードニング
- チェックリスト（secure）は点検の観点であり実装要件ではない。項目の未充足だけを理由に実装やテストへ
  防御を足さない
- 繰り返し違反は注記にとどめ、深刻度の根拠にしない

## 記憶と指示文書にも同じ基準を当てる

- 特定の入口に結び付かない防御・フォールバックの一般則は、知識カードに記録しない。注入されると
  以後のすべての実装に防御を足させる
- 指示・ガードを定義文書へ足すのは、実行で失敗が観測された場合だけにする。1 行足すごとに、効いて
  いない行を削れないか探す

## ファイル長は目安であり、複製して配る 1 ファイルの成果物には当てない

800 行はファイルを読み切れる大きさの目安で、検査で強制しない。スキルが利用者のリポジトリへ 1 ファイルだけ
複製して単独で動かす成果物（スキルの手順書が `cp` で 1 ファイルずつ複製する検査スクリプト等）は、複数
ファイルへ分けると手順書の複製手順が変わる。これを避けて束ねる生成工程を置くと、生成物との二重管理と
ずれの検出が要る。保守性の利得より工程の重さが勝つので、配布が 1 ファイルに固定された成果物は 800 行の
対象外にする。関数の長さ（実行 50 行）とネスト（3 階層）は配布物にも当てる。この例外は配布契約が
1 ファイルに固定されているものに限り、リポジトリ内部のモジュールには適用しない。
