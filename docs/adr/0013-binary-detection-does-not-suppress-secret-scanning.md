# ADR-0013: バイナリ判定で secret 検査を止めない（ADR-0001 の受容を撤回）

**日付**: 2026-08-27  **ステータス**: accepted
**関係**: [ADR-0001](0001-hooks-fail-open-when-inspection-cannot-complete.md) の
「バイナリ偽装は受容するリスク」という判断のみを supersede する。fail-open /
fail-closed の境界規則そのものは維持する。

## コンテキスト

ADR-0001 は次を明示的に受容していた。

> バイナリ判定されたファイルは secret scan 自体をスキップし severity warning
> の痕跡を残す（error にはしない — 画像等の commit を一律ブロックすると明示
> 要件に反する）。NUL バイトを混ぜて secret 混入を隠すバイナリ偽装は、この
> skip の副作用として受容するリスクであり、積極的に防ぐ設計目標ではない。

2026-08-26 の実機監査 F-06(b) がこの経路を実際に通した。`evaluate()` の入口から
決定的 fixture で実行し、先頭に NUL を 1 バイト置いた内容が `exitCode: 0` で
通ることを確認している。

再評価の決め手になったのは、**コード自身が逆の不変条件を宣言していた**ことである。
`commit_quality_scanner._is_binary_content` の docstring は

> この判定は lint チェックの抑制にのみ使用し、シークレット検出には使いません
> （バイナリ判定を悪用して secret 検査を回避できないようにするためです）

と書いているのに、同じファイルの `find_file_issues` はまさにそれを行っていた。
ADR-0001 の受容文とコード内の宣言が真っ向から矛盾しており、どちらか一方は必ず
動かさなければならない状態だった。

## 決定

**バイナリ判定は lint チェックの抑制にのみ用い、secret 検査の実施可否には
用いない。** バイナリ判定された内容に対しては、行分割の代わりに
`_extract_printable_runs`（`strings(1)` と同じ発想で、NUL を含む制御文字で
区切られた 4 文字以上の連続を抽出）を走査単位として、通常と同じ secret パターンを
適用する。抽出文字列は実際の行に対応しないため、行番号は報告せず
`in extracted binary content` と表示する。

`secret_scan_skipped`（severity warning）の痕跡 issue は不要になったので削除した。

「画像等のバイナリ commit を一律ブロックしない」という既存の要件は維持される。
真のバイナリは secret パターンに一致する印字可能文字列を通常含まないためである
（PNG ヘッダを含む fixture で error ゼロを確認済み）。

## 検討した代替案

### 代替案 1: ADR-0001 の受容を維持し、コード側の docstring を実態へ合わせる

- 長所: 実装変更ゼロ。矛盾は文言修正だけで解消する。
- 短所: 回避コストが「先頭に NUL を 1 バイト置く」と極端に低い。commit 品質
  フックの中核価値は secret の混入防止であり、そこだけが最も安く迂回できる
  状態を「設計どおり」と宣言することになる。ADR-0002 が定める
  「誤検出 > 誤通過」とも整合しない — NUL 偽装は解析できない構文ではなく、
  判定できる入力に対して意図的に検査を止めている。
- 却下理由: 受容の根拠だった「修正コストが高い」が成り立たない。印字可能文字列の
  抽出は正規表現 1 本であり、既存のパターン集合をそのまま再利用できる。

### 代替案 2: 拡張子 / MIME / 明示 allowlist で真のバイナリだけを skip する

- 長所: 画像等を確実に素通しでき、走査コストも下がる。
- 短所: allowlist は「.png という名前のテキストファイル」を素通しにする。攻撃
  コストは NUL 1 バイトから拡張子の付け替えに変わるだけで、質的な改善がない。
  加えて拡張子・MIME テーブルという保守対象が増える。
- 却下理由: 回避コストをほとんど上げないまま保守対象だけが増える。内容そのものを
  走査する方が、判定材料が 1 つで済み確実である。

### 代替案 3: バイナリを一律 deny する

- 長所: 実装が最も単純で、見逃しがゼロになる。
- 短所: 画像等の commit ができなくなる。ADR-0001 が「ユーザーの明示要件に反する」
  として却下済み。
- 却下理由: 同じ要件が依然として有効。

## 結果

### 肯定的

- `_is_binary_content` の docstring が宣言する不変条件を、実装が初めて満たす。
- NUL 1 バイトによる secret 検査回避が塞がれた。severity は `error` なので
  検出時は commit がブロックされる。
- 走査単位が減る（抽出文字列のみ）ため、真のバイナリに対する走査コストはむしろ
  下がる。`_SECRET_SCAN_TIME_BUDGET_SECONDS` の予算管理はそのまま効く。

### 否定的

- 抽出文字列は行に対応しないため、バイナリ内で検出した secret の位置を行番号で
  示せない。`line: 0` と `in extracted binary content` で表現する。

### リスク

- 印字可能文字列を偶然含む真のバイナリが secret パターンに一致すると、
  false positive で commit がブロックされる。ADR-0002 の「誤検出 > 誤通過」に
  従い、この方向の誤りは許容する。実測では PNG ヘッダで誤検出しないことを
  確認しているが、全バイナリ形式を検証したわけではない。
- 制御文字で区切られない形（例: すべて印字可能文字で構成された独自バイナリ）は
  そもそもバイナリ判定されないため、通常のテキスト経路で走査される。
