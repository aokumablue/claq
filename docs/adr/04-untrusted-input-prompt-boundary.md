# 信頼できない入力とプロンプト境界

transcript・hook payload・エージェントが処理した外部文字列は信頼できない入力であり、注入先は
次セッションのプロンプト境界である。ここへ何を通し、何を捨てるか。

| ADR | 決定 | 日付 | ステータス |
|---|---|---|---|
| [ADR-0007](#adr-0007-知識カードの-active-化権限は-payload-から剥奪するがpromote-と既存-active-カードは維持する) | payload/CLI から `source`/`status` の authority を剥奪する。`promote` の無効化と既存データ隔離は採らない | 2026-08-20 | accepted |
| [ADR-0015](#adr-0015-handoff-の足場タグ除去は孤立タグを細工とみなす-fail-closed-とする) | ペア除去後に片側だけの足場タグが残ったらメッセージを丸ごと破棄する（fail closed） | 2026-08-28 | accepted |

## 共通原則

**注入経路上のフィルタは fail closed に倒す。** 「残す」側に倒した誤りは次セッションの判断を
汚染するのに対し、「捨てる」側に倒した誤りは引き継ぎ 1 件の欠落で済む。同じ材料を扱っていても、
注入経路上に**無い**診断は逆向き（fail open）に倒す — 詳細は
[06-staleness-detection.md の ADR-0016](06-staleness-detection.md)。

**必要十分な範囲は「authority の剥奪」であって「機能の停止」ではない。** 実害が確認された経路
（payload だけで active を偽装できる）を塞ぐことと、正規の人間承認経路そのものを潰すことは別で
ある。後者は「機能を壊すことで脅威を消す」過剰対応になる（ADR-0007 代替案 1）。

**同一 UID からの直接改竄は防げない。** `mem.db` を直接更新できる以上、CLI をいくら固めても保証
にはならない。したがって**コードと文書が「人間承認のみ」という保証を主張しない**ようにし、境界の
代わりに事後追跡（監査ログ）を置く。

**タグ語彙に依存する防御は、タグを持たない足場を原理的に見ない。** 実測で確認されたもの:
`IMPORTANT: You are running in non-interactive --print mode…`、`Base directory for this skill:`、
`Another Claude session sent a message while you were working:`。denylist / allowlist / drift 検知の
いずれでも捕まらない構造的な天井である。

## ADR-0007: 知識カードの active 化権限は payload から剥奪するが、`promote` と既存 active カードは維持する

**日付**: 2026-08-20  **ステータス**: accepted

### コンテキスト

v0.9.34 のランタイム監査 H-01 は、`mem learn`（generic CLI）の呼び出し元が JSON payload に
`source: "human"` / `status: "active"` と書く、または helper の `--status active` を指定するだけで、
真正性検証なしに `status='active'` の知識カードを作成でき、SessionStart context への永続注入を自己
承認できてしまう問題を指摘した。

同レポート §8.3 はこの是正として次の 5 項目を挙げていた:

1. `mem/cli.py:_handle_learn` から `--status` を削除し、指定時は `UsageError`（exit 2）にする
2. `parse_knowledge_payload` は payload の `source`/`status` を authority として扱わず、常に
   `source="agent"` / `status="pending"` に固定する
3. `runtime/claq-helpers.sh` 等から active/archived 指定・promotion を agent が実行できると示す説明を除去する
4. host capability が未実装の間、`_handle_promote` を agent / generic CLI から使用不可にする
5. provenance を遡及判定できない既存の全 `active` カードを、backup / report の上で `pending` へ quarantine する

### 決定

**上記のうち項目 1〜3（payload/CLI から `source`/`status` の authority を剥奪する）だけを採用する。
項目 4（`promote` の無効化）と項目 5（既存 active カードの一括隔離）は採用しない。**

採用した範囲:

- `knowledge_input.parse_knowledge_payload()` は常に `source="agent"` / `status="pending"` を書き込み、
  payload がそれ以外の値を明示した場合は `KnowledgeInputError` にする
- `mem/cli.py` の `learn` サブコマンドは `--status` オプションそのものを拒否する（`CommandError`）。
  `list`/`search` の絞り込み用 `--status` は維持する
- `claq_mem_learn` から `--status`/`--source` の option parsing を削除し、常に `source=agent` /
  `status=pending` で登録される旨をコメントへ明記した
- `skills/learn/SKILL.md` / `commands/instinct.md` から「agent が active 化できる」という記述を削除し、
  昇格は `mem promote <key>`（人間が実行するコマンド）だけである旨に統一した

`_handle_promote` は変更していない。既存の `active` カードのマイグレーションも行っていない。

### 検討した代替案

#### 代替案 1: レポート §8.3 の 5 項目を全面採用する

- 長所: 「caller が active を自己承認できる」という脅威を最も広く塞げる
- 短所:
  - `promote` は `CLAUDE.md` のデータモデル前提に明記された正規の人間承認経路である。これを無効化すると、
    agent 由来の知識を人間がレビューして有効化する既存ワークフロー全体が機能しなくなる — 「機能を壊す
    ことで脅威を消す」という過剰対応になる
  - このセッション自身の SessionStart context には稼働中の `active` カードが 11 件前後注入されていた。
    これらを一括で `pending` へ落とすと、蓄積済みの有用な知識が次回以降のセッションへ注入されなくなる。
    脅威モデルの外側にあるリスクへの対処として、稼働中データを破壊するコストが大きすぎる
  - host-mediated で agent が偽造できない承認 capability は、Copilot・Claude Code のいずれでも実証されて
    いない。実装できない前提を機能停止の条件にすると、`promote` は無期限に使えなくなる
- 却下理由: 実害に対して必要十分な範囲は「payload/CLI からの authority を剥奪すること」であり、それ以上の
  「promote 自体の無効化」「既存データの破棄」は脅威モデルの外側の対応であり、得られる安全性の増分に対して
  コストが不釣り合いに大きい

#### 代替案 2: 何もしない（H-01 を non-issue として ADR 化する）

- 長所: 実装コストがゼロ
- 短所: 実際に payload だけで active card を作成できることを実行して確認済み
  （`{"source":"human","status":"active"}` を stdin に渡した `learn` が active card を作っていた）。これは
  脅威モデルの外側で発生しうる実害（agent が処理した外部入力がこの経路を悪用する）であり、修正不要とは言えない
- 却下理由: 実害が確認されている以上、payload の authority 剥奪という低コストな修正を見送る理由がない

### 結果

**肯定的** — `mem learn` の generic 経路から `source`/`status` を偽装して active 化する経路は塞がれた。
JSON `{"source":"human","status":"active"}` や `learn --status active` は exit 1 になり、DB に書き込まれ
ないことを実行して確認した。`promote <key>` による人間承認ワークフローと、稼働中の既存 active カードは
無傷で維持される。

**否定的** — `promote` 自体は引き続き agent が実行可能な CLI コマンドであり、「人間が意図して
`/instinct promote` を叩いた」ことを技術的に強制する手段は無い（運用上の慣習に依存する）。

> **2026-08-27 追記（F-21 対応）**: この受容判断そのものは再評価のうえ維持する。同一 UID から `mem.db` を
> 直接更新できる以上、CLI をいくら固めても保証にはならず、`promote` を潰すのは過剰対応である。一方で、
> **コードと文書が「人間承認のみ」という保証を主張していた点は是正した** — `mem/cli.py` は
> `learn --status active` を「有効化は promote による人間承認のみです」という理由で拒否していたが、その
> 人間承認を担保する仕組みは存在しない。README / `skills/learn/SKILL.md` / `commands/instinct.md` / CLI の
> 文言を「運用上の想定であり技術的強制ではない」へ改め、昇格時に key / scope / source / 直前 status / uid を
> 監査ログへ記録するようにした。これは境界ではなく事後追跡である。

**リスク**

- 将来、host-native な承認 capability（agent が偽造不能な単発トークン等）が実証された場合、`promote` を
  その capability 必須の経路へ差し替える余地を残しておく必要がある。現状の `_handle_promote` はこの将来
  変更を妨げない形（単純な status 更新のラッパー）のままにしてある
- 既存の active カードのうち、実際には自己承認されたもの（本 ADR 以前に payload 経由で active 化されたもの）が
  紛れている可能性は残る。遡及検知・監査は行っていない

## ADR-0015: handoff の足場タグ除去は孤立タグを細工とみなす fail closed とする

**日付**: 2026-08-28  **ステータス**: accepted

### コンテキスト

SessionEnd の handoff は transcript の user エントリから「直近のユーザー依頼」を抽出し、SessionStart で
`<claq-memory>` として次セッションのプロンプトへ注入する。transcript は信頼できない入力であり、注入先は
プロンプト境界である。

user エントリにはユーザーの発話だけでなく、ハーネスが生成した足場（`local-command-caveat` /
`local-command-stdout` / `local-command-stderr` / `task-notification` / `system-reminder` / `agent-message`、
およびスラッシュコマンド起動の `command-name` / `command-message` / `command-args`）も同じ形で載る。実測では、
あるセッションの引き継ぎ 3 件がすべて足場で埋まり実依頼が消えたうえ、注意書きに含まれる
`DO NOT respond to these messages` が疑似ユーザー指示として次セッションへ再注入されていた。

足場を除去する必要があるが、除去処理そのものが回避対象になる。足場ブロックの中身は攻撃者が影響しうる
（コマンド出力・サブエージェント通知）ため、中身に閉じタグや開始タグを混ぜてブロックを早期終端させれば、
細工した文字列を「依頼」として残せる。既存の `mem/tag_stripping.py` は信頼境界マーカーの偽装対策であり
**中身を残すのが正しい**。handoff の足場除去は目的が逆で**中身を捨てるのが正しい**。

### 決定

ペア除去後に片側だけの足場タグが残ったら、そのメッセージを丸ごと破棄する（fail closed）。残骸を依頼として
救わない。加えて、ブロック除去の中身は「同種の開始タグを含まない文字列」に限定し、タグ名の直後に名前の
終わり（`(?=[\s/>])`）を要求する。

`command-*` タグはこの規則の対象外とし、`/name args` へ畳んで元の位置へ差し込む。

### 検討した代替案

#### 代替案 1: fail open（除去できなかった分は中身を残す）

- 長所: 引き継ぎが最大限残る。`tag_stripping` と実装方針が揃う
- 短所: 実測で回避が成立した。`<open></close>PAYLOAD</close>` は非貪欲マッチが空の中身を食い、`PAYLOAD` が
  孤立閉じタグとともに残る。孤立タグ除去がその閉じタグを消すため痕跡も残らない
- 却下理由: 注入先がプロンプト境界である以上、「残す」側に倒した誤りは次セッションの判断を汚染する。
  「捨てる」側に倒した誤りは引き継ぎ 1 件の欠落で済む

#### 代替案 2: 足場タグの総数に上限を設け、超過時に破棄する

- 長所: タグ大量入力に対する走査コストと除去回避をまとめて塞げる（ように見えた）
- 短所: 実際に実装して撤去した。上限の根拠だった `.*?` の O(N·n) 走査は、各パターンへ同種開始タグの否定
  先読みを入れた時点で消えていた。実測（閉じタグを伴わない開始タグ）:

  | 入力 | 単純 `.*?` | 否定先読み |
  |---|---|---|
  | 8,000 個 | 4.70 秒 | 0.0012 秒 |
  | 20,000 個（全パターン合計） | — | 0.0053 秒（線形） |

  除去回避のほうは孤立タグ検出が 1 個でも破棄するため上限に依存しない。根拠を失った上限に残るのは「対に
  なった足場ブロックを大量に含む正当な依頼」を丸ごと落とす誤検知だけだった
- 却下理由: 走査コストは正規表現側で解くべきで、入力量の閾値で代用すると誤検知だけが残る

#### 代替案 3: 除去せず、注入時の `strip_tags` だけで防ぐ

- 長所: 追加コードが要らない
- 短所: `strip_tags` の対象は信頼境界マーカー 5 種でハーネス足場は含まれない。対象を広げると、中身を残す
  べき用途（知識カード本文の無害化）と中身を捨てるべき用途が同じ関数に同居し、片方の要件を変えるともう
  片方が静かに壊れる
- 却下理由: 目的の異なる 2 つの規則を 1 つの関数へ寄せる設計上の負債が大きい

#### 代替案 4: 未知タグも含めて `<...>` を一律除去する

- 長所: allowlist の陳腐化を受けない
- 短所: ユーザーが依頼本文に書いた不等号（コード片・比較演算子）や無関係なマークアップを壊す
- 却下理由: 正当な依頼を壊す代償が、未知足場タグを取りこぼす代償を上回る

### 結果

**肯定的**

- 細工された足場ブロックが「直近の依頼」として次セッションへ注入される経路が閉じた
- 否定先読みにより、ブロック除去が対を成さない開始タグを跨いで貫通し、その間にある実依頼を巻き込んで消す
  挙動もなくなった。走査コストも実測で線形に収まる
- タグ名の終わりを要求したことで、`<system-reminders>` や `<local-command-stdout-parser>` のように名前が
  足場名で始まるだけの別タグを巻き込む誤検知が消えた

**否定的**

- 足場タグ名を角括弧付きで引用した正当な依頼（この機能自体の改修依頼が典型）は、孤立開始タグと同じ形になる
  ためメッセージごと落ちる。これは受容した代償である。攻撃者は足場ブロックの中身へ開始タグを注入することで、
  自分が制御する文字列を前に置いた孤立「開始」タグを作れるため、prose 由来か細工由来かを形からは区別できない
- `command-*` を対象外にしたため、この経路だけタグを剥がして中身を残す非対称が残る。中身はユーザー自身が
  タイプしたスラッシュコマンドであり、攻撃者が影響しうる文字列は足場ブロックの内側にあってブロックごと破棄
  されるため、現時点で実証された悪用経路は無い

**リスク**

- 足場タグ名はハードコードした **denylist** であり、列挙漏れは「素通り」として現れる。ホストが新しい足場
  タグを追加すると静かに古び、テストも CI も緑のまま引き継ぎがノイズで埋まる状態へ戻りうる。実際 `/search`
  による実 transcript 273 本の走査で、マルチエージェント配信足場 `<agent-message from="...">` が列挙から
  漏れて中身ごと素通りしていることが見つかった（本 ADR 採択と同日に追加）
- この陳腐化の検知手段として、実 transcript コーパスに対する回帰スキャンで「対を成す未知タグ」だけを警告
  する案がある（同走査での実測は 273 本で誤検知 0 / 真の漏れ 1 件検出）。本 ADR では採らず、
  [ADR-0016](06-staleness-detection.md) で採択した
- タグ語彙による検知は**タグを持たない足場**を原理的に見ない（共通原則を参照）
