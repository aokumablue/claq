# シェルコマンド解析の境界 — 誤検出を誤通過より選ぶ

保護フックはシェルコマンド文字列を静的に解析して判定する。完全な意味解釈は原理的に不可能
なので、どこで倒すか・どこを非目標とするかを決める必要がある。

| ADR | 決定 | 日付 | ステータス |
|---|---|---|---|
| [ADR-0002](#adr-0002-git-commit--シェル保護フックの検出境界は誤検出を誤通過より選ぶ) | 解析できない構文は誤検出（安全側）へ倒す。解析できない構文への対応拡張は非目標 | 2026-08-18 | accepted |
| [ADR-0013](#adr-0013-バイナリ判定で-secret-検査を止めない) | バイナリ判定は lint 抑制にのみ使い、secret 検査は必ず実施する | 2026-08-27 | accepted（[ADR-0001](01-hook-failure-direction.md) の受容を撤回） |
| [ADR-0017](#adr-0017-heredoc-のデータ本文はコマンド列として解析しない) | heredoc のデータ本文はトークン化の前段で除去する（4 条件を除く） | 2026-08-31 | accepted（2026-09-06 改訂） |
| [ADR-0018](#adr-0018-cd-を含むコマンドでは-repo-スコープ判定を信用せず-deny-する) | `cd` を含むコマンドでは repo スコープ判定を適用せず deny する | 2026-09-03 | accepted |
| [ADR-0020](#adr-0020-シェル保護フックは-1-つのコマンド文字列を-2-つのシェル方言で解析する) | 1 つのコマンド文字列を POSIX 読みと Windows 読みの 2 通りで解析する | 2026-09-04 | accepted |
| [ADR-0021](#adr-0021-実行位置の特定は-wrapper-allowlist-で行いgit-起動の探索は全トークン走査のままにする) | 実行位置が要る側だけ wrapper allowlist を持つ。兄弟フックの非対称は意図的 | 2026-09-06 | accepted |

## 共通原則

**トークナイザベースの判定は、解析できない構文に対して必ずどちらかに倒れる。** 倒し方を
経路ごとに場当たりで決めると、監査は「なぜここは検出するのにここは検出しないのか」を毎回
指摘し続ける。したがって方向を 1 つに固定する — **誤検出（安全側に厳しく倒す）を誤通過
（見逃す）より選ぶ**（ADR-0002）。

この原則は以後の ADR で繰り返し再導出されている。以下は**適用範囲の明確化**であって
ADR-0002 の例外ではない。混同を避けるため、何が不確定なのかを軸に整理する。

| 不確定なもの | 扱い | ADR |
|---|---|---|
| 構文（エイリアス・変数展開・多段 `sh -c`・`eval`） | 非目標。検出しない | ADR-0002 |
| 構文だが環境非依存に確定できる（heredoc の本文範囲） | 確定できる場合だけ除去し、できなければ検出側 | ADR-0017 |
| 実行時状態（`cd` 後の cwd） | 判定を放棄して無条件 deny | ADR-0018 |
| 入力の読み方（シェル方言） | 両方で読み、どちらかが検出したら deny | ADR-0020 |
| 実行位置（wrapper を何語読み飛ばすか） | 名前集合が原理的に不可避。allowlist を採る | ADR-0021 |
| 内容の種別（バイナリかテキストか） | 検査を止める根拠にしない | ADR-0013 |

**ただし「誤検出を選ぶ」は無制限ではない。** ADR-0020 代替案 2（`\` を含むコマンドを一律
deny）は「誤検出の量が使えない水準になる」として棄却されている。可用性が壊れる水準の誤検出は
ADR-0002 の射程外である。

**`_command_name` による正規化は 1 関数に集約する。** basename 化 + 小文字化 + `.exe` 除去
を実行コマンド判定だけに適用し、wrapper 読み飛ばしと `cd` 判定に適用しないと、
`CD ..; rm ruff.toml` が ADR-0018 の無条件 deny 分岐へ落ちず**誤通過**する（実測）。

## ADR-0002: git commit / シェル保護フックの検出境界は誤検出を誤通過より選ぶ

**日付**: 2026-08-18  **ステータス**: accepted

### コンテキスト

`block_no_verify`（`git commit --no-verify` の検出）・`bash_config_protection`（Bash 経由の
設定ファイル直接書き換え検出）・`pre_bash_commit_quality`（`git commit` の検出）は、いずれも
POSIX シェルコマンド文字列を `hook_common.tokenize` / `split_segments` で解析して判定する。
POSIX シェルの完全な構文解釈は原理的に不可能に近く（`$(...)`・変数展開・エイリアス・多段
`sh -c`・`eval` が無限に組み合わさる）、監査は複数ラウンドにわたって同種の検出漏れ・誤検出を
指摘してきた。

- A-02: 書き込み先が引数に明示されない `python -c` / `eval` / 任意スクリプト経由の間接書き込みは
  `bash_config_protection` が検出しない
- A-04: `block_no_verify` は `sh -c 'sh -c "git commit --no-verify"'` や
  `eval "git commit --no-verify"`、command substitution を検出しない
- 前ラウンド: エイリアス・変数展開・任意ラッパースクリプト経由の呼び出しの非対応
- 前ラウンド: `pre_bash_commit_quality` の `echo "git commit"` を commit と誤検出する挙動

表面上は別々の指摘に見えるが、根は 1 つ（共通原則を参照）。

### 決定

**解析できない構文・判定が割れるケースは、常に「誤検出（false positive）」を「誤通過
（false negative）」より選ぶ。** ただし「解析できない構文そのものへの対応」は非目標として
明記し、無理に対応範囲を広げない。

- `block_no_verify` / `bash_config_protection` の非目標: シェルエイリアス・シェル関数・変数
  展開・コマンド置換・2 段以上の `sh -c` / `eval`・`git` 以外の名前を持つラッパースクリプト
  経由の呼び出し。これらは検出しない（false negative を許容する）
- 一方で `pre_bash_commit_quality` の `echo "git commit"` 誤検出は「安全側」として維持する。
  誤って quality scan を実行するコストは、commit を見逃すコストより小さい
- A-02 で書き込み先が引数位置に明示されるコマンド群（`cp` / `mv` / `install` / `ln -f` /
  `dd of=` / `perl -i`、リダイレクト演算子 `&>` / `>|` 等）は「解析できる」範囲なので対応した。
  一方 `python -c "open('x','w').write(...)"` や `eval` 経由の間接書き込みは非目標のまま

### 検討した代替案

#### 代替案 1: 完全な POSIX シェル AST パーサを導入する

- 長所: エイリアス・変数展開・多段ラッパーまで正確に解決できれば false negative が大幅に減る
- 短所: POSIX シェルの完全な意味解釈は実行時の環境（定義済みエイリアス・環境変数の値・PATH
  上の実行ファイル）に依存し、静的解析だけでは原理的に再現できない。実装コストも著しく大きく、
  依存ゼロ方針（標準ライブラリのみ）とも相容れない
- 却下理由: 「うっかり事故の抑止」という設計目標に対して過剰投資であり、かつ原理的に解けない
  問題を含む

#### 代替案 2: 解析できない構文はすべて deny（fail-closed）にする

- 長所: 見逃しがゼロになる
- 短所: 両フックは Bash という最も広い matcher に登録されているため、解析できない構文を一律
  deny すると `git commit` や設定ファイル書き込みと無関係な大多数の Bash 呼び出し（`$(date)`
  を含むログ出力等）まで巻き込み、可用性が壊れる
- 却下理由: [ADR-0001](01-hook-failure-direction.md) と同じ理由。検査対象が確定できない状況を
  deny に倒すと、通常作業ができなくなる被害の方が大きい

### 結果

**肯定的** — 「うっかり事故の抑止であり敵対的回避への防壁ではない」という一貫した設計境界が、
3 つのフックすべてで同じ言葉で説明できるようになった。A-02 の実害部分は「解析できる」範囲
として修正済み。

**否定的** — `python -c` / `eval` / 任意スクリプト経由の間接書き込み、2 段以上の `sh -c`・
変数展開経由の `--no-verify` 回避は、今後も検出されない。

**リスク** — 本フック群を「敵対的な回避を防ぐセキュリティ境界」だと誤認して運用すると、上記の
非対応経路が実害になりうる。`block_no_verify.py` / `bash_config_protection.py` のモジュール
docstring に「非目標」として明記し続けることで誤認を防ぐ。

## ADR-0013: バイナリ判定で secret 検査を止めない

（[ADR-0001](01-hook-failure-direction.md) の受容を撤回）

**日付**: 2026-08-27  **ステータス**: accepted
**関係**: ADR-0001 の「バイナリ偽装は受容するリスク」という判断のみを supersede する。
fail-open / fail-closed の境界規則そのものは維持する。

### コンテキスト

ADR-0001 は次を明示的に受容していた。

> バイナリ判定されたファイルは secret scan 自体をスキップし severity warning の痕跡を残す
> （error にはしない — 画像等の commit を一律ブロックすると明示要件に反する）。NUL バイトを
> 混ぜて secret 混入を隠すバイナリ偽装は、この skip の副作用として受容するリスクであり、
> 積極的に防ぐ設計目標ではない。

2026-08-26 の実機監査 F-06(b) がこの経路を実際に通した。`evaluate()` の入口から決定的
fixture で実行し、先頭に NUL を 1 バイト置いた内容が `exitCode: 0` で通ることを確認している。

再評価の決め手になったのは、**コード自身が逆の不変条件を宣言していた**ことである。
`commit_quality_scanner._is_binary_content` の docstring は

> この判定は lint チェックの抑制にのみ使用し、シークレット検出には使いません（バイナリ判定を
> 悪用して secret 検査を回避できないようにするためです）

と書いているのに、同じファイルの `find_file_issues` はまさにそれを行っていた。ADR-0001 の
受容文とコード内の宣言が真っ向から矛盾しており、どちらか一方は必ず動かさなければならない
状態だった。

### 決定

**バイナリ判定は lint チェックの抑制にのみ用い、secret 検査の実施可否には用いない。**
バイナリ判定された内容に対しては、行分割の代わりに `_extract_printable_runs`（`strings(1)` と
同じ発想で、NUL を含む制御文字で区切られた 4 文字以上の連続を抽出）を走査単位として、通常と
同じ secret パターンを適用する。抽出文字列は実際の行に対応しないため、行番号は報告せず
`in extracted binary content` と表示する。

`secret_scan_skipped`（severity warning）の痕跡 issue は不要になったので削除した。

「画像等のバイナリ commit を一律ブロックしない」という既存の要件は維持される。真のバイナリは
secret パターンに一致する印字可能文字列を通常含まないためである（PNG ヘッダを含む fixture で
error ゼロを確認済み）。

### 検討した代替案

#### 代替案 1: ADR-0001 の受容を維持し、コード側の docstring を実態へ合わせる

- 長所: 実装変更ゼロ。矛盾は文言修正だけで解消する
- 短所: 回避コストが「先頭に NUL を 1 バイト置く」と極端に低い。commit 品質フックの中核価値は
  secret の混入防止であり、そこだけが最も安く迂回できる状態を「設計どおり」と宣言することに
  なる。ADR-0002 とも整合しない — NUL 偽装は解析できない構文ではなく、判定できる入力に対して
  意図的に検査を止めている
- 却下理由: 受容の根拠だった「修正コストが高い」が成り立たない。印字可能文字列の抽出は正規表現
  1 本であり、既存のパターン集合をそのまま再利用できる

#### 代替案 2: 拡張子 / MIME / 明示 allowlist で真のバイナリだけを skip する

- 長所: 画像等を確実に素通しでき、走査コストも下がる
- 短所: allowlist は「.png という名前のテキストファイル」を素通しにする。攻撃コストは NUL
  1 バイトから拡張子の付け替えに変わるだけで、質的な改善がない。加えて拡張子・MIME テーブル
  という保守対象が増える
- 却下理由: 回避コストをほとんど上げないまま保守対象だけが増える

#### 代替案 3: バイナリを一律 deny する

- 長所: 実装が最も単純で、見逃しがゼロになる
- 短所: 画像等の commit ができなくなる。ADR-0001 が「ユーザーの明示要件に反する」として却下済み
- 却下理由: 同じ要件が依然として有効

### 結果

**肯定的** — `_is_binary_content` の docstring が宣言する不変条件を、実装が初めて満たす。
NUL 1 バイトによる secret 検査回避が塞がれた（severity は `error` なので検出時は commit が
ブロックされる）。走査単位が減るため、真のバイナリに対する走査コストはむしろ下がる。

**否定的** — 抽出文字列は行に対応しないため、バイナリ内で検出した secret の位置を行番号で
示せない（`line: 0` と `in extracted binary content` で表現する）。

**リスク** — 印字可能文字列を偶然含む真のバイナリが secret パターンに一致すると、false
positive で commit がブロックされる。ADR-0002 に従いこの方向の誤りは許容する。実測では PNG
ヘッダで誤検出しないことを確認しているが、全バイナリ形式を検証したわけではない。制御文字で
区切られない形（すべて印字可能文字で構成された独自バイナリ）はそもそもバイナリ判定されない
ため、通常のテキスト経路で走査される。

## ADR-0017: heredoc のデータ本文はコマンド列として解析しない

**日付**: 2026-08-31  **ステータス**: accepted（2026-09-06 改訂: 除去しない条件を 4 つへ）

### コンテキスト

保護フック 3 種は `hook_common.tokenize`（`shlex`）でコマンド文字列をトークン化して判定する。
`shlex` は heredoc を解釈しないため、本文行も通常のトークンとして返る。その結果、本文に書いた
**散文**が実行命令として読まれる。v0.9.44 の実起動で確認した誤発火は次の 3 件（いずれも
`<<'EOF'` のクォート付き区切り＝シェルが一切展開しない純データ）:

- `cat > note.md <<'EOF'` の本文に `git commit --no-verify` → `block_no_verify` が exit 2
- 同形の本文に `printf x > pyproject.toml` → `bash_config_protection` が exit 2
- 同形の本文に `git commit` → `pre_bash_commit_quality` が staged 検査へ入り、index に問題が
  あれば exit 2

対照として `echo 'git commit --no-verify'` は exit 0 になる（`shlex` がクォート内を 1 トークン
に保つため）。つまり「同じ語をクォートで囲めば通り、heredoc に書くと落ちる」という非対称が
出ている。このリポジトリ自身の文書はフックの禁止事項を頻繁に名指しするため、自分のフックを
説明する文書を自分のフックが書かせない状態になっていた。

一方で `bash <<'EOF'` / `cat <<'EOF' | bash` では本文が**実際に実行される**。実測でもこれらは
exit 2 であり、本文を一律に除去すれば ADR-0002 が禁じる誤通過が生まれる。

### 決定

heredoc の**データ**本文は、トークン化の前段でコマンド文字列から除去する
（`hook_common.strip_data_heredoc_bodies`）。ただし本文がデータだと**静的に確定できる場合
だけ**除去し、確定できなければ除去せず現状の検出側へ倒す。除去しない条件は次の 4 つ:

1. 演算子行に**本文を実行するトークン**がある。`SHELL_WRAPPER_EXECUTABLES`（`sh` / `bash` /
   `zsh` / `dash` の basename）に加えて、実行ファイルではないが渡されたテキストを現在のシェル
   で実行するビルトイン `_BODY_EXECUTING_BUILTINS`（`.` / `source` / `eval`）を含む。判定軸は
   「本文が実行されうるか」であって「実行ファイルか」ではない
2. 演算子行が継続演算子（`\` / `|` / `&`）で終わる — 本文の開始位置が次行とは限らない
3. 終端行が見つからない（未終端）
4. `<<` がそもそも heredoc 演算子ではない（コメント内・クォート内・`\` エスケープ後）。この
   場合 heredoc は開始せず、後続行は**実行されるコマンド**なので、本文として剥がすと保護フック
   が素通りする。判定は演算子の走査が持つクォート／コメント状態で行い、状態は**非本文行だけ**
   を鎖にして更新する（本文行・終端行はシェルの語彙ではないため）

条件 4 は本 ADR の前提そのものに対する例外ではなく、前提が成立する範囲の明示である。「本文
範囲は演算子・区切り語・終端行だけで決まる」は `<<` が演算子であるときにしか成立せず、`<<` が
演算子かどうかは行内のクォート／コメント状態に依存する。この状態は heredoc の外側から持ち越さ
れるため、演算子の検出だけでは決まらない。

これは ADR-0002 の例外ではなく**適用範囲の明確化**である。ADR-0002 の「誤検出 > 誤通過」は
解析できない構文についての規定であり、heredoc の本文範囲は演算子・区切り語・終端行だけで決まる
環境非依存の構文であって、エイリアス・変数展開・PATH のような環境依存の意味解釈を含まない。

### 検討した代替案

#### 代替案 1: NO-FIX（ADR-0002 を根拠に据え置く）

- 長所: 変更ゼロ。誤通過リスクを一切増やさない
- 短所: 文書作成という標準作業が塞がれる。`pre_bash_commit_quality` の誤発火は index の状態に
  依存するため再現性がなく、抑止として機能せず誤った安心感だけを残す
- 却下理由: ADR-0002 の適用範囲は解析できない構文であり、heredoc はそれに当たらない

#### 代替案 2: `tokenize` / `tokenize_with_status` の内部で正規化する

- 長所: 修正点が 1 箇所で済む
- 短所: `pre_bash_commit_quality` の生文字列正規表現フォールバックが非正規化のまま残り FP が
  半分残る。4 フックの挙動が 0 行 diff で変わり、フック単位の被覆を説明できない
- 却下理由: 穴が残り、被覆の説明可能性も失う

#### 代替案 3: `lib/harness.iter_bash_commands` で正規化する

- 長所: 全フックを 1 点で覆える
- 短所: list 形状のコンテナを改行で連結する仕様のため heredoc が合成境界をまたぐ。`sh -c` の
  再帰経路も覆えない。payload 形状の責務にシェル構文の知識が混ざる
- 却下理由: 責務の混在と、覆えない経路が残ること

#### 代替案 4: データ消費コマンドの allowlist（`cat` / `tee` / `jq` のときだけ剥がす）

- 長所: さらに検出側へ倒れる
- 短所: 集合が無限に広がり、列挙から漏れたコマンドで FP が戻る
- 却下理由: 「実行されうる形か」という判定軸に直接対応するのは denylist 側

### 結果

**肯定的**

- 実測 FP 3 件が解消し、文書作成が保護フックに阻まれなくなった
- `SHELL_WRAPPER_EXECUTABLES` が `hook_common` へ移り、`sh -c` 再帰と heredoc 判定が同じ集合を
  参照する（判定軸が 2 つに割れない）
- 終端行を残す設計により正規化は冪等で、適用点がフックごとに異なっても二重適用が安全
- 条件 4（クォート／コメント状態）により、`#` で始まる行の `<<` を演算子と読んで後続の**実行
  される**コマンドを本文として捨てる経路が閉じた。実測（v0.9.52）:

  | フック | コマンド | 条件 4 あり | 条件 4 なし |
  |---|---|---|---|
  | `block_no_verify` | `# <<EOF` ↵ `git commit --no-verify -m x` ↵ `EOF` | exit 2 | **exit 0** |
  | `bash_config_protection` | `# <<EOF` ↵ `printf x > ruff.toml` ↵ `EOF` | exit 2 | **exit 0** |
  | `pre_bash_commit_quality` | `# <<EOF` ↵ `rm app.py && git commit -m 'fix: x'` ↵ `EOF` | exit 2 | **exit 0** |

  いずれも `# <<EOF` の 1 行を先頭へ置くだけで成立し、3 種の保護フックが同時に素通りしていた。
  除去側の誤りは「文書が書けない」ではなく「保護が消える」形で出る、という点で条件 1〜3 と質が
  違う

**否定的**

- 非シェルインタプリタ（`python3 - <<EOF` 等）の本文が間接的にシェルを起動する形は検出できない。
  これは ADR-0002 が `python -c` 経由の間接実行を既に非目標としたのと同じ境界であり、一貫している
- 終端行の後続に空白がある場合（`EOF `）は POSIX どおり終端しない。bash 自身も終端しないため
  穴ではないが、直感には反する

**リスク**

- `cat <<'EOF' |` で改行し次行が `bash` という形は、本文の開始位置が次行ではないため「継続
  演算子で終わる行は残す」規則で守っている。この規則は後から「冗長」と見えて単純化されやすい。
  `tests/hooks/test_hook_common.py` の表と `tests/hooks/test_heredoc_boundary.py` の横断表で固定する
- ネストした heredoc（`<<'OUTER'` の本文に `<<'INNER'`）で走査が同期ずれを起こすと静かな誤通過に
  なる。本文走査中は `<<` を再検出しない設計とし、テストで固定した
- 条件 4 のクォート状態は**非本文行だけ**を鎖にして更新する。本文行を鎖に含めると、本文中の `'`
  が外側のクォート状態を反転させて以後の演算子検出がずれる。逆に鎖をリセットすると、行をまたぐ
  クォート（`echo '` ↵ `<<EOF'`）の内側が演算子に見える。どちらも静かな誤通過なので、横断表で固定する

## ADR-0018: `cd` を含むコマンドでは repo スコープ判定を信用せず deny する

**日付**: 2026-09-03  **ステータス**: accepted

### コンテキスト

`bash_config_protection` は保護対象ファイル（`ruff.toml` / `pyproject.toml` 等）への Bash 経由の
書き込みを検出するが、deny するのは書き込み先が**現在のリポジトリ配下**にある場合だけである
（A-06）。この repo スコープ判定は、書き込み先トークンを `Path.cwd()` 基準で解決して `repo_root`
配下かを見る形で実装されていた。

`cd` は同じコマンド文字列の中で cwd を動かす。フックはコマンドを**実行前**に静的解析するため、
`cd` 以降のセグメントに現れる相対パスは実行時の位置とずれる。実測（v0.9.48）:

- `cd plugins && printf 'x' > ../ruff.toml` → exit 0（素通り）。実行時の書き込み先はリポジトリ
  直下の `ruff.toml` だが、フックは cwd 基準で `<repo>/../ruff.toml` と解決し「リポジトリ外」と
  判定していた
- 対照 `printf 'x' > ruff.toml` は exit 2

`cd` の有無だけで保護が外れるため、これは「うっかりバイパス」の抑止としても成立していない。
なお構文自体は問題なく解析できており、ADR-0002 の規定はこのケースを直接には覆わない。ずれて
いるのは構文解析ではなく**スコープ規則の前提**（cwd が実行時まで不変であること）である。

### 決定

**コマンドが `cd` / `pushd` / `popd` / `chdir` を含む場合、repo スコープ判定を適用せず、保護
対象 basename のヒットをそのまま deny する。**

`cd` を跨いだ symlink 解決のずれは同じ理由で非目標とする（解決の基準点が不明なまま symlink を
辿っても結果は信用できない）。

これは ADR-0002 の適用範囲の拡張であり、ADR-0017 が heredoc について行ったのと同じ「スコープ
規則の明確化」に当たる。ADR-0002 が扱うのが**構文**の不確定性であるのに対し、本 ADR が扱うのは
**実行時状態**（cwd）の不確定性である。倒す向きは同じ。

### 検討した代替案

#### 代替案 1: NO-FIX（`cd` 経由の書き込みは非目標と明記する）

- 長所: 変更ゼロ。false positive を一切増やさない
- 短所: `cd` を 1 つ足すだけで保護が外れる。「保護がある」という表示が誤った安心になる状態が
  残り、ADR-0002 が繰り返し指摘を招くと述べた「経路ごとに場当たりで倒し方を決める」状態そのもの
  になる
- 却下理由: 抑止として機能しない保護を残す判断だから

#### 代替案 2: `cd` を追跡して解決基準点を更新する

- 長所: 判定が正確になり、false positive が増えない。`cd /tmp && printf x > ruff.toml` のように
  リポジトリ外が確定するケースを正しく allow できる
- 短所: サブシェル（`(cd /tmp; ...)`）・パイプライン内の `cd`・`cd -`・変数展開を含む
  `cd "$D"` を正しく扱うにはシェルのスコープ規則の模倣が要る。`split_segments` は `(` / `)` を
  区切りとして捨てるため、サブシェルの境界情報は既に失われている。さらにこの案は**現在 deny して
  いるケースを allow へ緩める**方向の変更を含む
- 却下理由: 誤通過を新たに作りうる緩和を、模倣の正確さに依存する実装で導入することになるため。
  ADR-0002 の「無理に対応範囲を広げない」に反する

### 結果

**肯定的** — `cd` の有無で保護が外れる経路が閉じる。判定できない状態の倒し方が
`block_no_verify` / `bash_config_protection` で揃う。

**否定的** — リポジトリ**外**のディレクトリへ `cd` してから保護対象と同じ basename のファイルを
書く操作が deny される。使い捨てフィクスチャを scratchpad に `ruff.toml` という名前で作る手順が
これに当たる（既知の pitfall `config-protection-denies-fixture-config-basenames` と同じ回避策が
効く: フィクスチャに保護対象の basename を使わない）。

**リスク** — `cd` を含む長いコマンドで、書き込み先が明らかにリポジトリ外でも deny される。回避は
`cd` を別の Bash 呼び出しへ分けるか、basename を変えること。いずれも agent 側で完結し、保護
フックの無効化を伴わない。

## ADR-0020: シェル保護フックは 1 つのコマンド文字列を 2 つのシェル方言で解析する

**日付**: 2026-09-04  **ステータス**: accepted

### コンテキスト

`block_no_verify` と `bash_config_protection` は `tool_input.command` を `shlex(posix=True)` で
トークン化して判定する。POSIX シェルではクォート外の `\` は「次の 1 文字をエスケープする記号」
なので、これは正しい解析である。

Windows ホストのシェルツールは PowerShell であり（release-verify 2026-09-03 §9.1 で
`Get-Command python3` 等の PowerShell 構文が実際に実行されている）、PowerShell と cmd では `\` は
**ただのパス区切り**である。その結果、同じ文字列が方言によって別のトークン列になる。実測:

| コマンド | POSIX 読み（当時） | 実際の Windows での意味 |
|---|---|---|
| `rm .\.eslintrc` | `['rm', '..eslintrc']` | `.eslintrc` の削除 |
| `C:\Git\bin\git.exe commit --no-verify` | `['C:Gitbingit.exe', ...]` | git のフックバイパス |

前者は保護対象 basename に一致せず、後者は `is_git_executable_token` が git と認識できない。
どちらも**Windows でだけ保護フックが素通りする**。

hook の入力にシェル種別は載っていない。`tool_name` は `Bash` / `shell` / `run_terminal_command`
等でホストの実装依存であり、そこから実行シェルの方言を確定することはできない。

### 決定

**保護フックは、コマンド文字列を「POSIX 読み」と「Windows 読み」の 2 通りで解析し、どちらかが
検出したら deny する。**

- Windows 読みの作り方は `\` の直後の文字で 3 通りに分ける（`hook_common.command_dialect_variants`）:
  - **パス構成文字** → `/` へ置換（`.\ruff.toml` → `./ruff.toml`）
  - **空白 / タブ** → `\` を除去（`my\ ruff.toml` → `my ruff.toml`）。エスケープを持たない
    シェルでは 2 引数であり、2 番目が実際に書き込み対象になる
  - **`/`** → 変換しない（`\/` は sed スクリプト等の POSIX エスケープで、Windows のパス区切りには
    現れない）
- Windows 読みが元と同じになるコマンドは、追加の解析をしない
- 変換関数は `hook_common` に 1 つだけ置き、2 フックが共有する

あわせて、実行位置のコマンド名比較を **basename 化 + 小文字化 + `.exe` 除去**（`_command_name`）へ
統一し、PowerShell / cmd の書き込み語彙を加えた: 長形式 cmdlet（`Remove-Item` / `Clear-Content` /
`Set-Content` / `Add-Content` / `Out-File` / `New-Item` / `Copy-Item` / `Move-Item`）と、cmd 組み込み・
PowerShell 既定エイリアス（`del` / `erase` / `rd` / `copy` / `move` / `ri` / `mi` / `clc` / `cpi` /
`sc` / `ac` / `ni`）。`rm` / `cp` / `mv` は PowerShell の別名として同じ cmdlet に解決されるため既に
効いていたが、長形式・別名・`.exe` 付きで書かれると外れていた。

`pre_bash_commit_quality` も同じ方言展開で `git commit` を探す（`_detect_git_commit`）。ここだけ
POSIX 読み 1 本だと、`C:\Git\bin\git.exe commit -m x` が `block_no_verify` では検出されるのに品質
ゲートだけ素通りする非対称になる。

### 根拠

- **ADR-0002 の範囲内。** 方言が確定できない以上、片方だけで解析するのは「解析できていない」
  ことを allow へ倒すのと同じである
- **誤検出と誤通過を分けて実測した。** 当初は `\` を無条件に `/` へ置き換えていたが、この変換は
  basename を変えるだけでなく**トークン境界を作り替える**。実測で 3 件が deny 側へ倒れたが、
  3 件は性質が違う:
  - `sed -i 's/\.git\/hooks\/pre-commit//' notes.md` は**純粋な誤検出**。`\/` は Windows のパス
    区切りに現れず、変換対象から外しても検出力は落ちない → 除外した
  - `rm my\ ruff.toml` と `git commit -m fix\ --no-verify` は**POSIX では誤検出だが Windows では
    真陽性**。エスケープを持たないシェルでは `my\` と `ruff.toml`、`fix\` と `--no-verify` が別
    引数になり、実際に `ruff.toml` が削除され `--no-verify` が git へ渡る。一度これを「誤検出」と
    見て除外したが、security-auditor の指摘で誤通過を新規に作っていたと判明し撤回した。現在は
    `\` を除去して検出側へ倒す

  Windows 側の検出（`rm .\ruff.toml` / `C:\Git\bin\git.exe commit --no-verify`）はいずれも維持。
  クォート済み（`rm "my\ ruff.toml"`）は 1 トークンのままなので誤検出は増えない。残る誤検出
  （例 `rm a\.eslintrc`）は ADR-0002 が受容する側であり、characterization test として固定してある
- **プラットフォーム分岐ではない。** 実行中の OS を見て挙動を変えるのではなく、入力を 2 通りに
  読む。macOS/Linux でも同じコードパスが走り、テストもそこで両方の読み方を踏める（Windows 専用の
  未検証分岐を作らない）
- **大小無視は既存の判断の踏襲。** `is_git_executable_token` は「macOS 既定の APFS が大小を区別
  しない」ことを理由に既に lower している。PowerShell の cmdlet 解決も大小無視なので揃えた。
  Linux では `RM` が `rm` に一致する誤検出側へ倒れるが、これも ADR-0002 の範囲内

### 検討した代替案

#### 代替案 1: 実行シェルを推定して方言を選ぶ

- 長所: 誤検出が原理的に発生しない
- 短所: 推定材料が無い。`tool_name` はホスト実装依存で、`Bash` という名前のツールが Windows では
  PowerShell を回している可能性を排除できない。`platform.system()` はフックが動く OS を示すだけで、
  ホストがどのシェルへ渡すかは決まらない（Windows 上の Git Bash 経由もありうる）
- 却下理由: 推定を外したときの失敗が「保護の無効化」であり、[ADR-0008 改訂 2](03-plugin-root-resolution.md)
  でユーザーが明示した「リスクがあるとみなせる推測 fallback を採らない」方針に反する

#### 代替案 2: `\` を含むコマンドは無条件で deny する

- 長所: 実装が最も単純
- 短所: POSIX で `\` は日常的に現れる（エスケープ・行継続）。ほぼ全ての複数行コマンドが拒否され、
  実用にならない
- 却下理由: 誤検出の量が「使えない」水準になる。ADR-0002 は誤検出を選ぶと言っているが、無制限に
  選ぶとは言っていない

#### 代替案 3: `shlex(posix=False)` の結果も併用する

- 長所: バックスラッシュを保つ「もう 1 つの読み方」を標準ライブラリから得られる
- 短所: `posix=False` はクォートをトークンに残すため、basename 比較の前に独自のクォート剥がしが
  必要になる。剥がし方の規則が 3 つ目の方言として増える
- 却下理由: `\` → `/` の置換のほうが、規則が 1 行で、テストで全域を示せる

### 影響

- `hook_common.command_dialect_variants()` を追加。`block_no_verify` は
  `_has_bypass_flag_in_dialect`、`bash_config_protection` は `_find_protected_write_in_dialect`、
  `pre_bash_commit_quality` は `_detect_git_commit` で、Bash 系 3 フックすべてが入口で方言を回す
- `bash_config_protection` の名前比較 3 箇所（実行コマンド判定・wrapper 読み飛ばし・`cd` 判定）と、
  縮退経路 `_raw_text_write_risk` の保護名照合がすべて大小無視になった
- heredoc のデータ本文除去は、両フックとも「方言展開の前に 1 回」へ揃えた（片方が方言ごとに剥がす
  形だと、同じ入力でもフックによって解析対象が変わる）
- Windows 実機での検証は未実施。方言変換自体は macOS のテストで両側を踏める（Windows 固有の分岐を
  持たない設計にしたのはこのため）

## ADR-0021: 実行位置の特定は wrapper allowlist で行い、git 起動の探索は全トークン走査のままにする

**日付**: 2026-09-06  **ステータス**: accepted

### コンテキスト

Bash 系の保護フック 2 つは、コマンド文字列のどこを見るかで正反対の方針を採っている。

`block_no_verify` はモジュール docstring で方針を明記している —— 「ラッパー名（`env` / `sudo` /
`nice` …）のホワイトリスト方式は将来のラッパーを取りこぼすため採らず、**トークンの basename が
`git`** なら git 起動とみなす」。セグメント先頭を前提にすると `sudo git commit --no-verify` /
`xargs -I% git ...` が素通りするためである。

`bash_config_protection` は逆に `_COMMAND_POSITION_WRAPPERS` という allowlist を持ち、`env` /
`sudo` / `timeout` / `nice` / `nohup` / `stdbuf` / `xargs` 等を読み飛ばして「実際に実行される
executable の index」を求める（`_command_index`）。

同じリポジトリの兄弟フックで方針が割れているため、片方の判断がもう片方へ「未修正の取りこぼし」
として流用されかねない。実際 `_COMMAND_POSITION_WRAPPERS` は release-verify のたびに要素が追加
されており、allowlist が原理的な弱点だという読みを誘っている。

### 決定

この非対称は意図的なものとして維持する。両フックは**必要としている判定が違う**。

`block_no_verify` が要るのは「このコマンドで git が起動されるか」だけで、git が何番目の語かは
結論に影響しない。だから名前集合を持たずに済み、持たないほうが強い。

`bash_config_protection` は実行位置の特定そのものを必要とする。M-01 が要求するのは
`tee pyproject.toml`（deny）と `echo tee pyproject.toml`（allow）の区別だが、この 2 つは構文上
まったく同じ「語 → 語 → パス」であり、分けるのは `echo` と `timeout` の**意味論**であって構文
ではない。したがってここでは何らかの名前集合が原理的に不可避で、選べるのは「wrapper を列挙する」
か「データを取るコマンドを列挙して残り全部を wrapper とみなす」かの 2 択しかない。前者
（allowlist）を採る。

allowlist の唯一の一般化として、wrapper を 1 つ以上通過した後に限り、数字で始まる非オプション語を
wrapper 自身の positional 値として読み飛ばす（`timeout 5 rm` の `5`、`nice -n 5 rm` のレベル）。
実行ファイル名が数字で始まることはまず無いためである。

### 検討した代替案

#### 代替案 1: `block_no_verify` の全トークン走査を `bash_config_protection` へ転用する

- 長所: 方針が 1 つに揃い、未知の wrapper を取りこぼさない
- 短所: 実行位置の情報がそもそも生まれないため、M-01 の false positive が丸ごと戻る。
  `echo tee pyproject.toml` / `echo timeout 5 rm ruff.toml` のような**言及**が deny になる
- 却下理由: `block_no_verify` が全トークン走査で足りるのは実行位置を必要としないからであって、
  方式が優れているからではない。必要としている判定が違う以上、転用できない

#### 代替案 2: データを取るコマンドを列挙し、残りを一律 wrapper とみなす（fail-closed 側）

- 長所: ADR-0002 の「誤検出 > 誤通過」に姿勢が合い、未知の wrapper を取りこぼさない
- 短所: 実測（v0.9.52、`_command_index` を差し替えて計測）で 2 件の実害が出た。

  | コマンド | 現行 | fail-closed 版 |
  |---|---|---|
  | `pushd sub && printf x > ../ruff.toml` | exit 2 | **exit 0** |
  | `cd sub && printf x > ../ruff.toml` | exit 2 | **exit 0** |
  | `grep -rn tee ruff.toml` | exit 0 | **exit 2** |

  1・2 行目は `pushd` / `cd` を wrapper として消費してしまうため `_changes_working_directory` が
  False を返し、repo スコープ判定が復活して `../ruff.toml` がルート外と判定される。ADR-0018 が
  置いた「cwd を動かすコマンドがあれば無条件 deny」という分岐が丸ごと失われる。3 行目は読み取り
  専用コマンドの引数を書き込み先と読む false positive
- 却下理由: fail-closed へ寄せたつもりで **ADR-0018 の deny 分岐を失っている**。Bash は最も広い
  matcher であり可用性の代償が最も大きい経路でもあるため、「有界な取りこぼし」を「無界な誤検出 +
  既存 deny 分岐の喪失」より選ぶ

#### 代替案 3: `block_no_verify` 側を allowlist へ揃える

- 長所: 方針が 1 つに揃う
- 短所: 取りこぼしのコストが非対称。`bash_config_protection` の取りこぼしは「うっかり書き換えを
  1 件見逃す」だが、`block_no_verify` の取りこぼしは `sudo git commit --no-verify` の素通り ——
  フックバイパスそのものである
- 却下理由: 実行位置を必要としない側へ名前集合を導入しても、得るものが無く失うものだけがある

### 結果

**肯定的** — M-01 の false positive（非実行位置での言及）と ADR-0018 の無条件 deny 分岐が両立する。
「なぜ兄弟と違うのか」がコードコメントではなく決定記録として残り、片方へ揃える変更が「未修正の
取りこぼしの修正」に見えなくなる。

**否定的** — `_COMMAND_POSITION_WRAPPERS` に載っていない wrapper（`chrt` 相当の新顔）は取りこぼす。
これは承知のうえの境界であり、numeric positional の消費だけが唯一の一般化である。語彙が増え続ける
形になり、release-verify のたびに追記されうる。

**リスク** — 兄弟の非対称は「片方が直っていない」と読まれて揃えられやすい。両モジュールの該当箇所に
本 ADR への参照を置き、どちらの側から読んでも非対称が意図的だと分かるようにする。allowlist の要素が
静かに減っても、集合リテラルは 1 statement なのでカバレッジでは検出できない。
`tests/hooks/test_protection_bypass_regressions.py` が期待値との完全一致（層 2）と全要素の deny 実測
（層 1）で固定する（M-10）。
