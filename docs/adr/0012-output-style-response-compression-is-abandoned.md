# ADR-0012: LLM 応答の事後圧縮パターン（output-style `slim`）を廃止する

**日付**: 2026-08-26  **ステータス**: accepted

## コンテキスト

`output-styles/slim.md` は「日本語で簡潔に応答。結論先・理由後、敬語なし」という応答スタイルをシステムプロンプトへ強制注入し、出力トークンを削減する仕組みだった。`plugin.json` の `outputStyles` 登録と frontmatter の `force-for-plugin: true` により、bluecore プラグイン配下の全セッションへ無条件で適用されていた。

このパターンは 2 世代の実装を経ている。初代は `hooks/pre_user_prompt.py`（UserPromptSubmit フックで `skills/s-slim/SKILL.md` を毎プロンプト `additionalContext` へ注入、`Settings.slim.enabled` で切り替え）で、output-style 非対応ホスト（Copilot CLI 等）にも効かせるための経路だった。`47a54c9` でフックを削除し、`43277c7` でネイティブの output-style へ移行した。

移行後、**同一種類の障害を 5 回修正しても再発した**。

| commit | 内容 |
|---|---|
| `642ba7a` | output-styles/slim による tool use の破損解消 |
| `39e9790` | slim output-style の tool call 破損を抑止 |
| `c58ffba` | slim で JSON 文字列値のエスケープ破損を防止 |
| `58c775a` | slim で tool call/構造化出力を壊す圧縮を抑制 |
| `a169e5a` | slim の call 破損を境界原則の言い換えで封じる |

原因は一貫している。「簡潔に」「体言止め」という指示はモデルの出力**全体**にかかり、ツール引数・JSON 文字列値・コードといった**一字一句が意味を持つ領域**まで圧縮対象に含めてしまう。対策として本文へ「コード・コマンド・識別子・構造化出力は原文のまま」という境界原則を書き足す方針を繰り返したが、境界の言語化は網羅できず、`a10f387` では本文を 60 行から 8 行へ削って副作用を減らす方向に転じていた。トークン削減が目的の仕組みが、破損の抑制のために機能を削られ続けている状態だった。

同じ判断は既に一度下されている。自動 Bash 出力圧縮フック（旧 `redux_filter`）は「非可逆な行折りたたみがソースコードを構文的に破壊する correctness hazard」としてハーネス監査の推奨チェックから撤去済みで、その理由は `harness_audit_repo_checks.py` の `_repo_context_compact_checks` docstring に記録されていた。入力側の事後圧縮で結論が出ていたものが、出力側では未適用のまま残っていた。

## 決定

**LLM 応答の事後圧縮を目的とする仕組みを持たない。** 具体的には次を規約とする。

1. **output-style による応答圧縮を提供しない** — `output-styles/slim.md` とディレクトリを削除し、`plugin.json` の `outputStyles` 登録を外す。bluecore は output-style を配布しない
2. **ハーネス監査 rubric からも撤去する** — 他リポジトリへ同パターンを推奨しない。`context-strategic-compact`（3点）と `cost-skill`（4点）を削除し、repo モード満点は 65 → 58、チェック数は 24 → 22 になる。採点基準が変わるため `rubric_version` も `2026-08-26` へ上げる
3. **トークン削減は出力の「量」ではなく「経路」で行う** — 既に採っている手段を正とする。`list` / `search` が `- [kind] title (key)` の 1 行だけを返し `body` は `show` でのみ返す設計、0 件なら 1 文字も出力しない設計（CLAUDE.md「出力トークンの最小化が設計原則」）。これらは**何を返すかの選択**であり、生成済みテキストへの非可逆変換ではない
4. **応答スタイルの指定はユーザーの領分とする** — スタイルを強制したい利用者は `settings.json` の `outputStyle` で自分の選択を置く。プラグインが `force-for-plugin` で上書きしない

## 検討した代替案

### 代替案 1: 境界原則の追記を続ける（6 回目の修正）

`a169e5a` までと同じく、破損したケースを本文の除外リストへ追加していく。

- 長所: 変更が小さい。トークン削減の効果を維持できる
- 短所: 境界の言語化は網羅できない。5 回の修正で本文は 60 行 → 8 行まで痩せており、次の追記は再び本文を膨らませる。膨らんだ本文は毎セッションのシステムプロンプトに載るので、削減したトークンを本文自身が食う
- 却下理由: **5 回の試行が経験的な反証になっている。** 「どこを圧縮してはいけないか」を事前に列挙しきる前提そのものが成り立たない — ツール引数の形式は呼び出すツールごとに違い、将来のツールは定義に存在しない

### 代替案 2: rubric チェックだけ残す

`slim.md` は削除するが、`context-strategic-compact` / `cost-skill` は他リポジトリ向けの推奨として残す。

- 長所: 満点とテストのアサーションを変えずに済む
- 短所: 自リポジトリの audit が永久に fail する。さらに悪いことに、bluecore 自身が correctness hazard と判断して捨てたパターンを、他リポジトリへ 7 点分のスコアで推奨し続ける
- 却下理由: `redux_filter` 撤去と同一の論理がそのまま適用される。**自分が捨てたものを他人に勧めない**

### 代替案 3: Copilot CLI 向けにプロンプト注入を復活させる

output-style 非対応ホストのために `pre_user_prompt.py` 相当を再実装する。

- 長所: ホスト間でスタイルが揃う
- 短所: 破損の原因は注入経路ではなく圧縮指示そのものなので、ホストを増やせば破損の再現箇所が増える。毎プロンプトの注入は SessionStart 一回の注入よりトークンを食う
- 却下理由: **決定の前提が逆。** 廃止するパターンに新しい配送経路を足す理由がない。なお現行 HEAD に注入経路は既に存在せず（`hooks.json` に UserPromptSubmit エントリなし、`SlimSettings` の残骸なし）、Copilot CLI は移行後 slim を一度も受け取っていない

## 結果

### 肯定的

- ツール呼び出し・JSON・コード出力の破損源が 1 つ消える。同種の修正コミットが 6 回目を迎えない
- システムプロンプトから slim 本文と毎ターンの reminder が消え、入力トークンが減る（削減目的の仕組みが入力側で払っていたコストの解消）
- ハーネス監査が自リポジトリで永久 fail する状態を解消し、他リポジトリへの誤った推奨を止める
- `redux_filter`（入力側）と slim（出力側）で判断が揃い、「非可逆な事後圧縮を持たない」が一貫した規約になる

### 否定的

- 応答が長くなり出力トークンが増える。定量値は測っていない（測るには同一タスクの A/B が要る）
- 日本語応答・結論先行を望む利用者は、自分の `settings.json` で `outputStyle` を設定する必要がある。プラグイン導入だけでは揃わない
- repo モード満点が 7 点下がるため、過去に採取した audit スコアと単純比較できない

### リスク

- **スコアの断絶**: 外部に保存された過去の baseline JSON（`max_score: 65`）と混在すると改善幅を誤読する。判別のため `rubric_version` を `2026-03-30` → `2026-08-26` へ上げた（`commands/harness.md` の版表記と満点表記も追従済み）。版が異なる baseline 同士は満点が違うため、スコアの差ではなく達成率で比較すること
- **再発**: 「トークン削減」を目的に同じパターンが再提案されうる。本 ADR がその再提案に対する既定の回答になる（代替案 1〜3 が主要な再提案の形）
