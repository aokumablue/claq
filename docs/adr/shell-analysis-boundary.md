# シェルコマンド解析の境界 — 誤検出を誤通過より選ぶ

保護フックはシェルコマンド文字列を静的に解析して判定する。完全な意味解釈は原理的に不可能なので、
どこで倒すか・どこを非目標とするかを決める。

## 共通原則

保護フック群は「うっかり事故の抑止」であり「敵対的回避への防壁」ではない。トークナイザベースの
判定は解析できない構文に対して必ずどちらかに倒れるため、倒し方を経路ごとに場当たりで決めず、
方向を 1 つに固定する — **誤検出（安全側に厳しく倒す）を誤通過（見逃す）より選ぶ。**

| 不確定なもの | 扱い |
|---|---|
| 構文（エイリアス・変数展開・多段 `sh -c`・`eval`） | 非目標。検出しない |
| 構文だが環境非依存に確定できる（heredoc の本文範囲） | 確定できる場合だけ除去し、できなければ検出側 |
| 実行時状態（`cd` 後の cwd） | 判定を放棄して無条件 deny |
| 入力の読み方（シェル方言） | 両方で読み、どちらかが検出したら deny |
| 実行位置（wrapper を何語読み飛ばすか） | 名前集合が原理的に不可避。allowlist を採る |
| 内容の種別（バイナリかテキストか） | 検査を止める根拠にしない |

「誤検出を選ぶ」は無制限ではない。`\` を含むコマンドを一律 deny するような、誤検出の量が使えない
水準になる案はこの原則の射程外であり採らない。

`_command_name` による正規化（basename 化 + 小文字化 + `.exe` 除去）は実行コマンド判定だけに適用
する専用の 1 関数に集約する。wrapper 読み飛ばしと `cd` 判定に同じ正規化を適用しないと、
`CD ..; rm ruff.toml` が `cd` 節の無条件 deny 分岐へ落ちず誤通過する。

## git commit / シェル保護フックの検出境界は誤検出を誤通過より選ぶ

`block_no_verify`（`git commit --no-verify` の検出）・`bash_config_protection`（Bash 経由の設定
ファイル直接書き換え検出）・`pre_bash_commit_quality`（`git commit` の検出）は、いずれも POSIX
シェルコマンド文字列をトークン化して判定する。POSIX シェルの完全な構文解釈は原理的に不可能に近い
（`$(...)`・変数展開・エイリアス・多段 `sh -c`・`eval` が無限に組み合わさる）ため、完全な AST
パーサは導入しない。解析できない構文・判定が割れるケースは、常に誤検出を誤通過より選ぶ。ただし
「解析できない構文そのものへの対応」は非目標として明記し、無理に対応範囲を広げない。

- `block_no_verify` / `bash_config_protection` の非目標: シェルエイリアス・シェル関数・変数展開・
  コマンド置換・2 段以上の `sh -c` / `eval`・`git` 以外の名前を持つラッパースクリプト経由の呼び
  出し。これらは検出しない（見逃しを許容する）
- `pre_bash_commit_quality` の `echo "git commit"` のような誤検出は「安全側」として維持する。
  誤って quality scan を実行するコストは、commit を見逃すコストより小さい
- 書き込み先が引数位置に明示されるコマンド群（`cp` / `mv` / `install` / `ln -f` / `dd of=` /
  `perl -i`、リダイレクト演算子 `&>` / `>|` 等）は「解析できる」範囲なので対応する。
  `python -c "open('x','w').write(...)"` や `eval` 経由の間接書き込みは非目標のまま

解析できない構文を一律 deny にはしない。両フックは Bash という最も広い matcher に登録されており、
一律 deny にすると `git commit` や設定ファイル書き込みと無関係な大多数の Bash 呼び出し
（`$(date)` を含むログ出力等）まで巻き込み、可用性が壊れる。

本フック群を「敵対的な回避を防ぐセキュリティ境界」だと誤認して運用すると、`python -c` / `eval` /
任意スクリプト経由の間接書き込み、2 段以上の `sh -c`・変数展開経由の `--no-verify` 回避は検出
されない、という非対応経路が実害になりうる。モジュール docstring に「非目標」として明記し続ける。

## バイナリ判定で secret 検査を止めない

バイナリ判定は lint チェックの抑制にのみ用い、secret 検査の実施可否には用いない。NUL バイトを
先頭に置くだけで secret 検査を止められるなら回避コストが極端に低く、「画像等のバイナリ commit を
一律ブロックしない」という要件がある以上、バイナリを一律 deny にもしない。拡張子 / MIME /
allowlist で真のバイナリだけを skip する方式も、拡張子の付け替えで同じコストのまま回避できるため
採らない。

バイナリ判定された内容に対しては、行分割の代わりに `strings(1)` と同じ発想で NUL を含む制御文字
区切りの 4 文字以上の連続を抽出し、通常と同じ secret パターンを適用する。抽出文字列は実際の行に
対応しないため、行番号は報告せず「in extracted binary content」と表示する。真のバイナリは secret
パターンに一致する印字可能文字列を通常含まない。

印字可能文字列を偶然含む真のバイナリが secret パターンに一致すると誤検出で commit がブロック
されるが、誤検出優先に従いこの方向の誤りは許容する。すべて印字可能文字で構成された独自バイナリは
そもそもバイナリ判定されず、通常のテキスト経路で走査される。

## heredoc のデータ本文はコマンド列として解析しない

保護フック 3 種は `shlex` でコマンド文字列をトークン化して判定するが、`shlex` は heredoc を解釈
せず本文行も通常のトークンとして返る。その結果、本文に書いた散文が実行命令として読まれ、フックの
禁止事項を名指しする説明文書自体が書けなくなる。一方で `bash <<'EOF'` / `cat <<'EOF' | bash` では
本文が実際に実行され、本文を一律に除去すると誤通過になる。heredoc の本文範囲は演算子・区切り語・
終端行だけで決まる環境非依存の構文であり、エイリアス・変数展開・PATH のような環境依存の意味解釈を
含まないため、これは誤検出優先の例外ではなく適用範囲の明確化である。

heredoc の**データ**本文は、本文がデータだと**静的に確定できる場合だけ**トークン化の前段で除去
する。確定できなければ除去せず検出側へ倒す。除去しない条件は次の 4 つ:

1. 演算子行に**本文を実行するトークン**がある。`sh` / `bash` / `zsh` / `dash` に加えて、渡された
   テキストを現在のシェルで実行するビルトイン（`.` / `source` / `eval`）を含む。判定軸は「本文が
   実行されうるか」であって「実行ファイルか」ではない
2. 演算子行が継続演算子（`\` / `|` / `&`）で終わる — 本文の開始位置が次行とは限らない
3. 終端行が見つからない（未終端）
4. `<<` がそもそも heredoc 演算子ではない（コメント内・クォート内・`\` エスケープ後）。この場合
   heredoc は開始せず、後続行は実行されるコマンドなので、本文として剥がすと保護フックが素通り
   する。判定は演算子の走査が持つクォート／コメント状態で行い、状態は非本文行だけを鎖にして更新
   する（本文行・終端行はシェルの語彙ではないため）

正規化は `tokenize` 内部ではなく `hook_common` の専用関数 1 箇所に集約し、4 フック全体で同じ挙動
にする。データ消費コマンドの allowlist（`cat` / `tee` / `jq` のときだけ剥がす）は集合が無限に
広がり列挙漏れで誤通過が戻るため採らない。

非シェルインタプリタ（`python3 - <<EOF` 等）の本文が間接的にシェルを起動する形は検出できない。
これは `python -c` 経由の間接実行を非目標としたのと同じ境界である。終端行の後続に空白がある場合
（`EOF `）は POSIX どおり終端しない。`cat <<'EOF' |` で改行し次行が `bash` という形は「継続演算子
で終わる行は残す」規則で守っており、これを冗長と見て単純化しないこと。ネストした heredoc で走査が
同期ずれを起こすと静かな誤通過になるため、条件 4 のクォート状態は非本文行だけを鎖にして更新する。

## `cd` を含むコマンドでは repo スコープ判定を信用せず deny する

`bash_config_protection` は保護対象ファイルへの書き込み先が現在のリポジトリ配下にある場合だけ
deny する。この判定は書き込み先トークンを `Path.cwd()` 基準で解決するが、`cd` は同じコマンド
文字列の中で cwd を動かすため、フックが実行前に静的解析する時点では `cd` 以降の相対パスと実行時
の位置がずれる。`cd plugins && printf 'x' > ../ruff.toml` は実行時の書き込み先がリポジトリ直下の
`ruff.toml` でも、cwd 基準で解決するとリポジトリ外と誤判定されて素通りする。

**コマンドが `cd` / `pushd` / `popd` / `chdir` を含む場合、repo スコープ判定を適用せず、保護対象
basename のヒットをそのまま deny する。** `cd` を追跡して解決基準点を更新する案は、サブシェル・
パイプライン内の `cd`・`cd -`・変数展開を含む `cd "$D"` を正しく扱うにはシェルのスコープ規則の
模倣が要り、かつ現在 deny しているケースを allow へ緩める方向の変更を含むため採らない。誤通過を
新たに作りうる緩和を、模倣の正確さに依存する実装で導入することはしない。`cd` を跨いだ symlink
解決のずれも同じ理由で非目標とする。

リポジトリ外のディレクトリへ `cd` してから保護対象と同じ basename のファイルを書く操作は誤って
deny される。回避は `cd` を別の Bash 呼び出しへ分けるか、basename を変えることであり、いずれも
保護フックの無効化を伴わない。

## シェル保護フックは 1 つのコマンド文字列を 2 つのシェル方言で解析する

`block_no_verify` と `bash_config_protection` は `shlex(posix=True)` でトークン化するが、Windows
ホストのシェルツールは PowerShell であり、`\` はエスケープ記号ではなくただのパス区切りとして働く。
同じ文字列が方言によって別のトークン列になる（`rm .\.eslintrc` は POSIX 読みで `..eslintrc` の
削除、Windows では `.eslintrc` の削除）。hook の入力にシェル種別は載っておらず、`tool_name` は
ホスト実装依存で実行シェルの方言を確定できないため、実行シェルを推定して方言を選ぶ方式は採らない
——推定を外したときの失敗が保護の無効化になる。

**保護フックは、コマンド文字列を「POSIX 読み」と「Windows 読み」の 2 通りで解析し、どちらかが
検出したら deny する。**

- Windows 読みは `\` の直後の文字で 3 通りに分ける: パス構成文字なら `/` へ置換
  （`.\ruff.toml` → `./ruff.toml`）、空白/タブなら `\` を除去（エスケープを持たないシェルでは
  2 引数になり 2 番目が実際に書き込み対象になる）、`/` なら変換しない（`\/` は sed 等の POSIX
  エスケープで Windows のパス区切りには現れない）
- Windows 読みが元と同じになるコマンドは追加の解析をしない
- 変換関数は 1 箇所だけに置き、フックが共有する
- 実行位置のコマンド名比較は basename 化 + 小文字化 + `.exe` 除去へ統一し、PowerShell / cmd の
  書き込み語彙（`Remove-Item` / `Clear-Content` / `Set-Content` / `Add-Content` / `Out-File` /
  `New-Item` / `Copy-Item` / `Move-Item` および `del` / `erase` / `rd` / `copy` / `move` / `ri` /
  `mi` / `clc` / `cpi` / `sc` / `ac` / `ni`）を加える
- `pre_bash_commit_quality` も同じ方言展開で `git commit` を探す。POSIX 読み 1 本のままだと
  `C:\Git\bin\git.exe commit -m x` が `block_no_verify` では検出されるのに品質ゲートだけ素通り
  する

実行中の OS を見て挙動を変えるのではなく、入力を常に 2 通り読む。macOS/Linux でも同じコード
パスが走り、テストもそこで両方の読み方を踏める。`\` を含むコマンドを一律 deny する案、
`shlex(posix=False)` を併用する案はいずれも採らない——前者は POSIX の日常的な `\` 使用
（エスケープ・行継続）まで拒否して実用にならず、後者はクォートをトークンに残すため独自の
クォート剥がしという 3 つ目の方言が増える。

POSIX では誤検出だが Windows では真陽性のケース（`rm my\ ruff.toml`）は検出側へ倒す。残る誤検出
（例 `rm a\.eslintrc`）は誤検出優先が受容する側。Linux では `RM` が `rm` に一致する誤検出側へ
倒れるが、これも誤検出優先の範囲内。Windows 実機での検証は、方言変換自体が macOS のテストで
両側を踏める設計に依存している。

## 実行位置の特定は wrapper allowlist で行い、git 起動の探索は全トークン走査のままにする

Bash 系の保護フック 2 つは、コマンド文字列のどこを見るかで正反対の方針を採る。この非対称は
意図的なものであり、統一しない——両フックは必要としている判定が違う。

`block_no_verify` はトークンの basename が `git` なら git 起動とみなす全トークン走査を使う。
セグメント先頭を前提にすると `sudo git commit --no-verify` / `xargs -I% git ...` が素通りする。
`block_no_verify` が要るのは「このコマンドで git が起動されるか」だけで、git が何番目の語かは
結論に影響しないため、名前集合を持たないほうが強い。

`bash_config_protection` は `env` / `sudo` / `timeout` / `nice` / `nohup` / `stdbuf` / `xargs` 等
を読み飛ばす wrapper allowlist（`_COMMAND_POSITION_WRAPPERS`）を使い、「実際に実行される
executable の index」を求める。`tee pyproject.toml`（deny）と `echo tee pyproject.toml`（allow）
は構文上まったく同じ「語 → 語 → パス」であり、分けるのは `echo` と `timeout` の意味論であって
構文ではないため、実行位置の特定そのものが必要になる。選べるのは「wrapper を列挙する」か
「データを取るコマンドを列挙して残り全部を wrapper とみなす」かの 2 択で、後者は `pushd` /
`cd` を wrapper として誤って消費し `cd` 節の無条件 deny 分岐を壊すため、前者（allowlist）を採る。
allowlist の唯一の一般化として、wrapper を 1 つ以上通過した後に限り、数字で始まる非オプション語を
wrapper 自身の positional 値として読み飛ばす（`timeout 5 rm` の `5`。実行ファイル名が数字で始まる
ことはまず無いため）。

`block_no_verify` の全トークン走査を `bash_config_protection` へ転用しない——実行位置の情報が
そもそも生まれず、非実行位置での言及が deny になる。逆に `bash_config_protection` の allowlist を
`block_no_verify` 側へ揃えない——取りこぼしのコストが非対称で、`block_no_verify` の取りこぼしは
`sudo git commit --no-verify` の素通りであり実行位置を必要としない側へ名前集合を導入しても得る
ものが無い。

`_COMMAND_POSITION_WRAPPERS` に載っていない wrapper は取りこぼす。これは承知のうえの境界であり、
numeric positional の消費だけが唯一の一般化である。allowlist の要素が静かに減っても集合リテラル
1 statement なのでカバレッジでは検出できないため、期待値との完全一致と全要素の deny 実測で固定
する。
