# 書いたものの陳腐化と、実測できないものの扱い

定義文書やコードへ書いた列挙・版・固定値は、外部世界が動くと黙って古くなる。失敗が「例外」では
なく「素通り」として現れるため、検知器を置かない限り緑のまま腐る。

| ADR | 決定 | 日付 | ステータス |
|---|---|---|---|
| [ADR-0016](#adr-0016-足場タグ-denylist-の陳腐化は実コーパス走査で検知するfail-open-の診断) | denylist の陳腐化は実コーパス走査で検知する（fail open の診断、CI には入れない） | 2026-08-29 | accepted |
| [ADR-0022](#adr-0022-外部の版付き標準を定義へ列挙するときは版を見出しへ書く) | 外部の版付き標準は版を見出しへ書く。版を書けないものは列挙せず名前で参照する | 2026-09-06 | accepted |
| [ADR-0023](#adr-0023-定義へ書く固定値は陳腐化の検知器があるかで残す--外す) | 固定値は「版かどうか」ではなく「陳腐化の検知器があるか」で残す / 外す | 2026-09-07 | accepted |

## 共通原則

**陳腐化の検知は fail open の診断であって、注入経路上のフィルタではない。** 取りこぼしは「発見が
遅れる」だけで新たな注入経路を作らないのに対し、誤検知は毎回赤いゲートを生み、赤が常態化したゲートは
読まれなくなる。したがって**疑わしきは報告しない側へ倒す**。同じ「未知タグ」という材料を扱いながら
[ADR-0015](04-untrusted-input-prompt-boundary.md)（fail closed）と向きが逆なのは、経路上の位置が違う
ためである。

**常に走らないものを CI ゲートに見せかけると、ゲートの信頼そのものが下がる。** ADR-0016 代替案 3
（コーパスは各利用者のローカルにしかない）と ADR-0022 代替案 2 / ADR-0023 代替案 3（外部ソース取得は
ネットワーク依存で `CLAUDE.md` の依存ゼロ原則に反する）は、同じ形で棄却されている。「skip される
ゲートはゲートとして機能しない」（[ADR-0014](07-verification-scope-release-gates.md)）の別の顔である。

**運用注意に委ねる案は、実績が反証している。** ADR-0016 代替案 1（denylist の更新を運用注意に委ねる）
と ADR-0022 代替案 4（定期メンテの運用注意に委ねる）はどちらも、実際に見逃した記録があるという理由で
棄却された。

**規約であって強制ではない。** 「版を書く」も「検知器があるか」も、破っても何も落ちない。この限界は
ADR-0022 と ADR-0023 が同じ言葉で受容している。

**実測できないものは、直さずに残存として明記する** — [ADR-0024 決定 4 / 代替案 4・7](01-hook-failure-direction.md)。
未検証の編集は「その環境で保護が黙って無効」という最悪の失敗へ倒れうるため、文書化された残存のほうが安全。
この却下は「直さない」ではなく「実測できる者が直す」である。

## ADR-0016: 足場タグ denylist の陳腐化は実コーパス走査で検知する（fail open の診断）

**日付**: 2026-08-29  **ステータス**: accepted

### コンテキスト

[ADR-0015](04-untrusted-input-prompt-boundary.md) で採択した handoff の足場除去は、タグ名のハードコード
**denylist**（`lib/harness.py` の `_SCAFFOLD_TAGS`）に依存する。denylist の列挙漏れは例外にならず「素通り」
として現れる。ホストが新しい足場タグを足しても、テストも CI も緑のまま引き継ぎがノイズで埋まる。

これは仮定の話ではない。本リポジトリだけで 2 回実害が出ている。1 回目は初回の足場漏れ（引き継ぎ 3 件が
すべて足場で埋まり実依頼が消えた）、2 回目はマルチエージェント配信足場 `<agent-message from="...">` が
列挙から漏れて中身ごと素通りしていた件である。

列挙漏れは定義上「まだ知らないもの」なので、列挙の完全性を静的に検証することはできない。テストは書けるが、
書けるのは既に知っているタグに対してだけで、漏れは 1 件も見つからない。

### 決定

実 transcript コーパスを走査し、除去処理を通した後にも残る「対を成す未知タグ」を報告する診断
`claq.ci.scan_scaffold_drift` を置く。`maintain` の final gate 項目とし、CI には組み込まない。終了コードは
`0` = ドリフトなし / `1` = 検出 / `2` = 走査対象ゼロ。

判定は次の 3 段で誤検知を落とす。いずれも実コーパス実測で決めた。

| 段 | 内容 | 実測 |
|---|---|---|
| 除去後のテキストを見る | 生テキストだと `<task-notification>` 内側の `<status>` 等が並び真の漏れが埋もれる | 16 種 → 3 種 |
| 対を成すものだけ | 依頼本文の裸プレースホルダ（`<key>` `<path>`）を落とす | 41 種（誤検知 40）→ 1 種（誤検知 0） |
| コードスパンを除く | 依頼本文が引用したコード片・正規表現内のタグを落とす | 3 種（`crm` / `document` / `tag`、全て誤検知）→ 0 種 |

現行コーパス 282 本での実測は**誤検知 0**。`agent-message` を denylist から外して素通りを再現すると**真の
漏れを 1 件検出**する。検知力を保ったまま誤検知が消えている。

### ADR-0015 との向きの違い

ADR-0015（handoff の除去）は **fail closed**。あれは注入経路上のフィルタであり、取りこぼしはそのまま次
セッションのプロンプト汚染になる。だから疑わしきは捨てる。

本 ADR（ドリフト検知）は **fail open**。これは注入経路上に無い診断であり、取りこぼしは「発見が遅れる」だけで
新たな注入経路を作らない。一方で誤検知は毎回赤いゲートを生み、赤が常態化したゲートは読まれなくなる。したがって
疑わしきは報告しない側へ倒す。

同じ「未知タグ」という材料を扱いながら向きが逆なのは、経路上の位置が違うためである。

### 検討した代替案

#### 代替案 1: 検知を置かず、denylist の更新を運用注意に委ねる

- 長所: コードが増えない
- 短所: 2 回とも運用注意では見つからず、実データを見て初めて見つかった
- 却下理由: 実績が反証している

#### 代替案 2: denylist をやめて allowlist にする

- 長所: 陳腐化の失敗が「素通り」から「過剰除去」へ反転し、静かに壊れなくなる
- 短所: ユーザーが依頼本文に書ける語は無限で、allowlist 側が現実的に閉じない。ADR-0015 代替案 4 で棄却した
  「正当な依頼を壊す」と同じ代償を、より広い範囲で払う
- 却下理由: denylist の陳腐化コストより allowlist の誤除去コストが大きい

#### 代替案 3: 検知を pytest / CI に入れる

- 長所: 自動で回る
- 短所: コーパスは各利用者のローカルにしか無く、未サニタイズかつユーザー固有でコミットできない。CI では常に
  `2` になり、`0` と区別されないまま形骸化する
- 却下理由: 常に走らないものを CI ゲートに見せかけると、ゲートの信頼そのものが下がる

#### 代替案 4: 誤検知が出たら `BENIGN_TAGS` に語を足して緑にする

- 長所: 運用が単純
- 短所: 実際の残存 3 種のうち `document` は**ホスト足場としてもあり得る語**だった。緑にするために足すと、将来
  その名前で本当に漏れたとき黙って握り潰す
- 却下理由: 検知器を緑にする操作が検知力を削る形になっている。`BENIGN_TAGS` は良性 HTML タグに限り、それ以外は
  原因側（コードスパン除去など）を直す

### 結果

**肯定的** — denylist の陳腐化が、実データに基づいて発見可能になった。手掛かりゼロだった箇所に観測点が付いた。
誤検知 0 なので、`1` が出たら実際に見る価値がある信号になっている。

**否定的**

- `BENIGN_TAGS` という第 2 の列挙が増えた。陳腐化すると誤検知 1 件として現れ、語を 1 つ足せば解消する。denylist の
  陳腐化（無言の素通り）と保守量は同じで、失敗の向きだけが反転している。これは意図した設計判断である
- コードスパン除去により、コードフェンス内で本当に漏れた足場は見えない。ホスト足場はメッセージ直下に生で載るもので
  あり、利用者が打ったフェンスの内側には現れないため現実の取りこぼしは想定していないが、原理上の穴として残る

**リスク**

- コーパスは走査時点の直近 50 本（既定）。古い host の足場は窓から落ちる
- タグ語彙による検知は**タグを持たない足場**を原理的に見ない。ADR-0015 が記録した構造的な天井は本 ADR でも
  解消していない（[04-untrusted-input-prompt-boundary.md](04-untrusted-input-prompt-boundary.md) の共通原則）

## ADR-0022: 外部の版付き標準を定義へ列挙するときは版を見出しへ書く

**日付**: 2026-09-06  **ステータス**: accepted

### コンテキスト

[ADR-0011 代替案 5](05-definition-and-subagent-design.md) は「汎用知識の列挙を削る」を棄却し、
`security-auditor` の OWASP Top 10・`code-refiner` のアルゴリズム改善表・`tdd-writer` のエッジケース列挙を
**網羅性の担保**として意図的に残すと決めた。この判断自体は今も正しい。

しかし「残す」と決めたことで、**残したものが古くなる経路**が開いたまま塞がれていなかった。2026-09-06 の定義
レビューで実害が 2 件見つかった。

1. `agents/security-auditor.md` の OWASP Top 10 が**2017 版**のまま 2 版取り残されていた。現行 2025 版で新設・
   再編された **A03 Software Supply Chain Failures** / **A06 Insecure Design** / **A10 Mishandling of
   Exceptional Conditions** が丸ごと欠落し、逆に廃止済みの XXE・Insecure Deserialization がトップレベルに
   残っていた。とりわけ A10（例外・タイムアウト・上限超過での fail open）は、
   [ADR-0001](01-hook-failure-direction.md) がこのリポジトリ自身の設計として採択した支配的パターンそのもので
   あり、`security-auditor` は同じファイルの「## プロンプト・エージェント境界」節で fail-open 検査を**手作りして
   いた** — 分類として与えられていれば手作りは要らなかった
2. `skills/skill-make/references/schemas.md` の `executor_model` が旧世代の `claude-sonnet-4-20250514` のまま
   だった。benchmark fixture の雛形なので生成物へ伝播する

どちらも既存の検査を素通りする。`tests/test_md_references.py` は `.md` 参照の切れを検出するが、**外部世界の事実が
古くなったこと**は検出できない。ADR-0011 決定 6 の「定義に書いた検証規則は CI で実測する」も、実測できるのは
リポジトリ内で閉じた規則だけである。ADR-0016 が denylist の陳腐化について解いた問題と同型だが、あちらはローカルの
実コーパスと突合できたのに対し、こちらは外部の版と突合するしかない。

さらに、この 2026-09-06 のレビューは **ADR-0011 代替案 5 とまったく同じ「OWASP 列挙の削除」を再提案した**。
ADR-0011 はその再提案を防ぐために代替案を記録したのに、防げていない。理由は単純で、`security-auditor.md` の
OWASP 節から ADR-0011 への参照が無く、`docs/` は配布物に含まれないため、定義だけを読む者には棄却の事実が届かない
からである。

### 決定

1. **外部の版付き標準を列挙するときは、版を見出しへ含める** — `## OWASP Top 10:2025` のように書く。版が見出しに
   あれば `git diff` にもレビューの目にも入り、「いつのものか」を読み手が判断できる。無版の `## OWASP Top 10` は
   「常に最新」を騙る
2. **版を書けないもの・書きたくないものは列挙せず、名前で参照する** — 網羅性の担保が要らないなら列挙しない。要る
   なら版を背負う。どちらでもない中間（無版の列挙）を置かない
3. **CI ゲートにはしない** — 外部ソースの取得はネットワーク依存であり、`CLAUDE.md` の「ランタイム依存はゼロ」に
   反する。加えて ADR-0016 代替案 3 と同型で、オフライン CI では常に skip され `0` と区別されないまま形骸化する。
   検知は `/maintain` の web トレンド入力（既定 ON・失敗時は「トレンド入力なし」と明記して続行）と、`/review` の
   観点「md の節見出しに含まれる年号・版を現行と突き合わせる」に載せる
4. **ADR で意図的に残すと決めた節には、定義側から ADR への 1 行参照を置く** — これは
   [ADR-0011 決定 4](05-definition-and-subagent-design.md) の適用であって新しい決定ではない。適用漏れが実際に
   再提案を招いたので明記する

### 検討した代替案

#### 代替案 1: 列挙をやめ、標準の名前だけを参照する（`OWASP Top 10 を全項目確認する`）

- 長所: 陳腐化しない。トークンも減る。モデルは OWASP Top 10 を名前で知っている
- 短所: 版を指定しない参照は、モデルの学習時点の版へ黙って落ちる。陳腐化が「見えるところ」から「見えないところ」へ
  移動するだけで、悪化している
- 却下理由: ADR-0011 代替案 5 が同じ提案を「網羅性の担保が落ちる」として棄却済み。本 ADR はその決定を覆さない
  （**この提案はさらに ADR-0023 で 3 回目が来た**）

#### 代替案 2: CI で外部ソースを取得し、列挙との差分を検知する

- 長所: 自動で回る。人手の突合が要らない
- 短所: ネットワーク依存。依存ゼロ原則に反し、オフライン CI では常に skip される。外部サイトの構造変更で壊れる保守
  負債も増える
- 却下理由: ADR-0016 代替案 3 と同じ形 — 常に走らないものを CI ゲートに見せかけると、ゲートの信頼そのものが下がる

#### 代替案 3: 版はコメントや本文の末尾に書き、見出しは無版のままにする

- 長所: 見出しが安定する。既存の節参照（`「## OWASP Top 10」`）を壊さない
- 短所: 本文末尾の年号は diff の文脈行に埋もれ、レビューの目に入らない。今回の 2017 版も「2017」と書いてすらいな
  かったが、仮に末尾にあっても 2 版分見逃されていた可能性が高い
- 却下理由: 見えないところに書いた版は、書いていないのとほぼ同じ。なお本リポジトリの節参照
  （`test_md_references.py` の `_iter_section_refs`）が OWASP 節を指している箇所は無いため、見出し変更のコストは
  実際には発生しない

#### 代替案 4: 何もせず、定期メンテの運用注意に委ねる

- 長所: 変更が要らない
- 短所: ADR-0011（2026-08-25）で「意図的に残す」と決めてから 2026-09-06 まで、`/maintain` も `/review` も 2017 版で
  あることを検出していない。運用注意は既に失敗している
- 却下理由: ADR-0016 代替案 1 と同じく、実績が反証している

### 結果

**肯定的**

- 陳腐化が `git diff` とレビューの目に入る位置へ出た。無言の劣化から、見える劣化になった
- OWASP 2025 の A10（Mishandling of Exceptional Conditions）が分類として入ったことで、`security-auditor` の
  fail-open 検査が手作りの独自節ではなく標準分類に乗った。[ADR-0001](01-hook-failure-direction.md) が採択した
  このリポジトリ自身の fail-open 設計を監査する語彙が揃った
- `skills/secure/SKILL.md` にサプライチェーン（ビルド系・配布経路）と異常系の観点が入り、`security-auditor` と
  `secure` のカバレッジが揃った
- ADR-0011 代替案 5 への 1 行参照が定義側に付き、次のレビューが同じ削除を再提案する経路が 1 つ塞がった

**否定的**

- 版を上げるたびに見出しが変わる。節参照を持つ節では参照側の追従が要る
- 「版を書く」は規約であって強制ではない。無版の列挙を新たに書いても何も落ちない

**リスク**

- 検知経路が `/maintain` の web トレンド入力と `/review` の人手観点だけであり、どちらも ADR-0016 と同じく
  **fail open の診断**である。見逃しは「発見が遅れる」として現れる。これは意図した設計判断で、注入経路上のフィルタ
  ではないため fail closed にはしない
- 版を持たない外部知識（言語慣行・フレームワーク作法）はこの規約の射程外で、陳腐化を検出する手段が引き続き無い

> **ADR-0023 による補足**: 決定 3 が指定した 2 つの検知経路のうち、`/review` 側は accepted 時点から未実装だった。
> 版を残す判断の前提だった二重検知が単一に縮退していたことになる。ADR-0023 決定 4 で解消した。

## ADR-0023: 定義へ書く固定値は「陳腐化の検知器があるか」で残す / 外す

**日付**: 2026-09-07  **ステータス**: accepted

### コンテキスト

2026-09-07 に「skill / commands / agents のバージョン指定など、バージョン変更等でメンテが必要となる記載は廃止し、
常に最新をエージェントが自動で判断するようにせよ。ただし品質低下を招く削減はしないこと」という依頼で全 43 ファイル
（6,307 行）をレビューした。

この依頼の前半は **ADR-0022 代替案 1** と同一で、そこでは「版を指定しない参照はモデルの学習時点の版へ黙って落ちる。
陳腐化が見えるところから見えないところへ移動するだけで悪化している」として棄却済みである。ADR-0011 代替案 5 を
含めると同じ提案の 3 回目にあたる。

一方で依頼の後半（品質低下を招く削減はしない）を最上位の制約として読むと、**依頼は ADR-0022 と矛盾しない**。
ADR-0022 が実際に守っているのは「版を書くこと」ではなく「陳腐化が見える位置にあること」であり、依頼が消したいのは
「書いてあること自体がメンテ負債になる固定値」である。両者が指す集合は重ならない。

しかし ADR-0022 はこの区別を明文化していない。決定 1 の対象は「外部の版付き標準」とだけ書かれており、次の 3 種が
同じ規則の下にあるのか区別できない。

1. 外部の版付き標準（`OWASP Top 10:2025`、MCP プロトコル `2026-07-28`）
2. 内部成果物の版（`rubric_version`、`max_score`）
3. 実測の採取条件（`mcp==2.1.1` / Python 3.14）

実際にレビューで見つかった実害は、この 3 種のどれでもない**4 種目 — 検知器を持たない固定値**に集中していた。

- `skills/skill-make/references/schemas.md` の `"executor_model": "claude-sonnet-5"` — 2 行下の
  `"analyzer_model": "most-capable-model"` は役割記述子なのに、同じ JSON の中で片方だけモデル ID が固定されていた。
  コードからもテストからも参照されない
- `skills/mcp-gen/references/sdk-api-evidence.md` の ★ 数 3 件 — 論旨は「星の多さは最新仕様を意味しない」であり、
  正確な数値は結論に一切効かない
- `skills/maintain/SKILL.md` の「provider 側の全 checks（現在 22 件）」 — 実測値と一致していたが、`rubric_version` と
  違い照合テストが無い
- `commands/harness.md` の「`max_score`（`repo` では 58）」 — `agents/harness-tuner.md` の JSON 例だけが照合されて
  おり、散文側は素通りしていた

同時に、ADR-0022 決定 3 が検知経路として指定した 2 つのうち **`/review` 側が実装されていなかった**（`/maintain`
側のみ存在）。版を残す判断の前提だった二重検知が、accepted 時点から単一に縮退していた。

### 決定

1. **固定値は「陳腐化の検知器があるか」で残す / 外すを決める。** 版であるかどうかでは決めない。検知器とは次の
   いずれかを指す:
   - CI の機械照合（`test_md_rubric_version_matches_audit_constant`、本 ADR で追加した
     `test_md_max_score_mentions_match_real_audit`）
   - 定義本文に書かれた自己検査（`mcp-gen/SKILL.md` の `LATEST_PROTOCOL_VERSION` 比較）
   - ADR-0022 決定 3 の運用検知（`/maintain` の web トレンド入力と `/review` の観点）
2. **検知器を持たない固定値は外す。** 外せない（フィールドとして必須である）なら、
   `analyzer_model: "most-capable-model"` のような**役割記述子**へ置き換える。役割は陳腐化しない
3. **実測の採取条件は「固定値」ではなく出典として扱い、常に残す。** ただし採取日を伴わせる — 採取日の無い
   「PyPI 最新」は、再採取の要否を判断できない
4. **ADR-0022 決定 3 の 2 経路は、両方が実在して初めて成立する。** 片方だけの実装を accepted と扱わない。
   `commands/review.md` へ観点を追加して本 ADR で解消した

### 検討した代替案

#### 代替案 1: 依頼どおり、版表記を一律に外す

- 長所: 依頼の文面に最も忠実。メンテ対象が単調に減る
- 短所: `OWASP Top 10:2025` を無版に戻すと、2026-09-06 に直したばかりの 2017 版取り残し（A03/A06/A10 の欠落）が
  再発する経路へ戻る。MCP の `2026-07-28` を外すと、スキルが存在する理由そのもの（学習データの旧仕様で書き始めると
  import が通ってサーバも起動するため誤りに気づけない）が失われる
- 却下理由: ADR-0022 代替案 1 が同じ提案を棄却済みであり、本 ADR はその決定を覆さない。加えて依頼自身が「品質低下を
  招く削減はしない」と上限を置いており、この削減はその上限に抵触する。**依頼に反しているのではなく、依頼の制約節に
  従った結果である。**

#### 代替案 2: 検知器の有無ではなく「外部 / 内部」で切る

- 長所: ADR-0022 の文面（外部の版付き標準）をそのまま拡張できる
- 短所: `rubric_version` は内部の版だが CI 照合があり残すべきで、`executor_model` は外部の事実だが検知器が無く外す
  べきである。境界が実害と一致しない
- 却下理由: 分類の軸が、直したい失敗モード（黙って古くなる）と直交していない

#### 代替案 3: 検知器の無い固定値にはすべて CI 照合を足す

- 長所: 何も削らずに済む
- 短所: ★ 数や「PyPI 最新」を CI で照合するにはネットワークが要る。ADR-0022 代替案 2 が同じ形を棄却済み
- 却下理由: 照合できるもの（`max_score`）には実際に足した。足せないものに足す手段が無い以上、残りは外すしかない

#### 代替案 4: `tdd-writer` にも信頼境界節を足す

Write を外した 3 定義（`comparator` / `grader` / `bench-analyzer`）が信頼境界を宣言する一方、Bash/Edit/Write を持つ
側は 1 件も宣言していなかった。この非対称は実在し、`reviewer` / `planner` / `code-refiner` には本 ADR のコミット列で
節を追加した。

- 長所: 4 定義すべてで対称になる
- 短所: `tdd-writer` は characterization で **production コードを一時的に mutate して赤くなることを確認する**ことを
  要求しており、判断が読んだテキストではなく実行結果に接地している。加えて弱体化は下流の `reviewer` のテスト改ざん
  ガードが決定的に検出する
- 却下理由: 採否の基準を「不信な材料を読むか」ではなく「**その材料から導いた判断が、ツール権限を超えた不可逆な効果を
  生むか**」に置いた。`code-refiner` の `clean` はコメントの『未使用』主張を削除根拠にしうるので該当し、`tdd-writer` は
  該当しない。fresh subagent 間の重複は [ADR-0011](05-definition-and-subagent-design.md) が原理的に消せないと認めて
  いるが、**当てはまらない定義にまで複製するのは、依頼が削れと言っている冗長そのもの**である

#### 代替案 5: `/review` ステップ 4 の自律実行を `--apply` フラグ制にする

レビュー指摘は不信なレビュー対象ファイル本文の読解から導出されるのに、人間ゲート無しで write-capable な `loop-dev` の
`task` になる。`/harness` は同じ位置で `--apply` の明示を要求しており非対称である。

- 長所: `/harness` と境界が揃う。注入された指摘がそのまま修正として実行される経路が塞がる
- 短所: `/review` ステップ 4 は「これは承認待ちではなくスコープ制限」と明文で設計されており、フラグ化はコマンドの中心
  的な設計変更にあたる。`/harness` が守っているのはハーネス設定（`hooks.json` / `settings.json`）で、blast radius が違う
- 却下理由: 依頼はレビューと定義の是正であって仕様変更ではない。代わりに信頼境界の明示（指摘テキストは不信データ由来で
  あり、実挙動の裏付けなしに `task` へ載せない）だけを採った。フラグ化が要るとの判断は利用者の領域に属する

#### 代替案 6: `html-gen` の外部リソース取得に SRI / ハッシュ検証を要求する

- 長所: OWASP 2025 A03 の観点として正しい形
- 短所: shadcn のカラーレジストリはハッシュを公開しておらず、要求しても満たす手段が無い
- 却下理由: 実行不能な勧告は、書いても守られないまま「対応済み」の見かけだけを作る

#### 代替案 7: `harness-tuner.md` / `skill-tune/SKILL.md` の逐語重複を単一情報源へ寄せる

- 長所: 片方だけ更新されたときのずれが消える
- 短所: 消費者が異なる。`agents/*.md` は会話履歴も親の注入も持たない fresh subagent が読み、`SKILL.md` は本体
  セッションへ載る。参照へ落とすと subagent 側は届かない
- 却下理由: [ADR-0011](05-definition-and-subagent-design.md)「否定的」節が同種の重複を「サブエージェントはコンテキストを
  共有しないため原理的に消せない」として既に受容済み。同じ判断を繰り返す

#### 代替案 8: テンプレート探索のフォールバックを `claq_plugin_root` 経由へ寄せる

`mcp-gen` / `html-gen` が `$HOME/.claude/plugins/cache` をホスト固定パスとして直書きしており、
`test_md_surfaces_have_no_vendor_specific_paths` は他ベンダのパスだけ禁じて自ベンダを許す非対称になっている。

- 長所: [ADR-0008](03-plugin-root-resolution.md) と揃う
- 短所: `env.sh` は POSIX 専用（`CLAUDE.md` 明記）で、Windows では現在の `find` より**悪化**する
- 却下理由: 第一経路は「スキル起動時に提示されるベースディレクトリ」でホスト非依存であり、問題はフォールバックが黙って
  0 件になることだけだった。ホスト固有である旨を明記して「見つからなければベースディレクトリの提示が必須」と書くことで、
  黙った失敗を解消した

### 結果

**肯定的**

- 依頼と ADR-0022 の見かけ上の衝突が、**制約節を最上位に置くことで矛盾なく解消**した。版表記を守りつつ、依頼が指して
  いた実害（検知器の無い固定値 4 件）を全件外せた
- ADR-0022 決定 3 の未実装だった半分（`/review` の観点）が塞がった。この観点は本レビュー自身が 1 件の実害を検出している
  — `agents/code-refiner.md` の Core Web Vitals / Lighthouse が無版のまま、退役した TTI を含み INP を欠いていた
  （OWASP 2017 と同型）
- `max_score` に全 md 走査の照合が入り、「片方だけ照合していたため散文が素通りしていた」という `_RUBRIC_VERSION_SITES`
  のコメントが記録していた事故形が塞がった
- 信頼境界の非対称（Write を外した側だけが宣言し、持っている側は無宣言）が、実際に該当する 3 定義に限って解消された

**否定的**

- 「検知器があるか」は規約であって強制ではない。検知器の無い固定値を新たに書いても何も落ちない。ADR-0022 の同じ限界を
  引き継ぐ
- 役割記述子への置き換え（`executor_model`）は、具体 ID より読み手の解釈幅が広い。fixture を手で作る人が「どのモデルを
  書けばよいか」を別途判断する必要がある

**リスク**

- 代替案 4 の判定基準（判断が不可逆な効果を生むか）は本 ADR で新設したもので、実測の裏付けがない。`tdd-writer` 経由の
  注入が実際に起きたら、判定基準ごと見直す
- `secure` を `user-invocable: true` にしたため `/` 補完へ露出した。ユーザーが `/review` の代わりに `/secure` を呼ぶ誤用が
  増える可能性がある。description の除外条件で誘導しているが、実測は無い
