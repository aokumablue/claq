# 信頼できない入力とプロンプト境界

transcript・hook payload・エージェントが処理した外部文字列は信頼できない入力であり、注入先は
次セッションのプロンプト境界である。ここへ何を通し、何を捨てるか。

## 共通原則

**注入経路上のフィルタは fail closed に倒す。** 「残す」側に倒した誤りは次セッションの判断を
汚染するのに対し、「捨てる」側に倒した誤りは引き継ぎ 1 件の欠落で済む。注入経路上に**無い**
診断（陳腐化検知など）はこの逆——取りこぼしが新たな注入経路を作らない診断は fail open へ倒す。
両者は同じ材料を扱っていても、経路上の位置が違うため向きが逆になる。

**必要十分な範囲は「authority の剥奪」であって「機能の停止」ではない。** 実害が確認された経路
（payload だけで正規承認を偽装できる）を塞ぐことと、正規の人間承認経路そのものを潰すことは別で
ある。後者は「機能を壊すことで脅威を消す」過剰対応になる。

**同一 UID からの直接改竄は防げない。** データストアを直接更新できる以上、CLI をいくら固めても
保証にはならない。したがってコードと文書は「人間承認のみ」という保証を主張せず、境界の代わりに
事後追跡（監査ログ）を置く。

**タグ語彙に依存する防御は、タグを持たない足場を原理的に見ない。** 実測で確認されたもの:
`IMPORTANT: You are running in non-interactive --print mode…`、`Base directory for this skill:`、
`Another Claude session sent a message while you were working:`。denylist / allowlist / drift
検知のいずれでも捕まらない構造的な天井である。

## 知識カードの active 化権限は payload から剥奪するが、`promote` と既存 active カードは維持する

`mem learn` の呼び出し元が JSON payload に `source: "human"` / `status: "active"` と書く、または
`--status active` を指定するだけで、真正性検証なしに `status='active'` の知識カードを作成でき、
SessionStart context への永続注入を自己承認できてしまう。

**payload/CLI から `source`/`status` の authority を剥奪する。`promote` の無効化と既存 active
カードの一括隔離は採らない。** `promote` は正規の人間承認経路であり、これを無効化すると agent
由来の知識を人間がレビューして有効化するワークフロー全体が機能しなくなる。既存の `active` カード
を一括で落とすと、蓄積済みの有用な知識が次回以降のセッションへ注入されなくなる。実害に対して
必要十分な範囲は「payload/CLI からの authority を剥奪すること」であり、それ以上は脅威モデルの
外側の対応である。

- `parse_knowledge_payload()` は常に `source="agent"` / `status="pending"` を書き込み、payload が
  それ以外の値を明示した場合はエラーにする
- `learn` サブコマンドは `--status` オプションそのものを拒否する。`list`/`search` の絞り込み用
  `--status` は維持する
- `claq_mem_learn` は常に `source=agent` / `status=pending` で登録する
- 昇格は `mem promote <key>`（人間が実行するコマンド）である。これは運用上の想定であり、技術的
  強制ではない。コードと文書は「人間承認のみ」という保証を主張しない
- 昇格時に key / scope / source / 直前 status / uid を監査ログへ記録する。これは境界ではなく
  事後追跡である

`promote` 自体は引き続き agent が実行可能な CLI コマンドであり、「人間が意図して昇格コマンドを
叩いた」ことを技術的に強制する手段は無い。将来、host-native な承認 capability が実証された場合、
`promote` をその capability 必須の経路へ差し替える余地を残し、現状の実装はこの将来変更を妨げない
形（単純な status 更新のラッパー）のままにする。payload 経由で active 化されたカードが既存データ
に紛れている可能性は残り、遡及検知は行わない。

## handoff の足場タグ除去は孤立タグを細工とみなす fail closed とする

SessionEnd の handoff は transcript の user エントリから「直近のユーザー依頼」を抽出し、
SessionStart で次セッションのプロンプトへ注入する。user エントリにはユーザーの発話だけでなく、
ハーネスが生成した足場（コマンド出力・タスク通知・システム注記・エージェントメッセージ、および
スラッシュコマンド起動の名前・メッセージ・引数）も同じ形で載る。足場で埋まった引き継ぎは実依頼を
消し、注意書きに含まれる「これらのメッセージに応答するな」的な文言が疑似ユーザー指示として
再注入される。

足場ブロックの中身は攻撃者が影響しうる（コマンド出力・サブエージェント通知）ため、中身に閉じ
タグや開始タグを混ぜてブロックを早期終端させれば、細工した文字列を「依頼」として残せる。信頼
境界マーカーの偽装対策とは目的が逆で、こちらは中身を捨てるのが正しい。

**ペア除去後に片側だけの足場タグが残ったら、そのメッセージを丸ごと破棄する（fail closed）。**
残骸を依頼として救わない。加えて、ブロック除去の中身は「同種の開始タグを含まない文字列」に限定
し、タグ名の直後に名前の終わりを要求する。`command-*` タグはこの規則の対象外とし、
`/name args` へ畳んで元の位置へ差し込む——中身はユーザー自身がタイプしたスラッシュコマンドであり、
攻撃者が影響しうる文字列は足場ブロックの内側にあってブロックごと破棄されるため安全である。

除去できなかった分の中身を残す fail open は採らない。`<open></close>PAYLOAD</close>` のような
形は非貪欲マッチが空の中身を食い、孤立タグ除去がその閉じタグを消して痕跡も残らないまま
`PAYLOAD` が生き残る。注入先がプロンプト境界である以上、「残す」側に倒した誤りは次セッションの
判断を汚染し、「捨てる」側に倒した誤りは引き継ぎ 1 件の欠落で済む。足場タグの総数に上限を設けて
超過時に破棄する方式も、各パターンへ同種開始タグの否定先読みを入れれば走査コストの問題は消え、
上限だけが「対になった足場ブロックを大量に含む正当な依頼」を誤って落とす結果になるため採らない。
未知タグも含めて `<...>` を一律除去する方式は、ユーザーが依頼本文に書いた不等号（コード片・
比較演算子）や無関係なマークアップまで壊すため採らない。この除去を専用の処理として持たず、
信頼境界マーカーの偽装対策（`strip_tags`）の対象語彙を広げて代用する方式も採らない——
`strip_tags` は中身を残すのが正しい用途（知識カード本文の無害化）であり、足場除去は中身を
捨てるのが正しい用途である。目的の異なる 2 つの規則を 1 つの関数へ寄せると、片方の要件を
変えるともう片方が静かに壊れる。

足場タグ名を角括弧付きで引用した正当な依頼は、孤立開始タグと同じ形になるためメッセージごと
落ちる。攻撃者は足場ブロックの中身へ開始タグを注入することで、自分が制御する文字列を前に置いた
孤立「開始」タグを作れるため、prose 由来か細工由来かを形からは区別できない。足場タグ名は
ハードコードした denylist であり、列挙漏れは「素通り」として現れる。タグ語彙による検知はタグを
持たない足場を原理的に見ない（共通原則）。

## 注入経路の文字は許可リストで残し、互換文字の山括弧は検出専用の NFKC で倒す

知識カード（title・body）・handoff 節・detach 失敗通知・`mem learn` の書き込みは同じ信頼境界を
通る。ここに載る文字列は、制御文字や不可視文字で鍵やタグを分断して `redact` / `strip_tags` を
すり抜け、後段の除去で 1 本に戻って注入される足場にできる。

**禁止する文字を列挙せず、残してよい文字だけを残す。** 禁止リストは、列挙漏れの不可視文字
（C1、双方向制御、ゼロ幅文字、タグ文字 U+E0000–E007F）を素通りさせる。タグ文字は不可視の
ASCII を混ぜられる経路でもある。

- 先に行区切り（CRLF・CR・NEL・LS・PS・VT・FF）を LF 1 つへ揃える。行頭マーカーの判定は LF
  分割だけなので、CR や NEL の後ろの行を見落とさないために必要である。
- 残すのは Unicode 一般カテゴリの L*・M*・N*・P*・S*・Zs と、タブ・LF。結合記号（M*）を残す
  のは、ひらがなの結合濁点・デーヴァナーガリーの母音記号・異体字セレクタ（U+FE0F）を落とさない
  ため。Cf（ZWSP・ZWJ・ZWNJ・bidi・タグ文字・BOM・ソフトハイフン）・Cc・Co・Cn・Cs・Zl・Zp は
  落とす。
- ZWJ も落とす。ZWJ を残すと、鍵を ZWJ で分断して `redact` をすり抜けられる。ZWJ 絵文字は
  ZWJ だけが落ち、構成要素の絵文字は残る（ZWNJ を使う言語の表記も同じく落ちる）。
- 本文の書き換えに NFKC は使わない。全角の括弧・英数字が半角に変わり、表示が変わるため。
- 除去は `normalize_user_message` / `strip_tags` / `redact` より前に置く。後ろに置くと除去が
  再結合した形をどの無害化も見ない。

**読み出し側は `redact` を掛けないため、除去で再結合した鍵だけを伏せる。** 保存済みの行や DB へ
の直接書き込みには、ZWSP で分断された鍵が残りうる。除去と `redact` が可換でなければ（除去後の
本文を `redact` した結果と、`redact` してから除去した結果が違えば）、除去後の本文を `redact`
して返す。除く文字が無い通常の本文は `redact` を走らせず、出力は変わらない。

**handoff 本文の行頭は、注入枠の見出し・カード行と同じに読まれうる形を空白 1 個の字下げへ倒す。**
注入枠は `## 見出し` と `- [kind] タイトル` で組み立てる。handoff は promote を通らないため、
本文がこの 2 つと同じに読まれる行を置けると、承認済みの知識と見分けの付かない節や項目を作れる。
許可リストの後、改行ごとに次の行を字下げする（元の字下げは捨て、空白 1 個にする）。

- 見出し: 字下げの後に `#` が来る行。
- カード行: 字下げの後に `-` `*` `+` のどれかが来て、0 個以上の空白を挟んで `[` が来る行。
- 字下げと、記号の後ろの空白は、許可リストが残す水平空白（半角・タブ・NBSP・U+2000–200A・
  U+3000 など）の任意個を同じに読む。`-` で始まる説明文（`- /plugin`、`-1 は…`）、`**[重要]**`、
  行中の `[x]` は変えない。
- 残余として次は対象にしない。注入枠が使う書式（`##` と `-` `[`）の ASCII 並びを空白で割る形
  だけを倒し、見た目の近さは追わない。
  - 番号付きリスト（`1. [`）、`•` `・`、全角の `＃` `－` `［` ほか NFKC で `#-*+[` になる文字、引用 `>`、
    入れ子の `- - [kind]`。
  - 結合記号（M*）で割った行頭（`́- [kind]`、`-́ [kind]`）。許可リストは結合記号を残し、
    `lstrip` も空白として落とさない。
  - 字下げ 1 個にした行は、CommonMark では依然として見出し・リスト項目として読める。
    本物のカード行との差は先頭の空白 1 個だけである。

**`claq-memory` を互換文字で書いた開き山括弧は `&lt;` にする。** 注入枠を閉じるのは字面どおりの
`</claq-memory>` だけだが、`＜/claq-memory＞` や `<／claq-memory>` を LLM は同等に読みうる。
NFKC で `<` `/` `-` やタグ名になる文字で書かれた `claq-memory` タグ（開き・閉じ）を、NFKC の
検出だけで見つけ、開きの山括弧（ASCII の `<` を含む）を `&lt;` に置換する。検出は 1 文字ずつ
正規化して元の位置へ戻す（NFKC は文字列長を変える）。`claq-memory` でない全角記号
（`＜重要＞`）は変えない。`<` に正規化される文字の集合は固定で持ち、全コードポイントの走査との
一致をテストで保つ。

- 無害化は `strip_tags` の `<` → `&lt;` と同じ形で、文字を消さない。`&` の再エスケープを避ける
  ため、`&` と ASCII の `<` を倒す段の後に置く。
- 埋め草削除で互換文字のタグが組み上がる場合（`＜まあ/claq-memory＞`）は、無害化対象の数え方
  と全倒しの両方に互換文字の山括弧を含め、`<` 相当の文字を 1 つ残らず `&lt;` にする。
- 対象は `claq-memory` だけである。他の境界タグを互換文字で書いた表記は倒さない。
- 許可リストはカテゴリで判定するため、可視性は別の規則で補う。何も表示せず ASCII の間へ挟んで
  タグ名・鍵・行頭マーカーを分断できる文字を、次のとおり落とす。判定は `keep_allowed_chars`
  の 1 箇所に閉じ、`redact` / `strip_tags` より前に効く。
  - 常に落とす: CGJ（U+034F）、ハングル filler（U+115F・U+1160・U+3164・U+FFA0）、クメール固有母音
    （U+17B4・U+17B5）、キタン小字 filler（U+16FE4）、点字空白（U+2800）。
  - 異体字セレクタ（モンゴル文字の U+180B–180D・U+180F、U+FE00–FE0F、U+E0100–E01EF）は、除去後の並びで直前が ASCII（文頭を含む）
    のときだけ落とす。ASCII に付かないものは残す。人名の異体字（IVS。`葛` + U+E0100）と絵文字の
    表示選択子（`❤` + U+FE0F）を壊さないため。keycap（`[0-9#*]` + U+FE0F? + U+20E3）の並びは
    丸ごと残す。
  - 視認できる結合記号（分音記号 U+0301、濁点 U+3099、デーヴァナーガリーの母音記号）は ASCII に
    付いていても残す。NFD で分解したラテン文字を壊さず、分断としても視認できるため範囲外とする。
    残余として、これらの記号で鍵やタグ名を分断した文字列は `redact` / `strip_tags` に一致しない。
  - Unicode の Default_Ignorable_Code_Point のうち Cf でないもの（上記が全て）は、この 2 規則で
    落ちる。Python に同名の判定が無いため、個別の文字をテストで固定する。
- commit スキャンが deny 出力へ載せるファイル本文の抜粋も同じ信頼境界にあるため、`strip_tags` の
  前に `keep_allowed_chars` を掛ける。
- 判定は実行系の `unicodedata` に依存する。実行系の Unicode 表より新しく割り当てられた文字は Cn
  として落ちる。
