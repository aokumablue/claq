# ADR-0015: handoff の足場タグ除去は孤立タグを細工とみなす fail closed とする

**日付**: 2026-08-28  **ステータス**: accepted

## コンテキスト

SessionEnd の handoff は transcript の user エントリから「直近のユーザー依頼」を抽出し、
SessionStart で `<ple4-memory>` として次セッションのプロンプトへ注入する。transcript は
信頼できない入力であり、注入先はプロンプト境界である。

user エントリにはユーザーの発話だけでなく、ハーネスが生成した足場（`local-command-caveat` /
`local-command-stdout` / `local-command-stderr` / `task-notification` / `system-reminder` /
`agent-message`、およびスラッシュコマンド起動の `command-name` / `command-message` /
`command-args`）も同じ形で載る。
実測では、あるセッションの引き継ぎ 3 件がすべて足場で埋まり実依頼が消えたうえ、注意書きに
含まれる `DO NOT respond to these messages` が疑似ユーザー指示として次セッションへ再注入されていた。

足場を除去する必要があるが、除去処理そのものが回避対象になる。足場ブロックの中身は攻撃者が
影響しうる（コマンド出力・サブエージェント通知）ため、中身に閉じタグや開始タグを混ぜて
ブロックを早期終端させれば、細工した文字列を「依頼」として残せる。既存の `mem/tag_stripping.py`
は信頼境界マーカーの偽装対策であり **中身を残すのが正しい**。handoff の足場除去は目的が逆で
**中身を捨てるのが正しい**。

## 決定

ペア除去後に片側だけの足場タグが残ったら、そのメッセージを丸ごと破棄する（fail closed）。
残骸を依頼として救わない。加えて、ブロック除去の中身は「同種の開始タグを含まない文字列」に
限定し、タグ名の直後に名前の終わり（`(?=[\s/>])`）を要求する。

`command-*` タグはこの規則の対象外とし、`/name args` へ畳んで元の位置へ差し込む。

## 検討した代替案

### 代替案 1: fail open（除去できなかった分は中身を残す）

- 長所: 引き継ぎが最大限残る。`tag_stripping` と実装方針が揃う。
- 短所: 実測で回避が成立した。`<open></close>PAYLOAD</close>` は非貪欲マッチが空の中身を食い、
  `PAYLOAD` が孤立閉じタグとともに残る。孤立タグ除去がその閉じタグを消すため痕跡も残らない。
- 却下理由: 注入先がプロンプト境界である以上、「残す」側に倒した誤りは次セッションの判断を
  汚染する。「捨てる」側に倒した誤りは引き継ぎ 1 件の欠落で済む。

### 代替案 2: 足場タグの総数に上限を設け、超過時に破棄する

- 長所: タグ大量入力に対する走査コストと除去回避をまとめて塞げる（ように見えた）。
- 短所: 実際に実装して撤去した。上限の根拠だった `.*?` の O(N·n) 走査は、各パターンへ
  同種開始タグの否定先読みを入れた時点で消えていた。実測（閉じタグを伴わない開始タグ）:

  | 入力 | 単純 `.*?` | 否定先読み |
  |---|---|---|
  | 8,000 個 | 4.70 秒 | 0.0012 秒 |
  | 20,000 個（全パターン合計） | — | 0.0053 秒（線形） |

  除去回避のほうは孤立タグ検出が 1 個でも破棄するため上限に依存しない。根拠を失った上限に
  残るのは「対になった足場ブロックを大量に含む正当な依頼」を丸ごと落とす誤検知だけだった。
- 却下理由: 走査コストは正規表現側で解くべきで、入力量の閾値で代用すると誤検知だけが残る。

### 代替案 3: 除去せず、注入時の `strip_tags` だけで防ぐ

- 長所: 追加コードが要らない。
- 短所: `strip_tags` の対象は信頼境界マーカー 5 種でハーネス足場は含まれない。対象を広げると、
  中身を残すべき用途（知識カード本文の無害化）と中身を捨てるべき用途が同じ関数に同居し、
  片方の要件を変えるともう片方が静かに壊れる。
- 却下理由: 目的の異なる 2 つの規則を 1 つの関数へ寄せる設計上の負債が大きい。

### 代替案 4: 未知タグも含めて `<...>` を一律除去する

- 長所: allowlist の陳腐化を受けない。
- 短所: ユーザーが依頼本文に書いた不等号（コード片・比較演算子）や無関係なマークアップを壊す。
- 却下理由: 正当な依頼を壊す代償が、未知足場タグを取りこぼす代償を上回る。

## 結果

### 肯定的

- 細工された足場ブロックが「直近の依頼」として次セッションへ注入される経路が閉じた。
- 否定先読みにより、ブロック除去が対を成さない開始タグを跨いで貫通し、その間にある実依頼を
  巻き込んで消す挙動もなくなった。走査コストも実測で線形に収まる。
- タグ名の終わりを要求したことで、`<system-reminders>` や `<local-command-stdout-parser>` のように
  名前が足場名で始まるだけの別タグを巻き込む誤検知が消えた。

### 否定的

- 足場タグ名を角括弧付きで引用した正当な依頼（この機能自体の改修依頼が典型）は、孤立開始タグと
  同じ形になるためメッセージごと落ちる。これは受容した代償である。攻撃者は足場ブロックの中身へ
  開始タグを注入することで、自分が制御する文字列を前に置いた孤立「開始」タグを作れるため、
  prose 由来か細工由来かを形からは区別できない。
- `command-*` を対象外にしたため、この経路だけタグを剥がして中身を残す非対称が残る。中身は
  ユーザー自身がタイプしたスラッシュコマンドであり、攻撃者が影響しうる文字列は足場ブロックの
  内側にあってブロックごと破棄されるため、現時点で実証された悪用経路は無い。

### リスク

- 足場タグ名はハードコードした **denylist** であり、列挙漏れは「素通り」として現れる。
  ホストが新しい足場タグを追加すると静かに古び、テストも CI も緑のまま引き継ぎがノイズで
  埋まる状態へ戻りうる。実際 `/search` による実 transcript 273 本の走査で、
  マルチエージェント配信足場 `<agent-message from="...">` が列挙から漏れて中身ごと
  素通りしていることが見つかった（本 ADR 採択と同日に追加）。
- この陳腐化の検知手段として、実 transcript コーパスに対する回帰スキャンで
  「対を成す未知タグ」だけを警告する案がある（同走査での実測は 273 本で誤検知 0 /
  真の漏れ 1 件検出）。本 ADR では採らず、**ADR-0016** で採択した。
- タグ語彙による検知は **タグを持たない足場** を原理的に見ない。実測で確認されたもの:
  `IMPORTANT: You are running in non-interactive --print mode…`、
  `Base directory for this skill:`、`Another Claude session sent a message while you were working:`。
  denylist / allowlist / drift 検知のいずれでも捕まらない構造的な天井である。
