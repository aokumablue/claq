# ADR-0010: サブエージェントは「渡す材料」で分割し、役割名では分割しない

**日付**: 2026-08-25  **ステータス**: accepted

## コンテキスト

サブエージェントは独立したコンテキスト窓・システムプロンプト・ツール権限を持つ別プロセスであり、親の会話履歴を引き継がない。したがって分割しているのは「仕事」ではなく「情報」である。2 体に渡す材料がほぼ同じなら、窓を 2 つ使うのにコンテキストは切れておらず、トークンだけが 2 倍になる。

本リポジトリの `agents/` は 13 定義まで増え、役割名（単純化役・デッドコード削除役・性能改善役・設計役・計画役）で切られていた。その結果、定義本文に「未使用・重複削除は dead-code-cleaner、性能改善は perf-optimizer 担当」のような相互ディスクレーマが三角形状に発生し、モデルが定義文なしでは境界を保持できない状態になっていた。`commands/refactor.md` は同一ファイル群を clean → simplify → perf の 3 コンテキストで読み直し、`skills/loop-dev/SKILL.md` は planner と architect に同じ要件・同じコードベースを渡して並列起動し、結果をマージしていた。

## 決定

サブエージェントの分割は「渡す材料」で判断する。役割名・職能名でしか区別できない分割は行わない。

**分けない**
- 2 体に渡す材料がほぼ同じ
- 役割名・職能名でしか区別できない
- 職務が「束ね」だけで判断を持たない（それは親の仕事）

**分ける**
- 見せない情報がある — `comparator` は出力の出自を渡されない（盲検）。`reviewer` は実装者の思考過程を渡されない
- 道具の制限をかけたい — `security-auditor` は Bash を持たず、read-only がツール権限で技術的に強制される
- 返す形を固定したい — `grader` の判定 JSON 契約（固定するのは**出力の形状**であって、agent 自身がファイルを書くことではない。2026-08-27 に grader / comparator / bench-analyzer から汎用 `Write` を外し、結果は返値で返して呼び出し元が保存する形にしたが、形状契約はそのまま維持される）

**判定時の注意**: 材料の比較は「何を渡されるか」だけでなく「**何を持たされないか**」まで見る。`reviewer` と `security-auditor` は表面上どちらも差分を読むが、reviewer には `test_cmd` と失敗テストシグネチャが渡され Bash で再実行できるのに対し、security-auditor は差分のみで実行手段を持たない。材料は同一ではないため統合しない。

**付随ルール**
- 調べ物は組み込みの Explore / Plan に任せる。自作するのは道具制限か出力形式固定が必要なときだけ
- 新規エージェントに `Task` を与えない（子が子を呼ぶ階層を作らない）
- description には「何をするか」ではなく「**いつ呼ぶか**」（呼ばない条件を含む）を書く
- 材料が同じで観点だけ違うものは `agents/bench-analyzer.md` の `mode` 分岐方式で 1 体にまとめる
- 定義の**中身**に何を書き何を書かないかは [ADR-0011](0011-agent-definitions-state-behavior-not-rationale.md)

本 ADR は `agents/` 配下に置かず `docs/adr/` に置く。`CLAUDE.md` は全階層の全サブエージェントが毎回読むため、エージェント定義を書くときだけ必要な基準をそこへ置くと起動回数だけコストが掛かる。

## 検討した代替案

### 代替案 1: エージェント数を維持し、相互ディスクレーマを増補して境界を明確にする

- 長所: 呼び出し元の書き換えが不要。既存の並列起動による wall-clock 短縮を維持できる
- 短所: 同じ材料を複数コンテキストへ渡す構造は変わらず、トークンの二重払いが残る。境界記述は増え続ける
- 却下理由: ディスクレーマが必要なこと自体が、モデルに保持できない分割であることの証拠

### 代替案 2: 基準を `CLAUDE.md` へ書く

- 長所: 全エージェントが自動で読むため周知が確実
- 短所: 全エージェントが毎回読むコストを払う。エージェント定義を書くとき以外は不要な情報
- 却下理由: 共有を 1 つ増やすと起動数だけ掛け算になる。基準の適用者はハーネスを編集する人間であり、実行中のエージェントではない

### 代替案 3: `reviewer` と `security-auditor` も統合する

- 長所: 同じ差分を 2 回読むコストが消え、二重報告禁止ルールが不要になる
- 短所: `security-auditor` の read-only はツール権限による技術的強制であり、Bash を持つ reviewer へ統合すると散文の約束へ格下げされる。統合後の定義は 187 行となり「一体が見る範囲を 1 つに絞る」に反する
- 却下理由: 材料が同一ではない（上記「判定時の注意」）。ADR-0004 が示した「レビューと検証は同一職務」という判断とも整合する

## 結果

### 肯定的

- エージェント数 13 → 9。相互ディスクレーマの三角形が解消
- `commands/refactor.md` が同一ファイル群を 3 コンテキストで読み直す構造を解消
- `loop-dev` の plan 段が並列 2 起動から単一起動になり、コードベース探索の二重払いが解消
- `Task` を持つエージェントがゼロになり、「子が子を呼ばない」が tools 権限で構造的に保証される
- `perf-optimizer` の「計測駆動（必須）」契約が空文化していた（呼び出し元 3 ファイルが一度も計測データを渡していなかった）ことが判明し、`code-refiner` の perf mode で前提条件として是正された

### 否定的

- `code-refiner` の 3 mode と `planner` の 2 モードは、呼び出し元が依頼文で明示する必要がある。親の手順書に書いた分岐は子へ届かないため、指定漏れは自動判別へフォールバックする（判別不能なら FAIL）
- `simplify` 段の並列起動は同一エージェントの複数インスタンスになり、`reviewer` + `security-auditor` 以外の異種並列が無くなった

### リスク

- `code-refiner` は 3 mode 分の指示を 1 定義に持つため、mode ごとの参照節を冒頭表で明示していても他 mode の記述に引きずられる可能性がある。定義冒頭で「自分のモードの節と共通契約だけを読む」と明示して緩和している
- 統合の実効はトークン占有率で確認する必要がある。`/usage` のサブエージェント別内訳を統合前後で比較する
