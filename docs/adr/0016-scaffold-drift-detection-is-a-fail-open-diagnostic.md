# ADR-0016: 足場タグ denylist の陳腐化は実コーパス走査で検知する（fail open の診断）

**日付**: 2026-08-29  **ステータス**: accepted

## コンテキスト

ADR-0015 で採択した handoff の足場除去は、タグ名のハードコード **denylist**（`lib/harness.py`
の `_SCAFFOLD_TAGS`）に依存する。denylist の列挙漏れは例外にならず「素通り」として現れる。
ホストが新しい足場タグを足しても、テストも CI も緑のまま引き継ぎがノイズで埋まる。

これは仮定の話ではない。本リポジトリだけで 2 回実害が出ている。1 回目は初回の足場漏れ
（引き継ぎ 3 件がすべて足場で埋まり実依頼が消えた）、2 回目はマルチエージェント配信足場
`<agent-message from="...">` が列挙から漏れて中身ごと素通りしていた件である。

列挙漏れは定義上「まだ知らないもの」なので、列挙の完全性を静的に検証することはできない。
テストは書けるが、書けるのは既に知っているタグに対してだけで、漏れは 1 件も見つからない。

## 決定

実 transcript コーパスを走査し、除去処理を通した後にも残る「対を成す未知タグ」を報告する
診断 `ple4.ci.scan_scaffold_drift` を置く。`maintain` の final gate 項目とし、CI には
組み込まない。終了コードは `0` = ドリフトなし / `1` = 検出 / `2` = 走査対象ゼロ。

判定は次の 3 段で誤検知を落とす。いずれも実コーパス実測で決めた。

| 段 | 内容 | 実測 |
|---|---|---|
| 除去後のテキストを見る | 生テキストだと `<task-notification>` 内側の `<status>` 等が並び真の漏れが埋もれる | 16 種 → 3 種 |
| 対を成すものだけ | 依頼本文の裸プレースホルダ（`<key>` `<path>`）を落とす | 41 種（誤検知 40）→ 1 種（誤検知 0） |
| コードスパンを除く | 依頼本文が引用したコード片・正規表現内のタグを落とす | 3 種（`crm` / `document` / `tag`、全て誤検知）→ 0 種 |

現行コーパス 282 本での実測は **誤検知 0**。`agent-message` を denylist から外して素通りを
再現すると **真の漏れを 1 件検出**する。検知力を保ったまま誤検知が消えている。

## ADR-0015 との向きの違い

ADR-0015（handoff の除去）は **fail closed**。あれは注入経路上のフィルタであり、
取りこぼしはそのまま次セッションのプロンプト汚染になる。だから疑わしきは捨てる。

本 ADR（ドリフト検知）は **fail open**。これは注入経路上に無い診断であり、取りこぼしは
「発見が遅れる」だけで新たな注入経路を作らない。一方で誤検知は毎回赤いゲートを生み、
赤が常態化したゲートは読まれなくなる（ADR-0014 の「skip されるゲートはゲートとして
機能しない」の別の顔）。したがって疑わしきは報告しない側へ倒す。

同じ「未知タグ」という材料を扱いながら向きが逆なのは、経路上の位置が違うためである。

## 検討した代替案

### 代替案 1: 検知を置かず、denylist の更新を運用注意に委ねる

- 長所: コードが増えない。
- 短所: 2 回とも運用注意では見つからず、実データを見て初めて見つかった。
- 却下理由: 実績が反証している。

### 代替案 2: denylist をやめて allowlist にする

- 長所: 陳腐化の失敗が「素通り」から「過剰除去」へ反転し、静かに壊れなくなる。
- 短所: ユーザーが依頼本文に書ける語は無限で、allowlist 側が現実的に閉じない。
  ADR-0015 代替案 4 で棄却した「正当な依頼を壊す」と同じ代償を、より広い範囲で払う。
- 却下理由: denylist の陳腐化コストより allowlist の誤除去コストが大きい。

### 代替案 3: 検知を pytest / CI に入れる

- 長所: 自動で回る。
- 短所: コーパスは各利用者のローカルにしか無く、未サニタイズかつユーザー固有でコミット
  できない。CI では常に `2` になり、`0` と区別されないまま形骸化する。
- 却下理由: 常に走らないものを CI ゲートに見せかけると、ゲートの信頼そのものが下がる。

### 代替案 4: 誤検知が出たら `BENIGN_TAGS` に語を足して緑にする

- 長所: 運用が単純。
- 短所: 実際の残存 3 種のうち `document` は**ホスト足場としてもあり得る語**だった。
  緑にするために足すと、将来その名前で本当に漏れたとき黙って握り潰す。
- 却下理由: 検知器を緑にする操作が検知力を削る形になっている。`BENIGN_TAGS` は
  良性 HTML タグに限り、それ以外は原因側（コードスパン除去など）を直す。

## 結果

### 肯定的

- denylist の陳腐化が、実データに基づいて発見可能になった。手掛かりゼロだった箇所に
  観測点が付いた。
- 誤検知 0 なので、`1` が出たら実際に見る価値がある信号になっている。

### 否定的

- `BENIGN_TAGS` という第 2 の列挙が増えた。陳腐化すると誤検知 1 件として現れ、語を 1 つ
  足せば解消する。denylist の陳腐化（無言の素通り）と保守量は同じで、失敗の向きだけが
  反転している。これは意図した設計判断である。
- コードスパン除去により、コードフェンス内で本当に漏れた足場は見えない。ホスト足場は
  メッセージ直下に生で載るものであり、利用者が打ったフェンスの内側には現れないため
  現実の取りこぼしは想定していないが、原理上の穴として残る。

### リスク

- コーパスは走査時点の直近 50 本（既定）。古い host の足場は窓から落ちる。
- タグ語彙による検知は **タグを持たない足場** を原理的に見ない。実測で確認されたもの:
  `IMPORTANT: You are running in non-interactive --print mode…`、
  `Base directory for this skill:`、`Another Claude session sent a message while you were working:`。
  ADR-0015 が記録した構造的な天井は本 ADR でも解消していない。
