# 検証範囲とリリースゲート

何を CI で自動検証し、何をリリースゲートにし、何を人間の実機再検証に委ねるか。および配布物に
何を含めないか。

## 共通原則

**skip されるゲートはゲートとして機能しない。** ホストの CLI が PATH に無い環境ではホスト確認は
実行できず、そこで skip されるだけのゲートは信頼を作らない。したがってホスト依存のゲートには
必ず CLI に依存しない静的ゲートを併置する。常に走らないものを CI ゲートに見せかけないという
判断はこの原則の別の適用である。

**費用対効果の判断は、比較対象が正しかったときにだけ引き継げる。** 「install/update フロー全体の
エミュレーション」を却下した判断は、「すでにあるツリーを読ませて登録結果を 1 回問い合わせる
だけ」の低コスト案には引き継げない。前提が違えば結論は引き継げない。

**配布物の最小化は「散文の警告」では守れない。** 配布ツリーで回帰そっくりの失敗が出る経路は、
構造的に発生しない形へ直すまで終わらない。

## CI は静的 validator を維持し、install/update フロー全体のエミュレーションは対象外とする

**CI は `hooks.json` の構造的な健全性を静的 validator で検証し続ける。** 実際のプラグイン
install/update フローや、各ホストの hook 登録機構への実登録をエミュレートする smoke test は、
自動検証の対象に含めない。これは実機での動作確認そのものを不要とする決定ではない。ホストの
component inventory 取得は別途リリースゲートにする（後述）。Claude Code 以外のホストについては、
実機再検証を人間が随時実施する。

各ホストの install/update を CI でエミュレートする smoke test を実装する案は、各ホストの
インストール機構を CI 環境で再現する必要があり各ホストの更新に追従し続ける保守コストが継続的に
発生し、ホストの内部実装に CI が依存することになり壊れやすいため採らない。手動チェックリストで
リリースごとに実施を義務付ける案は、実施漏れが起きやすく実施したかどうかを機械的に検証できない
ため採らない。

`hooks.json` の宣言漏れ（イベント未登録・`timeout` 未設定）は機械的に検出され続け、ホストの
内部実装変更に CI が追従する必要が無い。ただし静的 validator だけでは、宣言が構造的に正しくても
ホストへの登録・起動が正しい保証は無い——その欠落は後述の inventory ゲートが埋める。Copilot
CLI / Grok 固有の実行環境差は静的 validator では検出できず、実機再検証の頻度は人間の判断に
委ねる。

## 配布 artifact にテストを同梱せず、検証は source tree で行う

インストール処理は配布対象サブセット（`agents/` / `commands/` / `hooks/` / `runtime/` /
`skills/` / `src/`）だけを配置し、開発用アーティファクトを持ち出さない。配布物を最小化する
ことでインストールサイズと攻撃面を絞り、テスト・開発ツールという「ランタイムに不要な依存」を
利用者の環境へ持ち込まない。

配布ツリーへ開発用の `pyproject.toml` をそのまま持ち出すと、テスト設定が除去済みの `tests/` を
指したまま残り、配布ツリーで `pytest` を叩くと回帰そっくりの派手な失敗が出る。ランタイム依存は
ゼロで、`launcher.py` が `sys.path` へ `src/` を挿すだけであり、ホストが読むのは
`.claude-plugin/plugin.json` である。配布スクリプトの除外リストへ開発用 `pyproject.toml` を含め、
この出力が構造的に発生しないようにする。除外リストの定義はテストが機械的に固定する。

**配布 artifact（各ホストへインストールされる plugin tree）に `tests/` を同梱しない。回帰検知・
カバレッジ検証は、常に開発用 source tree（このリポジトリ自身）で実施する。** `pyproject.toml`
も配布しない。回帰検知の実測は常に source tree で取る。件数と statements 数は書かない——書けば
陳腐化し、次の監査が「数値と合わない」を欠陥として報告する材料になる。

配布 artifact にも `tests/` を同梱する案は、配布サイズが増え利用者の環境に開発専用ファイルを
持ち込み、ランタイムが venv も install.sh も持たないという設計原則とも整合しないため採らない。
installed tree でも動く軽量スモークテストを別途同梱する案は、別のテストスイートを二重管理する
新たな保守コストが発生し source tree のテストとの乖離リスクを抱えるため採らない。いずれも実機
での動作確認は人間が随時実施する運用で足りる。

installed tree だけを見て pytest を実行すると「テストが無い」ように見える。実機再検証を行う
担当者がこの設計判断を知らずに installed tree で pytest を実行すると誤検出を報告しうるが、
散文の警告では止まらないため、`pyproject.toml` を配布しないことで失敗そのものを構造的に消す。

## ホスト component inventory をリリースゲートにする

静的 validator も公式の strict validate も PASS するのに、ランタイムの loader が manifest の
`agents` エントリを directory として扱うため全件未登録になる、という非互換がありうる。壊れて
いることを示す信号は、すでにあるツリーを読ませて登録結果を 1 回問い合わせることで得られる。
インストール機構の再現もハッシュ付きディレクトリの模倣も要らない。

**ホストの component inventory 取得をリリースゲートに含める。** 具体的には次を満たすことを
リリース条件とする。

1. ホストの strict validate がプラグインに対して PASS する
2. ホストへ plugin detail を問い合わせた出力に、実ディレクトリと一致する Skills / Agents 数が
   現れる
3. debug log にプラグインコンポーネント読み取り失敗のエラーが 0 件である

**CLI に依存しない静的ゲートも併置する。** ホストの CLI が PATH に無い環境ではホスト確認は実行
できず、skip されるゲートはゲートとして機能しない。そのため、manifest が `agents` を宣言して
いないこと（＝ auto-discovery に委ねていること）と、ディスク上にエージェント定義が実在すること
を静的テストで常時検証する。

静的 validator だけを維持し登録結果の問い合わせをゲートにしない案は、component 群がまるごと
未登録になる種類の実害を静的検証では原理的に検出できない（manifest も公式 schema も validator
も、すべて「正しい」と答える）ため採らない。全ホスト（Claude Code / Copilot CLI / Grok）の
inventory を必須にする案は、他ホストの CLI をリリース環境へ常時用意する必要がありインストール
フローのエミュレーションで却下した保守コストがそのまま復活するため採らない。第一対象である
Claude Code だけを必須にすれば実害の大半を捕まえられ、他ホストは人間の実機再検証に委ねる。

ホストの更新で plugin detail の出力形式が変わると、ゲート側の追従が要る。ゲート実装は出力
文字列と集計規則に結合しており、ホスト側がどちらを変えても実体は正常なのに不一致としてリリース
を止めることがある。誤メッセージにはホストの実出力を併記し原因を追えるようにする。Copilot CLI
と Grok の登録は自動検証されない。inventory は「登録されたか」を見るだけで「登録されたものが
正しく動くか」は見ず、定義本文の欠陥は別の検証（validator・実機再検証）の担当である。
