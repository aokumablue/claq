# 定義文書とサブエージェントの設計

`agents/` / `skills/` / `commands/` に何を何体置き、その中身に何を書き何を書かないか。および
プラグインが「配布しないもの」の境界。

## 共通原則

**サブエージェントは自身のシステムプロンプトがコンテキストのほぼ全量である。** 1 行の無駄も
1 行の誤りも起動のたびに払う。したがって分割の粒度と定義の中身は同じコスト構造に支配されている。

**サブエージェントが起動時に受け取るのは 6 種だけ**: 自身のシステムプロンプト＋環境情報 / 親が
書いた依頼文 / 全階層の `CLAUDE.md` / 親セッション開始時点の git status / `skills` で preload
した本文 / sibling roster。**会話履歴と親の auto memory は含まれない。** サブエージェント起動時に
発火する hook イベントも無い。

**コンテキストを共有しないため、定義間の重複は原理的に消せない。** 複数 md にまたがる逐語重複を
参照へ落とすと、fresh subagent 側にはその参照先が届かない。

**非可逆な事後圧縮を持たない。** 入力側でも出力側でも結論は同じ。トークン削減は「生成済み
テキストの圧縮」ではなく「何を返すかの選択」で行う。

## reviewer agent は write-capable Bash を保持する

`security-auditor` は frontmatter の `tools` から Bash を外し、Read/Grep/Glob のみで完結する。
`reviewer` は `tools: Read, Grep, Glob, Bash` を維持しており、Bash を経由して任意の書き込みが
理論上可能な状態が残る。`ruff check` の実行と、呼び出し元から渡された `test_cmd` の再実行
（RED→GREEN 遷移の独立検証）はレビューの職務そのものであり、これらを実行するには Bash が要る。

**reviewer エージェントの `tools` から Bash を外さない。** 技術的な書き込み禁止の強制は行わず、
散文制約（read-only の職務境界を明記し、逸脱時はレビューを継続せず報告して停止する）を維持する。
security-auditor（チェックリストが Read/Grep/Glob のみで完結する）とは職務の性質が異なるため、
同じ強制を適用しない。

validator runner とレビュー agent を分割する案、`ruff check` / `test_cmd` の再実行を呼び出し元へ
移して reviewer には結果だけ渡す案は、いずれも Bash を持つ主体が存在するという根本的なリスクを
消さないか、渡された結果が本当にそのコマンドの実行結果かを reviewer が検証できなくなり自己申告を
信頼する経路を復活させるため採らない。検証の独立性が reviewer の核心的な価値である。

reviewer の散文制約は技術的強制ではないため、プロンプトインジェクション等でこの制約が無視された
場合、reviewer が実際に任意の書き込みを行う経路は理論上残る。この残存リスクは受容する。

## サブエージェントは「渡す材料」で分割し、役割名では分割しない

サブエージェントは独立したコンテキスト窓・システムプロンプト・ツール権限を持つ別プロセスであり、
親の会話履歴を引き継がない。したがって分割しているのは「仕事」ではなく「情報」である。2 体に渡す
材料がほぼ同じなら、窓を 2 つ使うのにコンテキストは切れておらず、トークンだけが 2 倍になる。
役割名（単純化役・デッドコード削除役・性能改善役・設計役・計画役）で切ると、定義本文に相互
ディスクレーマが三角形状に発生し、モデルが定義文なしでは境界を保持できない——ディスクレーマが
必要なこと自体が、モデルに保持できない分割であることの証拠である。

**サブエージェントの分割は「渡す材料」で判断する。役割名・職能名でしか区別できない分割は行わない。**

分けない: 2 体に渡す材料がほぼ同じ場合。役割名・職能名でしか区別できない場合。職務が「束ね」だけ
で判断を持たない場合（それは親の仕事）。

分ける: 見せない情報がある場合（`comparator` は出力の出自を渡されない盲検、`reviewer` は実装者の
思考過程を渡されない）。道具の制限をかけたい場合（`security-auditor` は Bash を持たず read-only
がツール権限で技術的に強制される）。返す形を固定したい場合（固定するのは出力の形状であって、
agent 自身がファイルを書くことではない。結果は返値で返して呼び出し元が保存する）。

材料の比較は「何を渡されるか」だけでなく「何を持たされないか」まで見る。`reviewer` と
`security-auditor` は表面上どちらも差分を読むが、reviewer には `test_cmd` と失敗テストの
シグネチャが渡され Bash で再実行できるのに対し、security-auditor は差分のみで実行手段を持たない。
材料は同一ではないため統合しない。

付随ルール:

- 調べ物は組み込みの Explore / Plan に任せる。自作するのは道具制限か出力形式固定が必要なときだけ
- 新規エージェントに `Task` を与えない（子が子を呼ぶ階層を作らない）
- description には「何をするか」ではなく「いつ呼ぶか」（呼ばない条件を含む）を書く
- 材料が同じで観点だけ違うものは `mode` 分岐方式で 1 体にまとめる

この基準は `agents/` 配下の各定義ファイルではなく `docs/adr/` に置く。`CLAUDE.md` は全階層の
全サブエージェントが毎回読むため、エージェント定義を書くときだけ必要な基準をそこへ置くと起動
回数だけコストが掛かる。基準の適用者はハーネスを編集する人間であり、実行中のエージェントでは
ない。エージェント数を維持したまま相互ディスクレーマを増補する対応、`reviewer` と
`security-auditor` を統合する対応は、いずれも上記の分割基準に反するため採らない。

`code-refiner` の複数 mode と `planner` のモードは、呼び出し元が依頼文で明示する必要がある。
親の手順書に書いた分岐は子へ届かないため、指定漏れは自動判別へフォールバックする（判別不能なら
FAIL）。複数 mode 分の指示を 1 定義に持つエージェントは他 mode の記述に引きずられる可能性が
あるため、定義冒頭で「自分のモードの節と共通契約だけを読む」と明示して緩和する。

## エージェント定義には挙動を書き、論拠と再説明は書かない

サブエージェントには SessionStart のメモリ注入が届かない。届かない前提を定義に書くと実現不可能な
指示になる。深刻度・確信度で報告を絞らせる指示は、モデルが literal に従い報告を減らす。自己検証の
再実行指示は品質を上げない。

エージェント定義には**そのエージェントの挙動を変える記述だけ**を置く。

1. **自動注入されるものを前提にしない** — サブエージェントが起動時に受け取るものは共通原則の
   6 種のみ。それ以外（会話履歴・親の注入・過去の検索結果）を前提に書かない。知識 DB を引くのは
   Bash を持つエージェントが自分で検索コマンドを叩く経路だけ。Bash が無いエージェントにはメモリ
   経路が無いので、必要なら呼び出し元が依頼文へ載せる
2. **深刻度・確信度で報告を絞らせない** — 見つけたものはすべて出させ、確信が持てないものに
   「未確認」ラベルを付ける。ノイズ削減は重複統合とスタイル除外で行う。安全性の担保は
   `Blockers: {n}`（CRITICAL+HIGH 件数）という集計の定義側で行い、報告量では行わない
3. **自己検証の再実行は指示しない** — 出力が満たすべき不変条件は契約として書く。「保存後に
   読み直して確かめる」「答えを double-check する」といった再実行手順は書かない。ただし他者の
   成果物の検証（`reviewer` の再実行によるテスト検証）は職務そのものなので対象外
4. **設計判断の論拠は ADR に置く** — 「なぜこの構成を採ったか」はエージェントの挙動を変えない。
   定義には ADR への 1 行参照だけを置く
5. **ツール権限が保証していることを散文で再説明しない** — 「Bash を持たないのでコマンド実行は
   できない」の詳説は不要。必要なのは「提案はテキストで返す」という行動指示だけ
6. **定義に書いた検証規則は CI で実測する** — 正規表現・許可リスト・形状検査など、外部入力を
   シェルやツールへ渡す前の関門を定義本文へ書いたら、その本文からリテラルを抽出して実入力で検査
   するテストを併せて置く

判定行の欠落は「指摘ゼロ」ではない。収束条件や final gate が `Blockers: {n}` 行の実在を前提と
する場合、行が無い（途中終了・出力破損・起動失敗）ときは未収束 / `BLOCKED` として扱う。

汎用知識のチェックリスト（OWASP・アルゴリズム改善表・エッジケース列挙）は網羅性の担保として残す。
削ると観点が落ちる。強調語のスイープ（「必ず」「必須」を平常語へ緩める）、番号付き手順の一般化、
XML タグによる構造化、安いモデルへの一律切り替え、汎用知識の列挙削減、`maxTurns` による強制打ち
切り、`effort` を下げてのコスト削減は、いずれも検討したが採らない——count は診断ではなく、
`Blockers: {n}` のような硬い契約を平常語へ落とすと壊れる。番号付きステップが JSON 出力契約の
フィールドと 1 対 1 対応している定義では一般化すると契約が壊れる。判定行を機械読みする
`reviewer` / `security-auditor` は途中で打ち切られると silent false-green になり、書き込み権限を
持つエージェントでは中断が作業ツリーを不整合のまま残す。エージェントの品質保持力を判定する eval が
無いまま安いモデルやモデル自身の低 effort に賭けることはしない。

決定 2 により MEDIUM/LOW の指摘量は増えうる。`Blockers` 自体は動かないので自動ゲートへの影響は
無いが、レポートが読みにくくなった場合は絞り込み基準の側を強め、深刻度による抑制へは戻さない。
`record: 自分では書かない` のような、複数 md にまたがる指示の逐語重複は Bash を持つ定義に残る
（共通原則が示すとおり、コンテキストを共有しないため原理的に消せない）。

## LLM 応答の事後圧縮パターン（output-style `slim`）を廃止する

「簡潔に」「体言止め」という指示はモデルの出力全体にかかり、ツール引数・JSON 文字列値・コード
といった一字一句が意味を持つ領域まで圧縮対象に含めてしまう。境界原則を書き足しても境界の言語化は
網羅できず、ツール引数の形式は呼び出すツールごとに違い将来のツールは定義に存在しない。非可逆な
行折りたたみはソースコードを構文的に破壊するため、同じ判断は入力側の自動出力圧縮にも当てはまる。

**LLM 応答の事後圧縮を目的とする仕組みを持たない。**

1. output-style による応答圧縮を提供しない（claq は output-style を配布しない）
2. ハーネス監査のスコア基準からもこのパターンを撤去する。他リポジトリへ同パターンを推奨しない
3. トークン削減は出力の「量」ではなく「経路」で行う。一覧表示は要約 1 行だけを返し詳細は個別
   取得でのみ返す設計、0 件なら 1 文字も出力しない設計。これらは何を返すかの選択であり、生成
   済みテキストへの非可逆変換ではない
4. 応答スタイルの指定はユーザーの領分とする。プラグインがホストの `outputStyle` 設定を強制で
   上書きしない

境界原則の追記を続ける方式は、どこを圧縮してはいけないかを事前に列挙しきる前提そのものが成り
立たないため採らない。監査の基準チェックだけを残す方式は、自分が correctness hazard と判断して
捨てたパターンを他リポジトリへスコアで推奨し続けることになるため採らない。他ホスト向けに
プロンプト注入で圧縮を復活させる方式は、破損の原因が注入経路ではなく圧縮指示そのものである以上
ホストを増やせば破損の再現箇所が増えるだけで、廃止するパターンに新しい配送経路を足す理由がない。

応答が長くなり出力トークンは増える。簡潔な応答・結論先行を望む利用者は、自分の設定で応答スタイル
を指定する必要がある。「トークン削減」を目的に同じパターンが再提案されうるが、本節がその再提案に
対する既定の回答である。
