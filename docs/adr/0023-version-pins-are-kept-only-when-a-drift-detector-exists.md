# ADR-0023: 定義へ書く固定値は「陳腐化の検知器があるか」で残す / 外す

**日付**: 2026-09-07  **ステータス**: accepted

## コンテキスト

2026-09-07 に「skill / commands / agents のバージョン指定など、バージョン変更等でメンテが
必要となる記載は廃止し、常に最新をエージェントが自動で判断するようにせよ。ただし品質低下を
招く削減はしないこと」という依頼で全 43 ファイル（6,307 行）をレビューした。

この依頼の前半は **ADR-0022 代替案 1**（「列挙をやめ、標準の名前だけを参照する」）と同一で、
そこでは「版を指定しない参照はモデルの学習時点の版へ黙って落ちる。陳腐化が見えるところから
見えないところへ移動するだけで悪化している」として棄却済みである。ADR-0011 代替案 5 を含め
ると同じ提案の 3 回目にあたる。

一方で依頼の後半（品質低下を招く削減はしない）を最上位の制約として読むと、**依頼は
ADR-0022 と矛盾しない**。ADR-0022 が実際に守っているのは「版を書くこと」ではなく
「陳腐化が見える位置にあること」であり、依頼が消したいのは「書いてあること自体が
メンテ負債になる固定値」である。両者が指す集合は重ならない。

しかし ADR-0022 はこの区別を明文化していない。決定 1 の対象は「外部の版付き標準」とだけ
書かれており、次の 3 種が同じ規則の下にあるのか区別できない。

1. 外部の版付き標準（`OWASP Top 10:2025`、MCP プロトコル `2026-07-28`）
2. 内部成果物の版（`rubric_version`、`max_score`）
3. 実測の採取条件（`mcp==2.1.1` / Python 3.14）

実際にレビューで見つかった実害は、この 3 種のどれでもない **4 種目 — 検知器を持たない固定値**
に集中していた。

- `skills/skill-make/references/schemas.md` の `"executor_model": "claude-sonnet-5"` —
  2 行下の `"analyzer_model": "most-capable-model"` は役割記述子なのに、同じ JSON の中で
  片方だけモデル ID が固定されていた。コードからもテストからも参照されない
- `skills/mcp-gen/references/sdk-api-evidence.md` の ★ 数 3 件 — 論旨は「星の多さは最新
  仕様を意味しない」であり、正確な数値は結論に一切効かない
- `skills/maintain/SKILL.md` の「provider 側の全 checks（現在 22 件）」 — 実測値と一致して
  いたが、`rubric_version` と違い照合テストが無い
- `commands/harness.md` の「`max_score`（`repo` では58）」 — `agents/harness-tuner.md` の
  JSON 例だけが照合されており、散文側は素通りしていた

同時に、ADR-0022 決定 3 が検知経路として指定した 2 つのうち **`/review` 側が実装されて
いなかった**（`/maintain` 側のみ存在）。版を残す判断の前提だった二重検知が、accepted 時点から
単一に縮退していた。

## 決定

1. **固定値は「陳腐化の検知器があるか」で残す / 外すを決める。** 版であるかどうかでは
   決めない。検知器とは次のいずれかを指す:
   - CI の機械照合（`test_md_rubric_version_matches_audit_constant`、
     本 ADR で追加した `test_md_max_score_mentions_match_real_audit`）
   - 定義本文に書かれた自己検査（`mcp-gen/SKILL.md` の `LATEST_PROTOCOL_VERSION` 比較）
   - ADR-0022 決定 3 の運用検知（`/maintain` の web トレンド入力と `/review` の観点）
2. **検知器を持たない固定値は外す。** 外せない（フィールドとして必須である）なら、
   `analyzer_model: "most-capable-model"` のような**役割記述子**へ置き換える。役割は
   陳腐化しない
3. **実測の採取条件は「固定値」ではなく出典として扱い、常に残す。** ただし採取日を伴わせる —
   採取日の無い「PyPI 最新」は、再採取の要否を判断できない
4. **ADR-0022 決定 3 の 2 経路は、両方が実在して初めて成立する。** 片方だけの実装を
   accepted と扱わない。`commands/review.md` へ観点を追加して本 ADR で解消した

## 検討した代替案

### 代替案 1: 依頼どおり、版表記を一律に外す

- 長所: 依頼の文面に最も忠実。メンテ対象が単調に減る。
- 短所: `OWASP Top 10:2025` を無版に戻すと、2026-09-06 に直したばかりの 2017 版取り残し
  （A03/A06/A10 の欠落）が再発する経路へ戻る。MCP の `2026-07-28` を外すと、スキルが
  存在する理由そのもの（学習データの旧仕様で書き始めると import が通ってサーバも起動する
  ため誤りに気づけない）が失われる。
- 却下理由: ADR-0022 代替案 1 が同じ提案を棄却済みであり、本 ADR はその決定を覆さない。
  加えて依頼自身が「品質低下を招く削減はしない」と上限を置いており、この削減はその上限に
  抵触する。**依頼に反しているのではなく、依頼の制約節に従った結果である。**

### 代替案 2: 検知器の有無ではなく「外部 / 内部」で切る

- 長所: ADR-0022 の文面（外部の版付き標準）をそのまま拡張できる。
- 短所: `rubric_version` は内部の版だが CI 照合があり残すべきで、`executor_model` は外部の
  事実だが検知器が無く外すべきである。境界が実害と一致しない。
- 却下理由: 分類の軸が、直したい失敗モード（黙って古くなる）と直交していない。

### 代替案 3: 検知器の無い固定値にはすべて CI 照合を足す

- 長所: 何も削らずに済む。
- 短所: ★ 数や「PyPI 最新」を CI で照合するにはネットワークが要る。ADR-0022 代替案 2 が
  同じ形を「CLAUDE.md の依存ゼロ原則に反し、オフライン CI では常に skip される」として
  棄却済み。
- 却下理由: 照合できるもの（`max_score`）には実際に足した。足せないものに足す手段が無い
  以上、残りは外すしかない。

### 代替案 4: `tdd-writer` にも信頼境界節を足す

Write を外した 3 定義（`comparator` / `grader` / `bench-analyzer`）が信頼境界を宣言する
一方、Bash/Edit/Write を持つ側は 1 件も宣言していなかった。この非対称は実在し、
`reviewer` / `planner` / `code-refiner` には本 ADR のコミット列で節を追加した。

- 長所: 4 定義すべてで対称になる。
- 短所: `tdd-writer` は characterization で **production コードを一時的に mutate して
  赤くなることを確認する**ことを要求しており、判断が読んだテキストではなく実行結果に
  接地している。加えて弱体化は下流の `reviewer` のテスト改ざんガードが決定的に検出する。
- 却下理由: 採否の基準を「不信な材料を読むか」ではなく「**その材料から導いた判断が、
  ツール権限を超えた不可逆な効果を生むか**」に置いた。`code-refiner` の `clean` は
  コメントの『未使用』主張を削除根拠にしうるので該当し、`tdd-writer` は該当しない。
  fresh subagent 間の重複は ADR-0011 が原理的に消せないと認めているが、**当てはまらない
  定義にまで複製するのは、依頼が削れと言っている冗長そのもの**である。

### 代替案 5: `/review` ステップ4 の自律実行を `--apply` フラグ制にする

レビュー指摘は不信なレビュー対象ファイル本文の読解から導出されるのに、人間ゲート無しで
write-capable な `loop-dev` の `task` になる。`/harness` は同じ位置で `--apply` の明示を
要求しており非対称である。

- 長所: `/harness` と境界が揃う。注入された指摘がそのまま修正として実行される経路が塞がる。
- 短所: `/review` ステップ4 は「これは承認待ちではなくスコープ制限」と明文で設計されており、
  フラグ化はコマンドの中心的な設計変更にあたる。`/harness` が守っているのはハーネス設定
  （`hooks.json` / `settings.json`）で、blast radius が違う。
- 却下理由: 依頼はレビューと定義の是正であって仕様変更ではない。代わりに信頼境界の明示
  （指摘テキストは不信データ由来であり、実挙動の裏付けなしに `task` へ載せない）だけを採った。
  フラグ化が要るとの判断は利用者の領域に属する。

### 代替案 6: `html-gen` の外部リソース取得に SRI / ハッシュ検証を要求する

- 長所: OWASP 2025 A03 の観点として正しい形。
- 短所: shadcn のカラーレジストリはハッシュを公開しておらず、要求しても満たす手段が無い。
- 却下理由: 実行不能な勧告は、書いても守られないまま「対応済み」の見かけだけを作る。

### 代替案 7: `harness-tuner.md` / `skill-tune/SKILL.md` の逐語重複を単一情報源へ寄せる

「md クロス参照・description は実装と一致」の 1 行が 2 ファイルへ逐語で重複している。

- 長所: 片方だけ更新されたときのずれが消える。
- 短所: 消費者が異なる。`agents/*.md` は会話履歴も親の注入も持たない fresh subagent が
  読み、`SKILL.md` は本体セッションへ載る。参照へ落とすと subagent 側は届かない。
- 却下理由: ADR-0011「否定的」節が同種の重複を「サブエージェントはコンテキストを共有
  しないため原理的に消せない」として既に受容済み。同じ判断を繰り返す。

### 代替案 8: テンプレート探索のフォールバックを `ple4_plugin_root` 経由へ寄せる

`mcp-gen` / `html-gen` が `$HOME/.claude/plugins/cache` をホスト固定パスとして直書きして
おり、`test_md_surfaces_have_no_vendor_specific_paths` は他ベンダのパスだけ禁じて自ベンダを
許す非対称になっている。

- 長所: ADR-0008（plugin root は `~/.ple4/env.sh` ポインタで解決）と揃う。
- 短所: `env.sh` は POSIX 専用（CLAUDE.md 明記。祖先 PID と `ps -o lstart=` の照合に依存）で、
  Windows では現在の `find` より**悪化**する。
- 却下理由: 第一経路は「スキル起動時に提示されるベースディレクトリ」でホスト非依存であり、
  問題はフォールバックが黙って 0 件になることだけだった。ホスト固有である旨を明記して
  「見つからなければベースディレクトリの提示が必須」と書くことで、黙った失敗を解消した。

## 結果

### 肯定的

- 依頼と ADR-0022 の見かけ上の衝突が、**制約節を最上位に置くことで矛盾なく解消**した。
  版表記を守りつつ、依頼が指していた実害（検知器の無い固定値 4 件）を全件外せた。
- ADR-0022 決定 3 の未実装だった半分（`/review` の観点）が塞がった。この観点は本レビュー
  自身が 1 件の実害を検出している — `agents/code-refiner.md` の Core Web Vitals /
  Lighthouse が無版のまま、退役した TTI を含み INP を欠いていた（OWASP 2017 と同型）。
- `max_score` に全 md 走査の照合が入り、「片方だけ照合していたため散文が素通りしていた」
  という `_RUBRIC_VERSION_SITES` のコメントが記録していた事故形が塞がった。
- 信頼境界の非対称（Write を外した側だけが宣言し、持っている側は無宣言）が、
  実際に該当する 3 定義に限って解消された。

### 否定的

- 「検知器があるか」は規約であって強制ではない。検知器の無い固定値を新たに書いても
  何も落ちない。ADR-0022 の同じ限界を引き継ぐ。
- 役割記述子への置き換え（`executor_model`）は、具体 ID より読み手の解釈幅が広い。
  fixture を手で作る人が「どのモデルを書けばよいか」を別途判断する必要がある。

### リスク

- 代替案 4 の判定基準（判断が不可逆な効果を生むか）は本 ADR で新設したもので、実測の
  裏付けがない。`tdd-writer` 経由の注入が実際に起きたら、判定基準ごと見直す。
- `secure` を `user-invocable: true` にしたため `/` 補完へ露出した。ユーザーが
  `/review` の代わりに `/secure` を呼ぶ誤用が増える可能性がある。description の
  除外条件で誘導しているが、実測は無い。
