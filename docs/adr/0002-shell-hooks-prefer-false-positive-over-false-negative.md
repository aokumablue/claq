# ADR-0002: git commit / シェル保護フックの検出境界は誤検出を誤通過より選ぶ

**日付**: 2026-08-18  **ステータス**: accepted

## コンテキスト

`block_no_verify`（`git commit --no-verify` の検出）・
`bash_config_protection`（Bash 経由の設定ファイル直接書き換え検出）・
`pre_bash_commit_quality`（`git commit` の検出）は、いずれも POSIX シェル
コマンド文字列をトークナイザ（`hook_common.tokenize`/`split_segments`）で
解析して判定する。POSIX シェルの完全な構文解釈は原理的に不可能に近く
（`$(...)`・変数展開・エイリアス・多段 `sh -c`・`eval` 等が無限に組み合わ
さる）、監査は複数ラウンドにわたって同種の検出漏れ・誤検出を指摘してきた:

- A-02（今回）: 書き込み先が引数に明示されない `python -c`/`eval`/任意
  スクリプト経由の間接書き込みは `bash_config_protection` が検出しない。
- A-04（今回）: `block_no_verify` は `sh -c 'sh -c "git commit --no-verify"'`
  や `eval "git commit --no-verify"`、command substitution
  （`$(printf ...)`）を検出しない（レポート自身が「1 段の `sh -c` は
  対応済み・2 段以上は非目標」と記載）。
- 前ラウンド: `block_no_verify` のエイリアス・変数展開・任意ラッパー
  スクリプト経由の呼び出しの非対応。
- 前ラウンド: `pre_bash_commit_quality` の `echo "git commit"` を commit と
  誤検出する挙動（regex フォールバックの副作用として許容済み）。

これらは表面上は別々の指摘に見えるが、根は 1 つ: **トークナイザベースの
判定は解析できない構文に対して必ずどちらかに倒れる**。倒し方を経路ごとに
場当たりで決めると、監査ツールは「なぜここは検出するのにここは検出しない
のか」を次のラウンドでも指摘し続ける。

## 決定

**解析できない構文・判定が割れるケースは、常に「誤検出（false positive =
安全側に厳しく倒す）」を「誤通過（false negative = 見逃す）」より選ぶ。**
ただし「解析できない構文そのものへの対応」は非目標として明記し、無理に
対応範囲を広げない。

適用の内訳:

- `block_no_verify`・`bash_config_protection` の非目標: シェルエイリアス・
  シェル関数・変数展開・コマンド置換・2 段以上の `sh -c`/`eval`・`git` 以外
  の名前を持つラッパースクリプト経由の呼び出し。これらは検出しない
  （false negative を許容する）。
- 一方で `pre_bash_commit_quality` の `echo "git commit"` 誤検出（commit で
  はないのに commit 判定される）は「安全側」として維持する。誤って quality
  scan を実行するコストは、commit を見逃して検査をすり抜けさせるコストより
  小さい。
- A-02 で書き込み先が引数位置に明示されるコマンド群（`cp`/`mv`/`install`/
  `ln -f`/`dd of=`/`perl -i`、リダイレクト演算子 `&>`/`>|` 等）は「解析
  できる」範囲なので今回対応した（`bash_config_protection.py`）。一方
  `python -c "open('x','w').write(...)"` や `eval` 経由の間接書き込みは
  「解析できない」範囲として今回も非目標のまま維持する。

## 検討した代替案

### 代替案 1: 完全な POSIX シェル AST パーサを導入する

- 長所: エイリアス・変数展開・多段ラッパーまで正確に解決できれば
  false negative が大幅に減る。
- 短所: POSIX シェルの完全な意味解釈は実行時の環境（定義済みエイリアス・
  環境変数の値・PATH 上の実行ファイル）に依存し、静的解析だけでは原理的に
  再現できない。実装コストも著しく大きく、依存ゼロ方針（標準ライブラリ
  のみ）とも相容れない。
- 却下理由: 「うっかり事故の抑止」という設計目標に対して過剰投資であり、
  かつ原理的に解けない問題（環境依存の意味解釈）を含む。

### 代替案 2: 解析できない構文はすべて deny（fail-closed）にする

- 長所: 見逃しがゼロになる。
- 短所: `block_no_verify`/`bash_config_protection` は Bash という最も
  広い matcher に登録されているため、解析できない構文を一律 deny すると
  `git commit` や設定ファイル書き込みと無関係な大多数の Bash 呼び出し
  （`$(date)` を含むログ出力等、日常的に使われる構文）まで巻き込み、
  可用性が壊れる。
- 却下理由: ADR-0001 と同じ理由。検査対象が確定できない状況を deny に
  倒すと、通常作業ができなくなる被害の方が大きい。

## 結果

### 肯定的

- 「うっかり事故の抑止であり敵対的回避への防壁ではない」という一貫した
  設計境界が、3 つのフックすべてで同じ言葉で説明できるようになった。
- A-02 の実害部分（`cp`/`mv`/`install`/`ln -f`/`dd of=`/`perl -i`、拡張
  リダイレクト演算子）は「解析できる」範囲として今回修正済み。

### 否定的

- `python -c`/`eval`/任意スクリプト経由の間接書き込み、2 段以上の
  `sh -c`・変数展開経由の `--no-verify` 回避は、今後も検出されない。

### リスク

- 本フック群を「敵対的な回避を防ぐセキュリティ境界」だと誤認して運用する
  と、上記の非対応経路が実害になりうる。`block_no_verify.py`・
  `bash_config_protection.py` のモジュール docstring に「非目標」として
  明記し続けることで誤認を防ぐ。
