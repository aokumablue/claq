# 定義文書とサブエージェントの設計

`agents/` / `skills/` / `commands/` に何を何体置き、その中身に何を書き何を書かないか。および
プラグインが「配布しないもの」の境界。

| ADR | 決定 | 日付 | ステータス |
|---|---|---|---|
| [ADR-0004](#adr-0004-reviewer-agent-は-write-capable-bash-を保持する) | reviewer の `tools` から Bash を外さない。検証の独立性は職務そのもの | 2026-08-18 | accepted |
| [ADR-0010](#adr-0010-サブエージェントは渡す材料で分割し役割名では分割しない) | サブエージェントは「渡す材料」で分割する。役割名でしか区別できない分割は行わない | 2026-08-25 | accepted |
| [ADR-0011](#adr-0011-エージェント定義には挙動を書き論拠と再説明は書かない) | 定義にはそのエージェントの挙動を変える記述だけを置く（6 規約） | 2026-08-25 | accepted |
| [ADR-0012](#adr-0012-llm-応答の事後圧縮パターンoutput-style-slimを廃止する) | LLM 応答の事後圧縮を目的とする仕組みを持たない | 2026-08-26 | accepted |

## 共通原則

**サブエージェントは自身のシステムプロンプトがコンテキストのほぼ全量である。** 1 行の無駄も
1 行の誤りも起動のたびに払う。したがって分割の粒度（ADR-0010）と定義の中身（ADR-0011）は同じ
コスト構造に支配されている。

**サブエージェントが起動時に受け取るのは 6 種だけ**: 自身のシステムプロンプト＋環境情報 / 親が
書いた依頼文 / 全階層の `CLAUDE.md` / 親セッション開始時点の git status / `skills` で preload した
本文 / sibling roster。**会話履歴と親の auto memory は含まれない。** `hooks.json` のイベントは
`PreToolUse` / `PreCompact` / `SessionStart` / `SessionEnd` の 4 つで、サブエージェント起動時に発火
するものは無い。

**コンテキストを共有しないため、定義間の重複は原理的に消せない。** `record: 自分では書かない` の
ような指示や、複数 md にまたがる逐語重複は、参照へ落とすと fresh subagent 側に届かない
（[ADR-0023 代替案 7](06-staleness-detection.md) が同じ判断を繰り返している）。

**非可逆な事後圧縮を持たない。** 入力側（旧 `redux_filter`）でも出力側（`output-styles/slim`）でも
結論は同じ。トークン削減は「生成済みテキストの圧縮」ではなく「何を返すかの選択」で行う（ADR-0012）。

## ADR-0004: reviewer agent は write-capable Bash を保持する

**日付**: 2026-08-18  **ステータス**: accepted

### コンテキスト

`security-auditor` は frontmatter の `tools` から Bash を外し、Read/Grep/Glob のみで完結する
（`tests/test_md_references.py::test_security_auditor_has_no_bash_access` が技術的に強制）。一方
`reviewer` は `tools: Read, Grep, Glob, Bash` を維持しており、Bash を経由して任意の書き込み
（`>`・`sed -i` 等）が理論上可能な状態が残る。

監査は複数ラウンドでこの非対称を指摘している（v0.9.32 §6.3、v0.9.33 で再提起）。代案として
「validator runner とレビュー agent を分離し、reviewer には Bash を渡さない構成」が提示された。

`reviewer.md` は `ruff check` の実行と、呼び出し元から渡された `test_cmd` の再実行（RED→GREEN 遷移の
独立検証、`verify_mode: reexecute`）を職務として明記しており、これらはいずれも Bash を要する。

### 決定

**reviewer エージェントの `tools` から Bash を外さない。** 技術的な書き込み禁止の強制は行わず、既存の
散文制約（read-only の職務境界を明記し、逸脱時はレビューを継続せず報告して停止する）を維持する。

`ruff check` の全体実行と、渡された `test_cmd` を基底コマンドとした失敗テストの再実行はレビューの職務
そのものであり、これらを実行するには Bash が要る。security-auditor（10 項目チェックリストが Read/Grep/
Glob のみで完結する）とは職務の性質が異なるため、同じ強制を適用しない。

### 検討した代替案

#### 代替案 1: validator runner とレビュー agent を 2 分割する（§6.3 の代案）

- 長所: レビュー agent 自体からは Bash 権限が技術的に消え、security-auditor と同じ強制ができる
- 短所:
  1. レビュー結果と検証結果（PASS/FAIL）を突合する責務が、reviewer からその呼び出し元へ押し戻される
     だけで、「Bash を持つ主体が存在する」という根本的なリスクは消えない
  2. agent 分割・呼び出し 1 段増によるコンテキスト消費と収束遅延を招く（`loop-dev` の evaluate ステップは
     既に条件付き並列 `security-auditor` を持ち、これ以上の agent 増殖は turn cap との兼ね合いも悪化させる）
- 却下理由: コストに見合うリスク低減が無い過剰設計と判断した。書込み権限の技術的強制という根本課題は
  分割しても解決しない

#### 代替案 2: `ruff check` / `test_cmd` の再実行を呼び出し元へ移し、reviewer には結果だけ渡す

- 長所: reviewer から Bash 実行そのものを完全に排除できる
- 短所: `reviewer.md` の一次検証 step 0 が定める「`test_cmd` の三層検証（由来の明示・シグネチャの正規表現
  制約・引用符付け連結）」は、reviewer 自身が実行することで初めて検証結果の信頼性を担保している（実装者の
  自己申告コマンドは受け付けない設計）。呼び出し元が代わりに実行して結果だけ渡す構成にすると、「渡された
  結果が本当にそのコマンドの実行結果か」を reviewer が検証できなくなり、自己申告を信頼する経路が復活する
- 却下理由: 検証の独立性という reviewer の核心的な価値を失う

### 結果

**肯定的** — reviewer は `ruff check` / `test_cmd` の独立再実行という職務を、Bash 実行の主体を分割せずに
一貫して担える。

**否定的** — security-auditor と異なり、reviewer では frontmatter の `tools` だけで書き込み不能を技術的に
保証できない。

**リスク** — reviewer の散文制約は技術的強制ではないため、プロンプトインジェクション等でこの制約が無視
された場合、reviewer が実際に任意の書き込みを行う経路は理論上残る。この残存リスクを受容した上で、
`agents/reviewer.md` に本 ADR への参照と却下理由を明記し、再監査のたびに同じ議論を繰り返さないようにする。

## ADR-0010: サブエージェントは「渡す材料」で分割し、役割名では分割しない

**日付**: 2026-08-25  **ステータス**: accepted

### コンテキスト

サブエージェントは独立したコンテキスト窓・システムプロンプト・ツール権限を持つ別プロセスであり、親の会話
履歴を引き継がない。したがって分割しているのは「仕事」ではなく「情報」である。2 体に渡す材料がほぼ同じなら、
窓を 2 つ使うのにコンテキストは切れておらず、トークンだけが 2 倍になる。

本リポジトリの `agents/` は 13 定義まで増え、役割名（単純化役・デッドコード削除役・性能改善役・設計役・
計画役）で切られていた。その結果、定義本文に「未使用・重複削除は dead-code-cleaner、性能改善は
perf-optimizer 担当」のような相互ディスクレーマが三角形状に発生し、モデルが定義文なしでは境界を保持できない
状態になっていた。`commands/refactor.md` は同一ファイル群を clean → simplify → perf の 3 コンテキストで読み
直し、`skills/loop-dev/SKILL.md` は planner と architect に同じ要件・同じコードベースを渡して並列起動し、結果を
マージしていた。

### 決定

サブエージェントの分割は「渡す材料」で判断する。役割名・職能名でしか区別できない分割は行わない。

**分けない**

- 2 体に渡す材料がほぼ同じ
- 役割名・職能名でしか区別できない
- 職務が「束ね」だけで判断を持たない（それは親の仕事）

**分ける**

- 見せない情報がある — `comparator` は出力の出自を渡されない（盲検）。`reviewer` は実装者の思考過程を
  渡されない
- 道具の制限をかけたい — `security-auditor` は Bash を持たず、read-only がツール権限で技術的に強制される
- 返す形を固定したい — `grader` の判定 JSON 契約（固定するのは**出力の形状**であって、agent 自身がファイルを
  書くことではない。2026-08-27 に grader / comparator / bench-analyzer から汎用 `Write` を外し、結果は返値で
  返して呼び出し元が保存する形にしたが、形状契約はそのまま維持される）

**判定時の注意**: 材料の比較は「何を渡されるか」だけでなく「**何を持たされないか**」まで見る。`reviewer` と
`security-auditor` は表面上どちらも差分を読むが、reviewer には `test_cmd` と失敗テストシグネチャが渡され Bash で
再実行できるのに対し、security-auditor は差分のみで実行手段を持たない。材料は同一ではないため統合しない。

**付随ルール**

- 調べ物は組み込みの Explore / Plan に任せる。自作するのは道具制限か出力形式固定が必要なときだけ
- 新規エージェントに `Task` を与えない（子が子を呼ぶ階層を作らない）
- description には「何をするか」ではなく「**いつ呼ぶか**」（呼ばない条件を含む）を書く
- 材料が同じで観点だけ違うものは `agents/bench-analyzer.md` の `mode` 分岐方式で 1 体にまとめる
- 定義の**中身**に何を書き何を書かないかは ADR-0011

本 ADR は `agents/` 配下に置かず `docs/adr/` に置く。`CLAUDE.md` は全階層の全サブエージェントが毎回読むため、
エージェント定義を書くときだけ必要な基準をそこへ置くと起動回数だけコストが掛かる。

### 検討した代替案

#### 代替案 1: エージェント数を維持し、相互ディスクレーマを増補して境界を明確にする

- 長所: 呼び出し元の書き換えが不要。既存の並列起動による wall-clock 短縮を維持できる
- 短所: 同じ材料を複数コンテキストへ渡す構造は変わらず、トークンの二重払いが残る。境界記述は増え続ける
- 却下理由: ディスクレーマが必要なこと自体が、モデルに保持できない分割であることの証拠

#### 代替案 2: 基準を `CLAUDE.md` へ書く

- 長所: 全エージェントが自動で読むため周知が確実
- 短所: 全エージェントが毎回読むコストを払う。エージェント定義を書くとき以外は不要な情報
- 却下理由: 共有を 1 つ増やすと起動数だけ掛け算になる。基準の適用者はハーネスを編集する人間であり、実行中の
  エージェントではない

#### 代替案 3: `reviewer` と `security-auditor` も統合する

- 長所: 同じ差分を 2 回読むコストが消え、二重報告禁止ルールが不要になる
- 短所: `security-auditor` の read-only はツール権限による技術的強制であり、Bash を持つ reviewer へ統合すると
  散文の約束へ格下げされる。統合後の定義は 187 行となり「一体が見る範囲を 1 つに絞る」に反する
- 却下理由: 材料が同一ではない（上記「判定時の注意」）。ADR-0004 が示した「レビューと検証は同一職務」という
  判断とも整合する

### 結果

**肯定的**

- エージェント数 13 → 9。相互ディスクレーマの三角形が解消
- `commands/refactor.md` が同一ファイル群を 3 コンテキストで読み直す構造を解消
- `loop-dev` の plan 段が並列 2 起動から単一起動になり、コードベース探索の二重払いが解消
- `Task` を持つエージェントがゼロになり、「子が子を呼ばない」が tools 権限で構造的に保証される
- `perf-optimizer` の「計測駆動（必須）」契約が空文化していた（呼び出し元 3 ファイルが一度も計測データを渡して
  いなかった）ことが判明し、`code-refiner` の perf mode で前提条件として是正された

**否定的**

- `code-refiner` の 3 mode と `planner` の 2 モードは、呼び出し元が依頼文で明示する必要がある。親の手順書に
  書いた分岐は子へ届かないため、指定漏れは自動判別へフォールバックする（判別不能なら FAIL）
- `simplify` 段の並列起動は同一エージェントの複数インスタンスになり、`reviewer` + `security-auditor` 以外の
  異種並列が無くなった

**リスク**

- `code-refiner` は 3 mode 分の指示を 1 定義に持つため、mode ごとの参照節を冒頭表で明示していても他 mode の
  記述に引きずられる可能性がある。定義冒頭で「自分のモードの節と共通契約だけを読む」と明示して緩和している
- 統合の実効はトークン占有率で確認する必要がある。`/usage` のサブエージェント別内訳を統合前後で比較する

## ADR-0011: エージェント定義には挙動を書き、論拠と再説明は書かない

**日付**: 2026-08-25  **ステータス**: accepted

### コンテキスト

ADR-0010 で分割粒度を見直し 13 → 9 定義へ統合した後、残る 9 定義（計 1448 行）の**中身**を Anthropic 公式の
サブエージェント仕様とプロンプティング指針に照らして点検した。点検で 2 つの実害が見つかった。

1. **事実誤認**: 6 定義が「`<ple4-memory>` 注入で起動（SessionStart の `mem context`）」と書いていたが、サブ
   エージェントには届かない（共通原則を参照）。呼び出し元も渡していなかった。同じ文が `skills/learn`
   `skills/loop-dev`（`context: fork` は全継承）`commands/feat-dev.md` にもあるが、そちらは本体セッションで動く
   ため正しい — agents へのコピペで前提が壊れていた
2. **Opus 5 で逆効果になる指示**: 公式の Opus 5 ガイドは「レビュープロンプトが『高深刻度のみ報告せよ』『保守的に』
   と言うと、モデルはそれを literal に従い報告を減らす」「自己検証の再実行指示は書き直すのではなく削除せよ」と
   明記する。`reviewer` / `security-auditor` の 80% 確信度ゲートと `grader` の JSON 自己再読が該当していた

### 決定

エージェント定義には**そのエージェントの挙動を変える記述だけ**を置く。具体的には次を規約とする。

1. **自動注入されるものを前提にしない** — サブエージェントが起動時に受け取るものは共通原則の 6 種のみ。それ以外
   （会話履歴・親の注入・過去の検索結果）を前提に書かない。知識 DB を引くのは Bash を持つエージェントが自分で
   `ple4_run ple4.mem.cli search` を叩く経路だけ。Bash が無いエージェントにはメモリ経路が無いので、必要なら
   呼び出し元が依頼文へ載せる
2. **深刻度・確信度で報告を絞らせない** — 見つけたものはすべて出させ、確信が持てないものに「未確認」ラベルを
   付ける。ノイズ削減は重複統合とスタイル除外で行う。安全性の担保は `Blockers: {n}`（CRITICAL+HIGH 件数）という
   **集計の定義**側で行い、報告量では行わない
3. **自己検証の再実行は指示しない** — 出力が満たすべき不変条件は契約として書く。「保存後に読み直して確かめる」
   「答えを double-check する」といった再実行手順は書かない。ただし**他者の成果物**の検証（`reviewer` の
   `verify_mode: reexecute`）は職務そのものなので対象外
4. **設計判断の論拠は ADR に置く** — 「なぜこの構成を採ったか」はエージェントの挙動を変えない。定義には ADR への
   1 行参照だけを置く
5. **ツール権限が保証していることを散文で再説明しない** — 「Bash を持たないのでコマンド実行はできない」の詳説は
   不要。必要なのは「提案はテキストで返す」という行動指示だけ
6. **定義に書いた検証規則は CI で実測する** — 正規表現・許可リスト・形状検査など、外部入力をシェルやツールへ渡す
   前の関門を定義本文へ書いたら、その本文からリテラルを抽出して実入力で検査するテストを併せて置く。プロンプト
   文書の契約は誰も実行しないため、書き間違えても気づけない（本 ADR 後の pass で、`reviewer` の形状検証が
   `CLAUDE.md` 規定の正規コマンド `. .venv/bin/activate && ...` を拒否しつつ `source ../../../evil/activate` を
   通す状態のまま放置されていたことが判明した）。実装は `plugins/ple4/tests/test_agent_regex_contracts.py`

**判定行の欠落は「指摘ゼロ」ではない**（本 ADR の点検中に見つかった別の欠陥への対処）。`loop-dev` の収束条件と
`/refactor` の final gate は、`Blockers: {n}` 行が出力に実際に含まれていることを前提とする。行が無い場合（途中
終了・出力破損・起動失敗）は未収束 / `BLOCKED` として扱う。

### 検討した代替案

公式ドキュメントを根拠に一度は有望に見えたが、実測または出典の精読で棄却した。**同じドキュメントを読んだ人が
同じ「改善」を再提案しないよう記録する。**

#### 代替案 1: 強調語のスイープ（「必ず」「必須」を平常語へ緩める）

公式は「`CRITICAL: You MUST` のような攻撃的な語は過剰トリガーを招くので `Use this tool when...` に緩めよ」と
する。`必須|必ず|絶対|禁止|厳守|CRITICAL|MUST|一切` を数えて 65 件を得た（reviewer 21 / security-auditor 17）。

- 却下理由: 実際に中身を見ると **24 件は severity ラベルとしての `CRITICAL`** で、語調ではなく出力契約のデータ
  だった。残るトーン語も大半は緩めてはいけない硬い制約 — `Blockers: {n}` 行の必須性、テストコマンド注入に対する
  「1 点でも不一致なら実行せず BLOCKER」、決定 2 で維持すると決めた常時報告ルール。**count は diagnosis では
  なかった**
- 後続 pass による裏付け: 重複の削除だけを行い**トーンを緩める編集を 1 件も行わなかった**結果、強調語は
  65 → 38 件（40% 減）になった（`reviewer` 21→9 / `security-auditor` 17→1）。count は症状で、原因は重複だったことが
  実測で確認できた

#### 代替案 2: 番号付き手順の一般化

公式は「規範的なステップより一般的な指示の方が良い推論を生む」とする。`grader` 11 / `bench-analyzer` 13 /
`comparator` 10 ステップが対象に見えた。

- 却下理由: この記述は**thinking / reasoning セクション**にあり、推論の進め方の話であって出力形式の話ではない。
  当該 3 定義の番号付きステップは JSON 出力契約のフィールドと 1 対 1 対応しており（手順 4「各期待値を判定する」→
  `expectations[]`、手順 7「メトリクスと時間を読む」→ `execution_metrics` / `timing`）、一般化すると契約が壊れる

#### 代替案 3: XML タグによる構造化

- 却下理由: agent 定義はほぼ instructions 単独で、混在による曖昧さが起きていない。公式のサブエージェント例も素の
  markdown。全面書き換えの churn に見合わない

#### 代替案 4: `model:` を指定して安いモデルへ回す

- 却下理由: どのエージェントが品質を保てるかを判定する eval が当 repo に無い（`grader` / `comparator` の機械は
  skill 用）。検証手段を名指しできない賭けは打たない

#### 代替案 5: 汎用知識の列挙を削る

`security-auditor` の OWASP Top 10（13 行）、`code-refiner` のアルゴリズム改善表、`tdd-writer` のエッジケース
列挙は「モデルが既に知っている」ため削減候補に見えた。

- 却下理由: 公式のシステムプロンプト指針は「**チェックリストを入れよ**」を 5 項目のうちの 1 つとして明示的に推奨
  している。これらは知識の再教育ではなく網羅性の担保であり、削ると観点が落ちる
- **この代替案は 2 回再提案された。** 1 回目は 2026-09-06（[ADR-0022](06-staleness-detection.md)）、2 回目は
  2026-09-07（[ADR-0023](06-staleness-detection.md)）。どちらも棄却を維持しつつ、「残したものが古くなる経路」を
  ADR-0022 が塞いだ

#### 代替案 6: `maxTurns` で暴走に決定的な上限をかける

- 却下理由: `reviewer` / `security-auditor` は `Blockers: {n}` を機械読みされる。途中で打ち切られると判定行が
  出力されず、上記の「判定行の欠落」経路に乗って silent false-green になる。この経路を塞いだ後でも、打ち切りは
  未収束エスカレーションを増やすだけで得るものが無い。当 repo に暴走の観測実績も無い。書き込み権限を持つ
  `code-refiner` / `tdd-writer` では、中断が作業ツリーを不整合のまま残すためさらに悪い

#### 代替案 7: `effort: medium` で `reviewer` のコストを下げる

公式の Opus 5 ガイドは「コードレビューの精度は低い effort 設定でも保たれる」と明記しており、`low`・`medium` を
コスト制御の主レバーとして推奨する。

- 却下理由: その記述の文脈は「**速い一次パス＋後で徹底パス**」の二段構成が前提。当 repo の `reviewer` は単一パス
  で blocker を gate しており、構成が違うため endorsement が移らない。加えて同じ変更セットで報告方針（決定 2）を
  変えたばかりで、effort を重ねると品質変化の原因を切り分けられなくなる

### 結果

**肯定的**

- 6 定義から偽の前提が消えた。特に `planner` / `security-auditor` は Bash を持たず、「自動注入された知識だけを
  参照する」という実現不可能な指示を持っていた（節ごと削除。「繰り返し違反」の判定・表示は `commands/review.md`
  側で完結しており機能欠落なし）
- `reviewer` / `security-auditor` が深刻度で報告を絞らなくなった。`Blockers: {n}` は CRITICAL+HIGH の件数なので、
  MEDIUM/LOW が増えても gate は動かない
- `reviewer` から 851 バイトの ADR 重複論拠が消えた（ADR-0004 が同じ決定を記録済み）
- 判定行の欠落を「指摘ゼロ」と誤読する silent false-green が塞がれた
- 本 ADR のコミット列自身が残した適用漏れを後続 pass（`73bc4cd` / `42fe98e` / `13002cf`）で掃討した。撤去済み
  `## 確信度ゲート` への dangling 参照 2 箇所、`reviewer` の同一主張 4 重、`security-auditor` / `planner` に残って
  いた決定 5 違反、`skills/adr` と重複する `planner` のオーファン節。9 定義は 1448 → 1367 行。さらに後続 pass で
  決定 1・決定 2 の適用漏れが 2 件見つかった（`security-auditor` の到達不能な `secure` 参照、および「## 成功指標」
  ＝ 何も見つけないことを成功と定義しており決定 2 が塞いだ literal-following 失敗モードそのもの）
- v0.9.40 の定義で `reviewer` / `security-auditor` を実走させた E2E が、静的検査では届かない層をまとめて可視化した。
  本 ADR の決定に沿った削除で失われた制約が 3 件、決定 2 の適用漏れが 1 件、防御の非対称が 3 件、そして決定 6 が
  対象とする検証規則の破綻が 6 件見つかった。**定義の縮約は、削った記述が他のどこにも残っていないかを実測で
  確かめるまで完了しない**

**否定的**

- `record: 自分では書かない` の指示は Bash を持つ 4 定義に残る（共通原則を参照）
- 代替案 6・7 を採らなかったため、トークンコストの決定的な下げ幅は得ていない

**リスク**

- 決定 2 により MEDIUM/LOW の指摘量が増える。`/review` を人間が読む際のノイズが増える可能性がある。`Blockers` は
  動かないので自動ゲートへの影響は無いが、レポートが読みにくくなるようなら「## 絞り込み基準」（重複統合・スタイル
  除外）側を強める — 深刻度による抑制へ戻さない
- 決定 1 により、過去の知識を参照したいエージェントは自分で `search` を叩く必要がある。呼び出し元が依頼文へ載せる
  運用に切り替えるほうが安い場面もあり、実際の利用状況を見て見直す余地がある
- `grader` / `comparator` を実行して結果を確かめる経路が repo に無い（両者を対象にしたテストも無い）。両定義への
  変更は静的レビューでしか裏を取れないため、単独でリバートできるコミットに分けている

## ADR-0012: LLM 応答の事後圧縮パターン（output-style `slim`）を廃止する

**日付**: 2026-08-26  **ステータス**: accepted

### コンテキスト

`output-styles/slim.md` は「日本語で簡潔に応答。結論先・理由後、敬語なし」という応答スタイルをシステムプロンプトへ
強制注入し、出力トークンを削減する仕組みだった。`plugin.json` の `outputStyles` 登録と frontmatter の
`force-for-plugin: true` により、ple4 プラグイン配下の全セッションへ無条件で適用されていた。

このパターンは 2 世代の実装を経ている。初代は `hooks/pre_user_prompt.py`（UserPromptSubmit フックで
`skills/s-slim/SKILL.md` を毎プロンプト `additionalContext` へ注入）で、output-style 非対応ホストにも効かせる
ための経路だった。`47a54c9` でフックを削除し、`43277c7` でネイティブの output-style へ移行した。

移行後、**同一種類の障害を 5 回修正しても再発した**。

| commit | 内容 |
|---|---|
| `642ba7a` | output-styles/slim による tool use の破損解消 |
| `39e9790` | slim output-style の tool call 破損を抑止 |
| `c58ffba` | slim で JSON 文字列値のエスケープ破損を防止 |
| `58c775a` | slim で tool call/構造化出力を壊す圧縮を抑制 |
| `a169e5a` | slim の call 破損を境界原則の言い換えで封じる |

原因は一貫している。「簡潔に」「体言止め」という指示はモデルの出力**全体**にかかり、ツール引数・JSON 文字列値・
コードといった**一字一句が意味を持つ領域**まで圧縮対象に含めてしまう。対策として本文へ「コード・コマンド・
識別子・構造化出力は原文のまま」という境界原則を書き足す方針を繰り返したが、境界の言語化は網羅できず、
`a10f387` では本文を 60 行から 8 行へ削って副作用を減らす方向に転じていた。トークン削減が目的の仕組みが、破損の
抑制のために機能を削られ続けている状態だった。

同じ判断は既に一度下されている。自動 Bash 出力圧縮フック（旧 `redux_filter`）は「非可逆な行折りたたみがソース
コードを構文的に破壊する correctness hazard」としてハーネス監査の推奨チェックから撤去済みだった。入力側の事後
圧縮で結論が出ていたものが、出力側では未適用のまま残っていた。

### 決定

**LLM 応答の事後圧縮を目的とする仕組みを持たない。** 具体的には次を規約とする。

1. **output-style による応答圧縮を提供しない** — `output-styles/slim.md` とディレクトリを削除し、`plugin.json` の
   `outputStyles` 登録を外す。ple4 は output-style を配布しない
2. **ハーネス監査 rubric からも撤去する** — 他リポジトリへ同パターンを推奨しない。`context-strategic-compact`
   （3 点）と `cost-skill`（4 点）を削除し、repo モード満点は 65 → 58、チェック数は 24 → 22 になる。採点基準が
   変わるため `rubric_version` も `2026-08-26` へ上げる
3. **トークン削減は出力の「量」ではなく「経路」で行う** — 既に採っている手段を正とする。`list` / `search` が
   `- [kind] title (key)` の 1 行だけを返し `body` は `show` でのみ返す設計、0 件なら 1 文字も出力しない設計。
   これらは**何を返すかの選択**であり、生成済みテキストへの非可逆変換ではない
4. **応答スタイルの指定はユーザーの領分とする** — スタイルを強制したい利用者は `settings.json` の `outputStyle` で
   自分の選択を置く。プラグインが `force-for-plugin` で上書きしない

### 検討した代替案

#### 代替案 1: 境界原則の追記を続ける（6 回目の修正）

`a169e5a` までと同じく、破損したケースを本文の除外リストへ追加していく。

- 長所: 変更が小さい。トークン削減の効果を維持できる
- 短所: 境界の言語化は網羅できない。5 回の修正で本文は 60 行 → 8 行まで痩せており、次の追記は再び本文を膨らませる。
  膨らんだ本文は毎セッションのシステムプロンプトに載るので、削減したトークンを本文自身が食う
- 却下理由: **5 回の試行が経験的な反証になっている。**「どこを圧縮してはいけないか」を事前に列挙しきる前提そのもの
  が成り立たない — ツール引数の形式は呼び出すツールごとに違い、将来のツールは定義に存在しない

#### 代替案 2: rubric チェックだけ残す

- 長所: 満点とテストのアサーションを変えずに済む
- 短所: 自リポジトリの audit が永久に fail する。さらに悪いことに、ple4 自身が correctness hazard と判断して捨てた
  パターンを、他リポジトリへ 7 点分のスコアで推奨し続ける
- 却下理由: `redux_filter` 撤去と同一の論理がそのまま適用される。**自分が捨てたものを他人に勧めない**

#### 代替案 3: Copilot CLI 向けにプロンプト注入を復活させる

- 長所: ホスト間でスタイルが揃う
- 短所: 破損の原因は注入経路ではなく圧縮指示そのものなので、ホストを増やせば破損の再現箇所が増える。毎プロンプトの
  注入は SessionStart 一回の注入よりトークンを食う
- 却下理由: **決定の前提が逆。** 廃止するパターンに新しい配送経路を足す理由がない。なお現行 HEAD に注入経路は既に
  存在せず、Copilot CLI は移行後 slim を一度も受け取っていない

### 結果

**肯定的**

- ツール呼び出し・JSON・コード出力の破損源が 1 つ消える。同種の修正コミットが 6 回目を迎えない
- システムプロンプトから slim 本文と毎ターンの reminder が消え、入力トークンが減る
- ハーネス監査が自リポジトリで永久 fail する状態を解消し、他リポジトリへの誤った推奨を止める
- `redux_filter`（入力側）と slim（出力側）で判断が揃い、「非可逆な事後圧縮を持たない」が一貫した規約になる

**否定的**

- 応答が長くなり出力トークンが増える。定量値は測っていない（測るには同一タスクの A/B が要る）
- 日本語応答・結論先行を望む利用者は、自分の `settings.json` で `outputStyle` を設定する必要がある
- repo モード満点が 7 点下がるため、過去に採取した audit スコアと単純比較できない

**リスク**

- **スコアの断絶**: 外部に保存された過去の baseline JSON（`max_score: 65`）と混在すると改善幅を誤読する。判別の
  ため `rubric_version` を `2026-03-30` → `2026-08-26` へ上げた。版が異なる baseline 同士は満点が違うため、スコアの
  差ではなく達成率で比較すること
- **再発**: 「トークン削減」を目的に同じパターンが再提案されうる。本 ADR がその再提案に対する既定の回答になる
  （代替案 1〜3 が主要な再提案の形）
