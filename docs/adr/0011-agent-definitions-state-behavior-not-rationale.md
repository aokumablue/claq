# ADR-0011: エージェント定義には挙動を書き、論拠と再説明は書かない

**日付**: 2026-08-25  **ステータス**: accepted

## コンテキスト

ADR-0010 で分割粒度を「渡す材料」で見直し 13 → 9 定義へ統合した後、残る 9 定義（計 1448 行）の**中身**を Anthropic 公式のサブエージェント仕様とプロンプティング指針に照らして点検した。サブエージェントは自身のシステムプロンプトがコンテキストのほぼ全量であり、1 行の無駄も 1 行の誤りも起動のたびに払う。

点検で 2 つの実害が見つかった。

1. **事実誤認**: 6 定義が「`<bluecore-memory>` 注入で起動（SessionStart の `mem context`）」と書いていたが、サブエージェントには届かない。`hooks.json` のイベントは `PreToolUse` / `PreCompact` / `SessionStart` / `SessionEnd` の 4 つで、サブエージェント起動時に発火するものは無い。公式仕様上サブエージェントが受け取るのは「自身のシステムプロンプト＋環境情報 / 親が書いた依頼文 / 全階層の CLAUDE.md / 親セッション開始時点の git status / `skills` で preload した本文 / sibling roster」であり、会話履歴と親の auto memory は含まれない。呼び出し元も渡していなかった。同じ文が `skills/learn` `skills/loop-dev`（`context: fork` は全継承）`commands/feat-dev.md` にもあるが、そちらは本体セッションで動くため正しい — agents へのコピペで前提が壊れていた。
2. **Opus 5 で逆効果になる指示**: 公式の Opus 5 ガイドは「レビュープロンプトが『高深刻度のみ報告せよ』『保守的に』と言うと、モデルはそれを literal に従い報告を減らす」「自己検証の再実行指示は書き直すのではなく削除せよ」と明記する。`reviewer` / `security-auditor` の 80% 確信度ゲートと `grader` の JSON 自己再読が該当していた。

## 決定

エージェント定義には**そのエージェントの挙動を変える記述だけ**を置く。具体的には次の 5 つを規約とする。

1. **自動注入されるものを前提にしない** — サブエージェントが起動時に受け取るものは上記の 6 種のみ。それ以外（会話履歴・親の注入・過去の検索結果）を前提に書かない。知識 DB を引くのは Bash を持つエージェントが自分で `bluecore_run bluecore.mem.cli search` を叩く経路だけ。Bash が無いエージェントにはメモリ経路が無いので、必要なら呼び出し元が依頼文へ載せる
2. **深刻度・確信度で報告を絞らせない** — 見つけたものはすべて出させ、確信が持てないものに「未確認」ラベルを付ける。ノイズ削減は重複統合とスタイル除外で行う。安全性の担保は `Blockers: {n}`（CRITICAL+HIGH 件数）という**集計の定義**側で行い、報告量では行わない
3. **自己検証の再実行は指示しない** — 出力が満たすべき不変条件は契約として書く。「保存後に読み直して確かめる」「答えを double-check する」といった再実行手順は書かない（モデル自身の挙動と二重化してコストだけ増える）。ただし**他者の成果物**の検証（`reviewer` の `verify_mode: reexecute`）は職務そのものなので対象外
4. **設計判断の論拠は ADR に置く** — 「なぜこの構成を採ったか」はエージェントの挙動を変えない。定義には ADR への 1 行参照だけを置く
5. **ツール権限が保証していることを散文で再説明しない** — 「Bash を持たないのでコマンド実行はできない」の詳説は不要。必要なのは「提案はテキストで返す」という行動指示だけ

**判定行の欠落は「指摘ゼロ」ではない**（本 ADR の点検中に見つかった別の欠陥への対処）。`loop-dev` の収束条件と `/refactor` の final gate は、`Blockers: {n}` 行が出力に実際に含まれていることを前提とする。行が無い場合（途中終了・出力破損・起動失敗）は未収束 / `BLOCKED` として扱う。

## 検討した代替案

公式ドキュメントを根拠に一度は有望に見えたが、実測または出典の精読で棄却した。**同じドキュメントを読んだ人が同じ「改善」を再提案しないよう記録する。**

### 代替案 1: 強調語のスイープ（「必ず」「必須」を平常語へ緩める）

公式は「`CRITICAL: You MUST` のような攻撃的な語は過剰トリガーを招くので `Use this tool when...` に緩めよ」とする。`必須|必ず|絶対|禁止|厳守|CRITICAL|MUST|一切` を数えて 65 件を得た（reviewer 21 / security-auditor 17）。

- 却下理由: 実際に中身を見ると **24 件は severity ラベルとしての `CRITICAL`**（`CRITICAL: 1 / HIGH: 1`、`Hardcoded secrets → CRITICAL:`）で、語調ではなく出力契約のデータだった。残るトーン語も大半は緩めてはいけない硬い制約 — `Blockers: {n}` 行の必須性（loop-dev が機械読みする契約）、テストコマンド注入に対する「1 点でも不一致なら実行せず BLOCKER」、決定 2 で維持すると決めた常時報告ルール。**count は diagnosis ではなかった**

### 代替案 2: 番号付き手順の一般化

公式は「規範的なステップより一般的な指示の方が良い推論を生む」とする。`grader` 11 / `bench-analyzer` 13 / `comparator` 10 ステップが対象に見えた。

- 却下理由: この記述は **thinking / reasoning セクション**にあり、推論の進め方の話であって出力形式の話ではない。当該 3 定義の番号付きステップは JSON 出力契約のフィールドと 1 対 1 対応しており（手順 4「各期待値を判定する」→ `expectations[]`、手順 7「メトリクスと時間を読む」→ `execution_metrics` / `timing`）、一般化すると契約が壊れる

### 代替案 3: XML タグによる構造化

公式は「instructions / context / examples / 変数入力が混在するプロンプトでは XML タグが曖昧さを減らす」とし、例は `<example>` で囲むことを推奨する。

- 却下理由: agent 定義はほぼ instructions 単独で、混在による曖昧さが起きていない。公式のサブエージェント例も素の markdown。全面書き換えの churn に見合わない

### 代替案 4: `model:` を指定して安いモデルへ回す

- 却下理由: どのエージェントが品質を保てるかを判定する eval が当 repo に無い（`grader` / `comparator` の機械は skill 用）。検証手段を名指しできない賭けは打たない

### 代替案 5: 汎用知識の列挙を削る

`security-auditor` の OWASP Top 10（13 行）、`code-refiner` のアルゴリズム改善表、`tdd-writer` のエッジケース列挙は「モデルが既に知っている」ため削減候補に見えた。

- 却下理由: 公式のシステムプロンプト指針は「**チェックリストを入れよ**（確認・検証すべき項目のリスト）」を 5 項目のうちの 1 つとして明示的に推奨している。これらは知識の再教育ではなく網羅性の担保であり、削ると観点が落ちる

### 代替案 6: `maxTurns` で暴走に決定的な上限をかける

- 却下理由: `reviewer` / `security-auditor` は `Blockers: {n}` を機械読みされる。途中で打ち切られると判定行が出力されず、上記の「判定行の欠落」経路に乗って silent false-green になる。この経路を塞いだ後でも、打ち切りは未収束エスカレーションを増やすだけで得るものが無い。当 repo に暴走の観測実績も無い。書き込み権限を持つ `code-refiner` / `tdd-writer` では、中断が作業ツリーを不整合のまま残すためさらに悪い

### 代替案 7: `effort: medium` で `reviewer` のコストを下げる

公式の Opus 5 ガイドは「コードレビューの精度は低い effort 設定でも保たれる」と明記しており、`low`・`medium` をコスト制御の主レバーとして推奨する。

- 却下理由: その記述の文脈は「**速い一次パス＋後で徹底パス**」の二段構成が前提。当 repo の `reviewer` は単一パスで blocker を gate しており、構成が違うため endorsement が移らない。加えて同じ変更セットで報告方針（決定 2）を変えたばかりで、effort を重ねると品質変化の原因を切り分けられなくなる

## 結果

### 肯定的

- 6 定義から偽の前提が消えた。特に `planner` / `security-auditor` は Bash を持たず、「自動注入された知識だけを参照する」という実現不可能な指示を持っていた（節ごと削除。「繰り返し違反」の判定・表示は `commands/review.md` 側で完結しており機能欠落なし）
- `reviewer` / `security-auditor` が深刻度で報告を絞らなくなった。`Blockers: {n}` は CRITICAL+HIGH の件数なので、MEDIUM/LOW が増えても gate は動かない
- `reviewer` から 851 バイトの ADR 重複論拠が消えた（ADR-0004 が同じ決定を記録済み）
- 判定行の欠落を「指摘ゼロ」と誤読する silent false-green が塞がれた
- 本 ADR のコミット列自身が残した適用漏れを後続 pass（`73bc4cd` / `42fe98e` / `13002cf`）で掃討した。撤去済み `## 確信度ゲート` への dangling 参照 2 箇所（`5d200fc` の残骸）、`reviewer` の同一主張 4 重、`security-auditor` / `planner` に残っていた決定 5 違反、`skills/adr` と重複する `planner` のオーファン節。9 定義は 1448 → 1371 行

### 否定的

- `record: 自分では書かない` の指示は Bash を持つ 4 定義に残る。サブエージェントはコンテキストを共有しないため、この種の指示の重複は原理的に消せない
- 代替案 6・7 を採らなかったため、トークンコストの決定的な下げ幅は得ていない

### リスク

- 決定 2 により MEDIUM/LOW の指摘量が増える。`/review` を人間が読む際のノイズが増える可能性がある。`Blockers` は動かないので自動ゲートへの影響は無いが、レポートが読みにくくなるようなら「## 絞り込み基準」（重複統合・スタイル除外）側を強める — 深刻度による抑制へ戻さない
- 決定 1 により、過去の知識を参照したいエージェントは自分で `search` を叩く必要がある。呼び出し元が依頼文へ載せる運用に切り替えるほうが安い場面もあり、実際の利用状況を見て見直す余地がある
- `grader` / `comparator` を実行して結果を確かめる経路が repo に無い（両者を対象にしたテストも無い）。両定義への変更は静的レビューでしか裏を取れないため、単独でリバートできるコミットに分けている
