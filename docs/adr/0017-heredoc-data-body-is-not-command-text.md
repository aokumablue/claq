# ADR-0017: heredoc のデータ本文はコマンド列として解析しない

**日付**: 2026-08-31  **ステータス**: accepted

## コンテキスト

PreToolUse の保護フック 3 種（`block_no_verify` / `bash_config_protection` /
`pre_bash_commit_quality`）は `hook_common.tokenize`（`shlex`）でコマンド文字列を
トークン化して判定する。`shlex` は heredoc を解釈しないため、本文行も通常のトークン
として返る。その結果、本文に書いた**散文**が実行命令として読まれる。v0.9.44 の実起動で
確認した誤発火は次の 3 件（いずれも `<<'EOF'` のクォート付き区切り＝シェルが一切展開
しない純データ）:

- `cat > note.md <<'EOF'` の本文に `git commit --no-verify` → `block_no_verify` が exit 2
- 同形の本文に `printf x > pyproject.toml` → `bash_config_protection` が exit 2
- 同形の本文に `git commit` → `pre_bash_commit_quality` が staged 検査へ入り、index に
  問題があれば exit 2

対照として `echo 'git commit --no-verify'` は exit 0 になる（`shlex` がクォート内を
1 トークンに保つため）。つまり「同じ語をクォートで囲めば通り、heredoc に書くと落ちる」
という非対称が出ている。このリポジトリ自身の文書はフックの禁止事項を頻繁に名指しする
ため、自分のフックを説明する文書を自分のフックが書かせない状態になっていた。

一方で `bash <<'EOF'` / `cat <<'EOF' | bash` では本文が**実際に実行される**。実測でも
これらは exit 2 であり、本文を一律に除去すれば ADR-0002 が禁じる誤通過が生まれる。

## 決定

heredoc の**データ**本文は、トークン化の前段でコマンド文字列から除去する
（`hook_common.strip_data_heredoc_bodies`）。ただし本文がデータだと**静的に確定できる
場合だけ**除去し、確定できなければ除去せず現状の検出側へ倒す。除去しない条件は次の 3 つ:

1. 演算子行にシェル起動トークンがある（`SHELL_WRAPPER_EXECUTABLES` = `sh`/`bash`/`zsh`/`dash` の basename）
2. 演算子行が継続演算子（`\` / `|` / `&`）で終わる — 本文の開始位置が次行とは限らない
3. 終端行が見つからない（未終端）

これは ADR-0002 の例外ではなく**適用範囲の明確化**である。ADR-0002 の「誤検出 > 誤通過」は
解析できない構文についての規定であり（`pre_bash_commit_quality` の F-08 が同じ線引きを既に
採っている）、heredoc の本文範囲は演算子・区切り語・終端行だけで決まる環境非依存の構文で
あって、エイリアス・変数展開・PATH のような環境依存の意味解釈を含まない。

## 検討した代替案

### 代替案 1: NO-FIX（ADR-0002 を根拠に据え置く）

- 長所: 変更ゼロ。誤通過リスクを一切増やさない。
- 短所: 文書作成という標準作業が塞がれる。`pre_bash_commit_quality` の誤発火は index の
  状態に依存するため再現性がなく、抑止として機能せず誤った安心感だけを残す。
- 却下理由: ADR-0002 の適用範囲は解析できない構文であり、heredoc はそれに当たらない。

### 代替案 2: `tokenize` / `tokenize_with_status` の内部で正規化する

- 長所: 修正点が 1 箇所で済む。
- 短所: `pre_bash_commit_quality` の生文字列正規表現フォールバックが非正規化のまま残り
  FP が半分残る。4 フックの挙動が 0 行 diff で変わり、フック単位の被覆を説明できない。
- 却下理由: 上記のとおり穴が残り、被覆の説明可能性も失う。

### 代替案 3: `lib/harness.iter_bash_commands` で正規化する

- 長所: 全フックを 1 点で覆える。
- 短所: list 形状のコンテナを改行で連結する仕様のため heredoc が合成境界をまたぐ。
  `sh -c` の再帰経路も覆えない。payload 形状の責務にシェル構文の知識が混ざる。
- 却下理由: 責務の混在と、覆えない経路が残ること。

### 代替案 4: データ消費コマンドの allowlist（`cat`/`tee`/`jq` のときだけ剥がす）

- 長所: さらに検出側へ倒れる。
- 短所: 集合が無限に広がり、列挙から漏れたコマンドで FP が戻る。
- 却下理由: 「実行されうる形か」という判定軸に直接対応するのは denylist 側。

## 結果

### 肯定的

- 実測 FP 3 件が解消し、文書作成が保護フックに阻まれなくなった。
- `SHELL_WRAPPER_EXECUTABLES` が `hook_common` へ移り、`sh -c` 再帰と heredoc 判定が
  同じ集合を参照する（判定軸が 2 つに割れない）。
- 終端行を残す設計により正規化は冪等で、適用点がフックごとに異なっても二重適用が安全。

### 否定的

- 非シェルインタプリタ（`python3 - <<EOF` 等）の本文が間接的にシェルを起動する形は
  検出できない。これは ADR-0002 が `python -c` 経由の間接実行を既に非目標としたのと
  同じ境界であり、一貫している。
- 終端行の後続に空白がある場合（`EOF `）は POSIX どおり終端しない。bash 自身も終端
  しないため穴ではないが、直感には反する。

### リスク

- `cat <<'EOF' |` で改行し次行が `bash` という形は、本文の開始位置が次行ではないため
  「継続演算子で終わる行は残す」規則で守っている。この規則は後から「冗長」と見えて
  単純化されやすい。`tests/hooks/test_hook_common.py` の表と
  `tests/hooks/test_heredoc_boundary.py` の横断表で固定する。
- ネストした heredoc（`<<'OUTER'` の本文に `<<'INNER'`）で走査が同期ずれを起こすと
  静かな誤通過になる。本文走査中は `<<` を再検出しない設計とし、テストで固定した。
