# ADR-0018: `cd` を含むコマンドでは repo スコープ判定を信用せず deny する

**日付**: 2026-09-03  **ステータス**: accepted

## コンテキスト

`bash_config_protection` は保護対象ファイル（`ruff.toml` / `pyproject.toml` 等）への
Bash 経由の書き込みを検出するが、deny するのは書き込み先が**現在のリポジトリ配下**に
ある場合だけである（A-06）。この repo スコープ判定は、書き込み先トークンを
`Path.cwd()` 基準で解決して `repo_root` 配下かを見る形で実装されていた。

`cd` は同じコマンド文字列の中で cwd を動かす。フックはコマンドを**実行前**に静的解析
するため、`cd` 以降のセグメントに現れる相対パスは実行時の位置とずれる。実測（v0.9.48）:

- `cd plugins && printf 'x' > ../ruff.toml` → exit 0（素通り）
  実行時の書き込み先はリポジトリ直下の `ruff.toml` だが、フックは cwd 基準で
  `<repo>/../ruff.toml` と解決し「リポジトリ外」と判定していた。
- 対照 `printf 'x' > ruff.toml` は exit 2。

`cd` の有無だけで保護が外れるため、これは「うっかりバイパス」の抑止としても成立して
いない。なお構文自体は問題なく解析できており、ADR-0002 の「解析できない構文は誤検出側へ
倒す」という規定はこのケースを直接には覆わない。ずれているのは構文解析ではなく
**スコープ規則の前提**（cwd が実行時まで不変であること）である。

## 決定

**コマンドが `cd` / `pushd` / `popd` / `chdir` を含む場合、repo スコープ判定を適用せず、
保護対象 basename のヒットをそのまま deny する。**

`cd` を跨いだ symlink 解決のずれは同じ理由で非目標とする（解決の基準点が不明なまま
symlink を辿っても結果は信用できない）。

これは ADR-0002 の適用範囲の拡張であり、ADR-0017 が heredoc について行ったのと同じ
「スコープ規則の明確化」に当たる。ADR-0002 が扱うのが**構文**の不確定性であるのに対し、
本 ADR が扱うのは**実行時状態**（cwd）の不確定性である。倒す向きは同じ
（判定できない状態は誤検出側へ倒す）。

## 検討した代替案

### 代替案 1: NO-FIX（`cd` 経由の書き込みは非目標と明記する）

- 長所: 変更ゼロ。false positive を一切増やさない。
- 短所: `cd` を 1 つ足すだけで保護が外れる。「保護がある」という表示が誤った安心に
  なる状態が残り、ADR-0002 が繰り返し指摘を招くと述べた「経路ごとに場当たりで倒し方を
  決める」状態そのものになる。
- 却下理由: 抑止として機能しない保護を残す判断だから。

### 代替案 2: `cd` を追跡して解決基準点を更新する

- 長所: 判定が正確になり、false positive が増えない。`cd /tmp && printf x > ruff.toml`
  のようにリポジトリ外が確定するケースを正しく allow できる。
- 短所: サブシェル（`(cd /tmp; ...)`）・パイプライン内の `cd`・`cd -`・変数展開を含む
  `cd "$D"` を正しく扱うにはシェルのスコープ規則の模倣が要る。`split_segments` は
  `(` / `)` を区切りとして捨てるため、サブシェルの境界情報は既に失われている。
  さらにこの案は**現在 deny しているケースを allow へ緩める**方向の変更を含む
  （`cd /tmp && printf x > ruff.toml` は現在 exit 2）。
- 却下理由: 誤通過を新たに作りうる緩和を、模倣の正確さに依存する実装で導入することに
  なるため。ADR-0002 の「無理に対応範囲を広げない」に反する。

## 結果

### 肯定的

- `cd` の有無で保護が外れる経路が閉じる。
- 判定できない状態の倒し方が `block_no_verify` / `bash_config_protection` で揃う。

### 否定的

- リポジトリ**外**のディレクトリへ `cd` してから保護対象と同じ basename の
  ファイルを書く操作が deny される。使い捨てフィクスチャを scratchpad に
  `ruff.toml` という名前で作る手順がこれに当たる（既知の pitfall
  `config-protection-denies-fixture-config-basenames` と同じ回避策が効く:
  フィクスチャに保護対象の basename を使わない）。

### リスク

- `cd` を含む長いコマンドで、書き込み先が明らかにリポジトリ外でも deny される。
  回避は `cd` を別の Bash 呼び出しへ分けるか、basename を変えること。いずれも
  agent 側で完結し、保護フックの無効化を伴わない。
