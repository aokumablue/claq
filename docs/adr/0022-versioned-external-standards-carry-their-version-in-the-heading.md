# ADR-0022: 外部の版付き標準を定義へ列挙するときは版を見出しへ書く

**日付**: 2026-09-06  **ステータス**: accepted

## コンテキスト

ADR-0011 代替案 5 は「汎用知識の列挙を削る」を棄却し、`security-auditor` の OWASP Top 10・
`code-refiner` のアルゴリズム改善表・`tdd-writer` のエッジケース列挙を**網羅性の担保**として
意図的に残すと決めた。この判断自体は今も正しい。

しかし「残す」と決めたことで、**残したものが古くなる経路**が開いたまま塞がれていなかった。
2026-09-06 の定義レビューで実害が 2 件見つかった。

1. `agents/security-auditor.md` の OWASP Top 10 が **2017 版**のまま 2 版取り残されていた。
   現行 2025 版で新設・再編された **A03 Software Supply Chain Failures** /
   **A06 Insecure Design** / **A10 Mishandling of Exceptional Conditions** が丸ごと欠落し、
   逆に廃止済みの XXE・Insecure Deserialization がトップレベルに残っていた。
   とりわけ A10（例外・タイムアウト・上限超過での fail open）は、ADR-0001 がこのリポジトリ
   自身の設計として採択した支配的パターンそのものであり、`security-auditor` は同じファイルの
   「## プロンプト・エージェント境界」節で fail-open 検査を**手作りしていた** — 分類として
   与えられていれば手作りは要らなかった。
2. `skills/skill-make/references/schemas.md` の `executor_model` が旧世代の
   `claude-sonnet-4-20250514` のままだった。benchmark fixture の雛形なので生成物へ伝播する。

どちらも既存の検査を素通りする。`tests/test_md_references.py` は `.md` 参照の切れを検出するが、
**外部世界の事実が古くなったこと**は検出できない。ADR-0011 決定 6 の「定義に書いた検証規則は
CI で実測する」も、実測できるのはリポジトリ内で閉じた規則だけである。ADR-0016 が denylist の
陳腐化について解いた問題と同型だが、あちらはローカルの実コーパスと突合できたのに対し、
こちらは外部の版と突合するしかない。

さらに、この 2026-09-06 のレビューは **ADR-0011 代替案 5 とまったく同じ「OWASP 列挙の削除」を
再提案した**。ADR-0011 はその再提案を防ぐために代替案を記録したのに、防げていない。
理由は単純で、`security-auditor.md` の OWASP 節から ADR-0011 への参照が無く、
`docs/` は配布物に含まれないため、定義だけを読む者には棄却の事実が届かないからである。

## 決定

1. **外部の版付き標準を列挙するときは、版を見出しへ含める** — `## OWASP Top 10:2025` のように
   書く。版が見出しにあれば `git diff` にもレビューの目にも入り、「いつのものか」を読み手が
   判断できる。無版の `## OWASP Top 10` は「常に最新」を騙る
2. **版を書けないもの・書きたくないものは列挙せず、名前で参照する** — 網羅性の担保が要らない
   なら列挙しない。要るなら版を背負う。どちらでもない中間（無版の列挙）を置かない
3. **CI ゲートにはしない** — 外部ソースの取得はネットワーク依存であり、CLAUDE.md の
   「ランタイム依存はゼロ（標準ライブラリのみ）」に反する。加えて ADR-0016 代替案 3 と同型で、
   オフライン CI では常に skip され `0` と区別されないまま形骸化する。検知は `/maintain` の
   web トレンド入力（既定 ON・失敗時は「トレンド入力なし」と明記して続行）と、`/review` の
   観点「md の節見出しに含まれる年号・版を現行と突き合わせる」に載せる
4. **ADR で意図的に残すと決めた節には、定義側から ADR への 1 行参照を置く** — これは
   ADR-0011 決定 4（「設計判断の論拠は ADR に置く。定義には ADR への 1 行参照だけを置く」）の
   適用であって新しい決定ではない。適用漏れが実際に再提案を招いたので明記する

## 検討した代替案

### 代替案 1: 列挙をやめ、標準の名前だけを参照する（`OWASP Top 10 を全項目確認する`）

- 長所: 陳腐化しない。トークンも減る。モデルは OWASP Top 10 を名前で知っている。
- 短所: 版を指定しない参照は、モデルの学習時点の版へ黙って落ちる。陳腐化が
  「見えるところ」から「見えないところ」へ移動するだけで、悪化している。
- 却下理由: ADR-0011 代替案 5 が同じ提案を「網羅性の担保が落ちる」として棄却済み。
  本 ADR はその決定を覆さない。

### 代替案 2: CI で外部ソースを取得し、列挙との差分を検知する

- 長所: 自動で回る。人手の突合が要らない。
- 短所: ネットワーク依存。CLAUDE.md の依存ゼロ原則に反し、オフライン CI では常に skip される。
  外部サイトの構造変更で壊れる保守負債も増える。
- 却下理由: ADR-0016 代替案 3 と同じ形 — 常に走らないものを CI ゲートに見せかけると、
  ゲートの信頼そのものが下がる。

### 代替案 3: 版はコメントや本文の末尾に書き、見出しは無版のままにする

- 長所: 見出しが安定する。既存の節参照（`「## OWASP Top 10」`）を壊さない。
- 短所: 本文末尾の年号は diff の文脈行に埋もれ、レビューの目に入らない。今回の 2017 版も
  「2017」と書いてすらいなかったが、仮に末尾にあっても 2 版分見逃されていた可能性が高い。
- 却下理由: 見えないところに書いた版は、書いていないのとほぼ同じ。なお本リポジトリの
  節参照（`test_md_references.py` の `_iter_section_refs`）が OWASP 節を指している箇所は
  無いため、見出し変更のコストは実際には発生しない。

### 代替案 4: 何もせず、定期メンテの運用注意に委ねる

- 長所: 変更が要らない。
- 短所: ADR-0011（2026-08-25）で「意図的に残す」と決めてから 2026-09-06 まで、
  `/maintain` も `/review` も 2017 版であることを検出していない。運用注意は既に失敗している。
- 却下理由: ADR-0016 代替案 1 と同じく、実績が反証している。

## 結果

### 肯定的

- 陳腐化が `git diff` とレビューの目に入る位置へ出た。無言の劣化から、見える劣化になった。
- OWASP 2025 の A10（Mishandling of Exceptional Conditions）が分類として入ったことで、
  `security-auditor` の fail-open 検査が手作りの独自節ではなく標準分類に乗った。
  ADR-0001 が採択したこのリポジトリ自身の fail-open 設計を監査する語彙が揃った。
- `skills/secure/SKILL.md` にサプライチェーン（ビルド系・配布経路）と異常系の観点が入り、
  `security-auditor` と `secure` のカバレッジが揃った。
- ADR-0011 代替案 5 への 1 行参照が定義側に付き、次のレビューが同じ削除を再提案する経路が
  1 つ塞がった。

### 否定的

- 版を上げるたびに見出しが変わる。節参照を持つ節では参照側の追従が要る（現状 OWASP 節に
  参照は無いが、将来同じ形を他の節へ適用するときは確認が要る）。
- 「版を書く」は規約であって強制ではない。無版の列挙を新たに書いても何も落ちない。

### リスク

- 検知経路が `/maintain` の web トレンド入力と `/review` の人手観点だけであり、どちらも
  ADR-0016 と同じく **fail open の診断**である。見逃しは「発見が遅れる」として現れる。
  これは意図した設計判断で、注入経路上のフィルタではないため fail closed にはしない。
- 版を持たない外部知識（言語慣行・フレームワーク作法）はこの規約の射程外で、陳腐化を
  検出する手段が引き続き無い。
