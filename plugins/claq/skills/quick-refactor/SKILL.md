# 即時ハンドオフリファクタ

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | 振る舞いを変えない書き換えを適用する / 等価性の根拠を型で名指す / 崩れるとすればどこかを挙げる / 守るテストの所在を示す |
| 人間 | テストを走らせる / 緑が保たれたか確かめる / 等価性の判断を下す / 結果を貼り戻す |

このモードは検証を省くのではなく、人間の手に移す。省くのは「自分で走らせて自分で緑を見る」工程だけである。

## ルール1: 確かめるためのコマンドを自分で実行しない

やらないこと — 書き換えが等価か確かめるために次を実行すること。

- テストスイートの実行
- ビルド / コンパイル
- リンタ / フォーマッタ / 型検査
- 対象プログラムの試走・ベンチマーク

やること — 読解は制限しない。対象の読み取り、呼び出し元の全探索、既存テストの一覧、動的参照の検索は続け、むしろ増やす。走らせずに等価性を主張する根拠は現物の読解しかない。抑えるのは実行であって調査ではない。

例外 — 人間が明示的に実行を頼んだら従う。実行しても返し方は変えず、結果は「実行済み」行に入れる。抑えているのは頼まれていない自己検証である。

## ルール2: 振る舞いを変える変更を混ぜない

書いてよいのは、観測できる振る舞いが変わらない書き換えだけ。バグ修正・仕様変更・性能改善・エラーメッセージの改善は、どれも振る舞いの変更であってリファクタではない。

途中でバグを見つけても直さず、「ついでに見つけたもの」に 1 行で挙げる。直してしまうと、テストが落ちたときに人間は「リファクタが壊したのか、修正が壊したのか」を切り分けられない（等価でない変更が 1 行でも混ざると、等価性の主張を検証できなくなる）。

リファクタの種類も混ぜない。改名と抽出と移動を 1 回で当てると、落ちたときにどの操作が壊したか分からないので、種類ごとに分けて並べる。

## ルール3: 等価性は根拠の型で名指す

「振る舞いは変えていません」は主張であって根拠ではない。操作の型を名指すと、その型に固有の壊れ方が決まる。探すのは自分の書き換えの粗ではなく、その型が壊れる既知の箇所である。

| 型 | 崩れるとすればここ |
|---|---|
| 移動 | 評価順・初期化順・スコープの変化、定義前参照 |
| 改名 | 文字列や設定からの動的参照、外部公開名なら未追跡の呼び出し元 |
| 抽出 | キャプチャし損ねた変数、早期 return の意味変化、例外の通り道 |
| インライン化 | 副作用の実行回数、短絡評価で消えていた式の復活 |
| 重複の統合 | 2 箇所にあった微差（境界値・既定値・ログ文言）の消失 |
| デッドコード削除 | リフレクション・設定ファイル・テストからの参照 |

表に無い型を当てたら、その型が崩れる箇所を自分で 1 行書く。書けないなら、その書き換えは等価だと主張できていない。

## ルール4: 守るテストの所在を先に特定する

等価性を検査する手段が無いまま構造を変えるのは賭けである。書き換える前に、その振る舞いを現に守っているテストを探す。

- ある → 書き換えを適用し、そのテスト名をハンドオフに載せる
- 無い → 構造には手を付けず、現在の挙動を固定する特性化テストを先に出し、緑を確かめてから書き換える順にする。テストの体裁は quick-test に合わせ、期待する色は GREEN で宣言する

「テストが無いので慎重に書き換えました」はこのモードの失敗である。慎重さは検査の代わりにならない。

## ルール5: 解説は差分と意図だけ

書くもの: 何をどの型で書き換えたか、なぜ等価か。

書かないもの: 書き換えていない箇所の説明、コード全文の再掲（変更行だけで足りる）、一般論・設計論・前置き・締めの挨拶、リファクタの効能の一般論（「可読性が上がります」は根拠ではない）。

## 制御を返すときの形

毎回この構造と順番で返す。

```text
適用した書き換え:
- <ファイルパス>: <何をしたか。1行> / 型: <移動 / 改名 / 抽出 / インライン化 / 統合 / 削除 のいずれか>

等価性の根拠: <その型で振る舞いが保たれると言える理由。1〜2文>

崩れるとすれば: <その型に固有の壊れ方のうち、実際に確認した箇所。確認できていなければそう書く>

守るテスト: <このリファクタが壊れたら落ちるテスト名。見つからなければ「無し」と書き、特性化テストを先に出した旨を添える>

ついでに見つけたもの: <手を出さなかったバグ・設計上の疑問。1行ずつ。無ければ「なし」>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと結果を1行。頼まれていなければ行ごと省く>

次に実行: <そのまま貼れるコマンド1行>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  通れば: <何が見えれば等価だと判断できるか>
  落ちたら: <どの出力のどの部分を貼り戻してほしいか>
```

「崩れるとすれば」「守るテスト」はブロックごと省かず、該当が無ければ「なし」と 1 行書く（ブロックが消えると、危険が無かったのか確認を書き忘れたのかを区別できない）。「次に実行」「落ちたら」の無いハンドオフは失敗である。次に何をすればよいか、落ちたときに何を貼ればよいかが分からなければ、往復はそこで止まる。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る（パッケージ定義のスクリプト欄、タスクランナーの設定、テスト設定ファイル、CI の定義、リポジトリの開発手順書）。

書く前にリポジトリ直下のファイル一覧を見て、宣言ファイルを実際に開き、そこにある文字列をそのまま渡す。この種の宣言はほぼルートにあり、対象を追ってソースを読んでいるだけでは目に入らない。

「守るテスト」の絞り込みの記法も同じに扱う。そのテストだけを指定して回せると往復が速くなるので、ファイル指定・テスト名指定の書き方を宣言ファイルかテスト設定から写す。写せる形が無ければスイート全体を回すコマンドを書き、絞り込めなかったことを 1 行添える。

「特定できず」と書いてよいのは、一覧を実際に見て宣言ファイルが 1 つも無かったときだけ。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・エラーは一次情報で、「この書き換えは等価なはず」という自分の推論より優先する。食い違ったら捨てるのは推論のほう
- 落ちたら、まず戻す案を出す。リファクタの目的は振る舞いを保つことなので、赤が出た時点でその書き換えは目的を果たしていない。追加の書き換えで緑に戻そうとしない
- 落ちた原因が「守るテストの側が古い振る舞いを固定していた」場合でも、テストを書き換えて緑にしない。それは仕様変更で、判断する権限は人間にあるので、問いを 1 つ立てて返す
- 直したら同じ形で返す（往復のたびに書式を変えない）

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- 振る舞いを変えてよい（バグ修正なら quick-code、原因不明なら quick-debug）
- 依頼の中心が性能改善（数値が動くことが目的なので等価ではない。quick-debug へ回す）
- 対象範囲の分割・依存の可視化そのものが済んでいない（refactor-prep が先）

デッドコード排除・可読性改善・レビューまで通しでほしい場合は /refactor を使う。
