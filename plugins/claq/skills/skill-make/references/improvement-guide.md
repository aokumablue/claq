# スキル改善ガイド

`skill-make` のスキル改善と高度な機能の詳細。

## 改善の考え方

1. フィードバックを一般化する
   - 何度でも使えるスキルを作る。数個の例で速く回しても、その例だけに最適化されたスキルには価値が無い
   - きつすぎる MUST や過剰に狭い制約より、別の比喩や別のやり方を示すほうが効くことがある
2. プロンプトを軽く保つ
   - 効いていない説明は削る
   - 最終出力だけでなくトランスクリプトも見て、モデルが無駄な作業をしていれば、その原因になっている指示を減らす
3. なぜを説明する
   - 何をさせるかだけでなく、なぜ必要かも書く。良い足場があれば、モデルは手順以上のことができる
   - 大文字の ALWAYS/NEVER ばかりになるのは黄色信号。理由を説明して自然な文に書き換える
4. テストケース間の重複を探す
   - 複数の実行で同じヘルパースクリプトや同じ多段手順が繰り返されていないかを見る
   - 3 つとも `create_docx.py` や `build_chart.py` を作っているなら、そのスクリプトはスキルに同梱したほうがよい。一度書いてスキルの `scripts/` に置けば毎回の再発明を防げる

## 反復ループ

改善後は次を繰り返す。

1. 変更をスキルに反映する
2. すべてのテストケースを新しい `iteration-<N+1>/` で再実行する（ベースラインも含む）
3. `benchmark.json` / `grading.json` を読んで結果を分析する
4. 新しい改善点を抽出して、さらに改善する

止める条件:

- フィードバックがすべて空になった
- これ以上有意な進展が無い

ユーザーが満足したかは、結果を受け取った呼び出し元（`/skill-gen`）で確かめる（fork の中からはユーザーに問えない）。

## 上級編: 盲検比較

スキルの 2 版をより厳密に比べたいときは、盲検比較を使える（`../../../agents/comparator.md` と `../../../agents/bench-analyzer.md`）。どちらがどちらかを明かさずに 2 つの出力を独立したエージェントに渡して品質を判定させ、その勝因を分析する。サブエージェントが要り、多くの場合は人間によるレビューのループで足りる。

## 説明文の最適化

SKILL.md の前置きの `description` は、Claude がスキルを呼ぶかどうかを左右する主要因である。作成・改善の後、トリガー精度を上げるための最適化を提案する。train/holdout で過適合を避ける収束判断の考え方は `skill-tune`（Step 7 の hold-out 過適合チェック）に従う。

### 1. トリガー用 eval クエリを作る

`should_trigger` の true/false を混ぜた 20 件を JSON で保存する。should-trigger は 8〜10 件（同じ意図の別表現を広く）、should-not-trigger も 8〜10 件（近いが別のタスクが必要なもの）。クエリは実際のユーザーが打つ具体的な例にする（パス・列名・会社名・URL などの背景付き。小文字・略語・タイポ・口語も可。長さにばらつきを持たせ、エッジケースを重視する）。

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

### 2. 候補を手動で反復評価する

eval セットを train 60% / holdout 40% に手で分け、description の候補ごとに train 側で `should_trigger` の判定精度を確かめ、holdout 側で過適合していないかを確かめる。

### 3. 結果を反映する

holdout のスコアが最も良かった description を採用し、SKILL.md の frontmatter を更新する。
