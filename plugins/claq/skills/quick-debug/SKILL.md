# 即時ハンドオフ切り分け

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | 仮説を並べる / 仮説を落とす観測を計装として適用する / 観測の読み方を渡す / 返ってきた観測で仮説を落とす |
| 人間 | 再現する / 走らせる / ログと数値を貼り戻す / 本番や手元でしか見えない事実を持ち込む |

このモードは切り分けを省くのではなく、観測を人間の手に移す。省くのは「自分で走らせて自分でログを見る」工程だけである。

## ルール1: 確かめるためのコマンドを自分で実行しない

やらないこと — 原因を確かめるために次を実行すること。

- 再現手順の実行・対象プログラムの試走
- テストスイートの実行 / ビルド / コンパイル
- プロファイラ・ベンチマークの採取
- リンタ / 型検査

やること — 読解は制限しない。スタックトレースの追跡、該当行の読み取り、呼び出し元の全探索、同種の既存バグの検索は続け、むしろ増やす。走らせずに正しい仮説を立てる手段は現物の読解しかない。抑えるのは実行であって調査ではない。

例外 — 人間が明示的に実行を頼んだら従う。実行しても返し方は変えず、結果は「実行済み」行に入れる。抑えているのは頼まれていない自己検証である。

## ルール2: 修正を当てない。入れるのは観測

quick-code は最も確率の高い修正をすぐ適用するが、このモードでは適用しない。原因が確定する前に修正を当てると、当たればなぜ直ったか分からないまま直り（同じバグが別の形で戻る）、外れれば元の症状に自分の変更が重なって切り分けが難しくなる。

適用するのは観測である: ログ行、assert、仮説を写した失敗するテスト、区間タイマ。これらは差分として適用済みで返せて、人間の 1 回の実行で仮説が落ちる。提案で終わらせず、計装を入れた状態で返す（人間はコピペ要員ではない）。

計装は消せる形で入れる。1 か所にまとめ、消す行をハンドオフに書く（調査後に人間が探し回ることになる計装は汚染である）。

## ルール3: 仮説は絞らず並べる

quick-code は候補が複数あれば一番ありそうな 1 つを書くが、このモードでは落とせていない仮説を消さない。読んだだけで消えた仮説は挙げなくてよいが、実行しないと決まらない仮説を「たぶん違う」で消すのは切り分けではなく省略である。

- 並べる仮説は 3 件まで。4 件以上残るなら消さずに、1 回の観測で真偽が分かれる単位（経路の前半／後半など）へ束ねる
- 各仮説に「これが真なら観測はこう出る」を添える（これが無い仮説は、観測が返ってきても落とせない）
- 再現していない症状には仮説を立てず、再現手順の確定を先に人間へ返す

## ルール4: 1 回の実行で最も多く落ちる観測を 1 つ選ぶ

仮説ごとに計装を撒かない。3 件の仮説に 3 か所のログを入れると、人間は 3 行を貼り戻すうえ、1 回の実行で全経路が通るとは限らない。

選ぶのは、真でも偽でも仮説が減る観測である。経路の中間点を 1 つ測り、前半なら A と B が落ち、後半なら C が落ちる、という形に組む。どちらに転んでも減らない観測は入れない。

## ルール5: 観測が数値のとき

症状が「遅い / 重い / メモリを食う」なら、仮説は「どこが支配的か」の形になり、観測は真偽ではなく内訳（区間タイマ、呼び出し回数のカウンタ、プロファイラの出力）になる。

ベースラインが返ってくる前に最適化を当てない。測らずに入れた最適化は、効いたのか効かなかったのか別の何かが変わったのかを区別できない。数値の仮説が落ちるのは前後 2 つの数値が揃ったときだけで、「速くなったはず」は観測ではない。内訳が返ってきたら占有率の小さい仮説から落とし、支配的な 1 件に絞るまで最適化の差分は出さない。

## ルール6: 解説は仮説と観測だけ

書くもの: 何を疑っているか、何を見れば決まるか。

書かないもの: 症状の言い換え（人間は自分が踏んだ症状を知っている）、読んだコードの説明・一般的なデバッグ手法の解説、落とした仮説の詳細な検討過程（落ちたことと根拠の 1 行で足りる）、前置き・締めの挨拶。

## 制御を返すときの形

毎回この構造と順番で返す。

```text
残っている仮説:
- <仮説。1行> / 真なら: <観測がどう出るか。1行>
- <仮説。1行> / 真なら: <観測がどう出るか。1行>

落とした仮説: <落ちた仮説と、落とした根拠。読解で落ちたのか観測で落ちたのかを書く。無ければ「なし」>

入れた観測:
- <ファイルパス>: <何を出す計装か。1行>

消し方: <調査後に消す行。ファイルパスと目印。計装を入れていなければ「計装なし」>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと結果を1行。頼まれていなければ行ごと省く>

次に実行: <そのまま貼れるコマンド1行。再現手順が宣言ファイルから読めないなら人間の再現手順をそのまま書く>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  読み方: <出力のどこを見ると、どの仮説が落ちるか>
  貼り戻すもの: <出力のどの部分が要るか。全文か、特定の行か>
```

「落とした仮説」「消し方」はブロックごと省かず、該当が無ければ「なし」と 1 行書く（ブロックが消えると、無かったのか書き忘れたのかを区別できない）。「次に実行」「読み方」「貼り戻すもの」の無いハンドオフは失敗である。何を叩き、出力の何を見て、何を貼ればよいかが分からなければ、往復はそこで止まる。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る（パッケージ定義のスクリプト欄、タスクランナーの設定、テスト設定ファイル、CI の定義、リポジトリの開発手順書）。

書く前にリポジトリ直下のファイル一覧を見て、宣言ファイルを実際に開き、そこにある文字列をそのまま渡す。この種の宣言はほぼルートにあり、スタックトレースを追ってソースを読んでいるだけでは目に入らない。

ログの出し方も同じに扱う。ログレベルの上げ方・詳細出力のフラグ・プロファイラの起動方法は、言語の一般論ではなくプロジェクトの設定（ロギング設定・起動スクリプト・開発手順書）に書かれた形を写す。写せる形が無ければ、素の実行コマンドに「この出力が見えるはず」を添える。

「特定できず」と書いてよいのは、一覧を実際に見て宣言ファイルが 1 つも無かったときだけ。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・スタックトレース・数値は一次情報で、「このコードはこう動くはず」という自分の推論より優先する。食い違ったら捨てるのは推論のほう
- まず仮説を落とす。観測と食い違う仮説を残したまま次の計装を足さない
- 修正へ進んでよいのは、人間の観測で仮説が 1 件だけ残ったときに限る。そのときは quick-code の形（変更 / 意図 / 前提 / 次に実行）で返す（観測が仮説を 1 つに落とした時点で、その修正はもう推測ではない）。2 件以上残っていれば次の観測を出し、「たぶんこれだろう」で修正へ渡らない
- 観測がどの仮説とも合わなければ、仮説の立て方を変える（同じ前提のまま計装を細かくしても落ちない）。何を誤解していたかを 1〜2 行で述べ、仮説を作り直して返す
- 直したら同じ形で返す（往復のたびに書式を変えない）

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- 原因が既に分かっていて、修正だけが要る（quick-code）
- 振る舞いを変えずに構造だけ整えたい（quick-refactor）
- 症状が再現しておらず、再現条件の特定そのものが依頼の中心にある

再現から修正・回帰防止・レビューまで通しでほしい場合は /bugfix を使う。
