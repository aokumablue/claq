## ツールは問いから決める

利用者が実際に聞く問いを先に集め、問いに答えるのに要るツールだけを置く。上流の
API やエンドポイントごとに 1 ツールにしない（モデルが API の結合と取捨を担わされ、
呼び出し回数と誤りが増える）。上流の API を包むサーバでは、さらに 10〜30 件の問いのカタログを作る（SKILL.md 手順1）。

読み取り系のツールは次の類型から選ぶ。

| 類型 | 名前の型 | 役割 | 既定の応答 |
|---|---|---|---|
| 解決 | `<resource>_search` | 曖昧な語・条件から候補と ID を返す | 候補 10 件の要約（ID・人が読めるラベル・識別に要る数項目） |
| 取得 | `<resource>_get` | ID で 1 件を返す | 主要な項目（summary ビュー） |
| 下位コレクション | `<child>_list` | 大きな入れ子の配列（明細など）をページングで辿る | 20 件 |
| 集計 | `<resource>_aggregate` | 件数・合計・内訳をサーバで計算する | 集計表だけ |
| 文脈合成 | `<subject>_context_get` | 複数の上流の関連データを 1 回で束ねる | 各部の要約 |
| 項目辞書 | `fields_describe` | 項目のパス・型・意味・機微区分を返す | 一致した項目だけ |

件数や合計を問う問いには集計ツールを用意する（数千件をモデルに読ませて数えさせない）。

## ツールの数とツールセット（MCP 2026-07-28）

- 既定で公開するツールは 10 以下にする（`smoke_config.MAX_TOOLS`）。定義が大きいと
  毎回の文脈を占め、ツールの選択も誤りやすくなる。
- 超えるときはツールセットに分け、デプロイの設定かトークンのスコープで有効にする。
  `tools/list` は接続ごとや他のリクエストの副作用で変えてはならず、認可によってだけ
  変えてよい（仕様）。
- 実行時にツールセットを切り替えるツールは作らない（副作用で一覧が変わり仕様に反する）。
- サーバ側で `search_tools` と汎用の `call_tool` を組み合わせた振り分けを作らない
  （個々のツールのスキーマと注釈がホストから見えず、確認・検索・型生成が働かない）。

## 名前

- `<resource>_<verb>`（例: `orders_search`）。英小文字・数字・`_` だけで、40 文字以内。
- `.` と `-` を使わない（ホストがツールの完全名で置き換える。仕様上は許されている）。
- `get_entity` / `search_items` のような汎用の名前にしない。何を返すかが名前で分かるようにする。

## 説明文

`@mcp.tool(description=...)` で書く。省くと docstring の全文（`Args:` や実装の注記）が
そのまま説明になる。docstring は開発者向けに別に書く。

```text
<何を返すかを 1 文で>。
使う場面: <どんな問いのときに使うか>。
使わない場面: <代わりに使うツールとその条件>。
主な引数: <引数名 = 意味（単位・書式）>。
応答: 既定 <件数またはビュー>、最大 <件数>。続きは next_cursor を cursor に渡す。
```

- 内部用語・上流の API 名・コード値を書かない。
- 説明は静的な文字列にし、上流のデータから組み立てない（説明の汚染を防ぐ）。

## 引数

| 規則 | 理由 |
|---|---|
| 引数は平坦に並べ、入れ子のモデルを引数にしない（期間は `ordered_from` / `ordered_to`） | 入れ子のモデルは公開スキーマに `$defs` / `$ref` を出し、ホストによってはモデルへの見え方が崩れる。smoke が落とす |
| 省略可能な引数は `X \| None = None` で書いてよい | 公開スキーマの `anyOf` は guard が外す。受け付ける範囲は SDK が元の型で検証する |
| 閉じた集合は `Literal`（`enum` になる）。数百を超える動的な集合は `str` で受けてサーバで検証し、解決用のツールを置く | 定義の肥大化と、スキーマの陳腐化を避ける |
| 範囲・長さ・件数に `Field(ge=, le=, min_length=, max_length=)` で上限を付ける | 過大な要求を入口で止め、モデルが呼ぶ前に範囲を知れる |
| 名前に意味と単位を入れる（`customer_id`・`amount_min_jpy`・`period_days`） | `user` より `user_id` のほうが誤用が減る |
| 日付は `pattern` で `YYYY-MM-DD` を強制し、実在する日付かはサーバで検証する。範囲の両端を含むかとタイムゾーンを説明に書く | JSON Schema 2020-12 の `format` は既定で検証されない |
| 例は `Field(examples=[...])` と説明文の両方に書く | MCP のツール定義に例専用の欄は無く、ホストが `examples` をモデルに見せるかは不定 |
| 自然な検索語は `*_search`、ID は `*_get` で受ける。1 つの引数に混ぜない | 責務が混ざると、モデルが ID を検索語として送る |
| 引数の名前を変えない（変えるなら新しいツールにする） | 未知の引数は guard が拒否するので、古い呼び方は失敗になる |
| `x-mcp-header` を使わない（ゲートウェイの振り分けに要る、機微でない値だけを例外とする） | ヘッダは中間装置から見える |

制約は型注釈で宣言する（自前の `if` では公開スキーマに載らず、モデルが呼ぶ前に範囲を知れない）。

| 制約 | 書き方 | 公開スキーマ |
|---|---|---|
| 数値範囲 | `Annotated[int, Field(ge=1, le=100)]` | `minimum` / `maximum` |
| 選択肢 | `Literal["dev", "prod"]` | `enum` |
| 文字列書式 | `Annotated[str, Field(pattern=...)]` | `pattern` |
| 文字列長 | `Annotated[str, Field(min_length=1, max_length=200)]` | `minLength` / `maxLength` |
| 件数 | `Annotated[list[str], Field(max_length=5)]` | `maxItems` |
| 例 | `Annotated[str, Field(examples=["..."])]` | `examples` |

## 出力

- 戻り値の型を pydantic のモデルで書く（`outputSchema` が生成され、ホストの code mode が型として使う）。
- 出力のモデルは閉じない。増えうる値（状態など）は `Literal` にせず、`str` と説明で示す
  （出力スキーマを閉じると、値や項目を足したときにキャッシュした古いスキーマでの検証が落ちる）。
- 値が無い項目を出さないなら `Field(default=None, exclude_if=lambda value: value is None)`、
  空の一覧を出さないなら `exclude_if=lambda value: not value`（SDK は None を null で出す）。
- 一覧の結果は `items`・`has_more`・`next_cursor`・`as_of`・`notes` を持たせる。
  部分失敗は `partial`、切り詰めは `notes` に書く。
- 機械用の ID と人が読めるラベルを並べる。金額は `amount` と `currency` の組、日時は
  ISO 8601 とオフセット。
- text は structuredContent の写しを guard が詰めた JSON にする。自分で text を組み立てない。

## 失敗（MCP 2026-07-28 / mcp 2.3.0 実測）

| 起きたこと | 返し方 |
|---|---|
| 未知のツール | SDK が `isError: true` のツール実行エラー（`Unknown tool: <名前>`）で返す（自分では作らない。mcp 2.1.1 で実測。2.3.0 では未確認） |
| 形が壊れたリクエスト（`name` が無い・型が違う） | SDK が JSON-RPC error（`-32602`）を返す（自分では作らない） |
| 未知の引数 | guard が `isError` で名指しする |
| 型・範囲の違反 | SDK が `isError` で検証の文面を返す |
| 業務上の失敗（見つからない・条件が無い・期間が逆） | `ToolError` で、何が悪いか・正しい形・次に使うツールを書く |
| 上流の失敗 | `ToolError` で、時間を置くか条件を絞るかを行動の形で書く。上流の詳細はログにだけ出す |

- `ToolError`（`from mcp.server.mcpserver.exceptions import ToolError`）で投げる。素の例外
  （`ValueError` など）は文面が伏せられ、モデルには `Error executing tool <name>` しか届かない。
  ツール本体から投げた `MCPError` は、ツール実行エラーではなく JSON-RPC error（文面はそのまま）
  になる。どちらもツール本体では使わない。
- 権限の無い ID と存在しない ID は区別せず「見つからないか、閲覧の権限がありません」と返す（存在を漏らさない）。
- スタックトレース・上流の URL やホスト名・SQL・秘密を文面に入れない。

## 注釈（MCP 2026-07-28）

- 読み取り専用: `ToolAnnotations(readOnlyHint=True, openWorldHint=False)`。外部の
  開かれたコンテンツ（Web 検索など）を返すなら `openWorldHint=True`。
- 書き込み: `readOnlyHint=False` と、`destructiveHint`（上書き・削除するか）・
  `idempotentHint`（同じ引数で繰り返しても結果が変わらないか）。この 2 つは
  `readOnlyHint=False` のときにだけ意味を持つ。
- 注釈は信頼されないヒントである。読み取り専用は上流の資格情報のスコープで保証する。

## 状態

- 接続やプロセスを会話とみなさない。呼び出しをまたぐ状態は、ツールが返した識別子を
  次の呼び出しの引数で受け取る。
- 認可の文脈を運ぶハンドル（カーソル・ジョブ）は、推測できない値にし、主体に結びつけ、
  有効期限を付け、期限を説明に書く。期限切れは次の行動を書いた `ToolError` にする。
- ドメイン上の識別子（注文番号など）は普通の ID でよい（取り違えると要件違反を作り込む）。

## モデルへ使い方を伝える経路

優先順に、ツールの説明 → 引数の説明と例 → `instructions` → 結果の `notes` とエラー文。
守らせたい不変条件（読み取り専用・主体の範囲・件数の上限）は文章に頼らず、コードで強制する。

- `instructions`（`MCPServer(instructions=...)`）: ツールをまたぐ流れ・ID の規約・データの
  鮮度・上限だけを短く書く。ツールの説明を繰り返さない。ホストが文脈へ入れるとは限らない。
- Prompts: 利用者が選んで起動する定型作業にだけ使う（モデルは自分では選ばない）。
- Resources: コア機能を載せない（文脈へ入れるかはホストが決める）。
- Skills 拡張: 長い業務手順を配るのに使えるが、対応するホストが限られるのでコアにしない。
