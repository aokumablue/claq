# リモート配置の認可とデータの守り方

Streamable HTTP で複数の利用者に公開するサーバの規則。stdio のサーバは認可仕様の対象外で、
資格情報は環境変数（または OS のキーチェーン）から取る。

スケルトンの HTTP に認証は無い。ループバック以外へ公開するのは、認可を実装してから
にする（スケルトンの `transport.py` は、ループバック以外の `--host` を起動時に拒否する）。

OAuth の実装はスケルトンの範囲外である。SDK の認可機能（`token_verifier` など）は
このスキルでは実測していないので、使う前に SDK のドキュメント
（<https://py.sdk.modelcontextprotocol.io/>）と仕様
（<https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization>）を読み、
smoke に 401 / 403 の検査を足してから使う。

## 仕様上の要件（MCP 2026-07-28 認可）

| 要件 | 種別 |
|---|---|
| MCP サーバは OAuth 2.1 のリソースサーバとして振る舞う | 仕様 |
| Protected Resource Metadata（RFC 9728）を公開する | MUST |
| アクセストークンが自分（このサーバの正規の URI）宛に発行されたことを検証する。無効・期限切れには 401 | MUST |
| 自分宛でないトークンを受け入れない。受け取ったトークンを他へ通さない | MUST NOT |
| スコープ不足には 403 と `WWW-Authenticate: Bearer error="insufficient_scope", scope="..."` を返し、その操作に要るスコープを 1 回でまとめて示す | SHOULD |
| `Origin` を検証し、不正なら 403 | MUST |
| `clientInfo` は自己申告なので、セキュリティの判断に使わない | SHOULD NOT |

本番は HTTPS で公開する。クライアントの登録方式（Client ID Metadata Documents を推奨、
動的登録は非推奨）はクライアントと認可サーバの間の話で、サーバは PRM で認可サーバの
場所を示せばよい。

## スコープ

- 初期のスコープは最小（基本の読み取り）にし、機微な項目などは要るときに段階的に要求させる。
- `scopes_supported` に全てのスコープを並べない。ワイルドカードのスコープを作らない。
- `tools/list` をスコープで絞ってよい。主体や認可で内容が変わる応答すべて（`tools/list` と
  `resources/read` を含む）は、`cache_hints` を `scope="private"` にする（`"public"` だと
  別の利用者へ使い回される）。

## 上流の資格情報

- 上流 API には、上流の認可サーバが発行した別のトークンを使う。MCP クライアントから
  受け取ったトークンを上流へ渡さない（仕様が禁じるトークンパススルー）。
- 取り方の優先順:
  1. ユーザー委任: 上流が対応していれば、利用者の権限を保ったまま上流用のトークンを得る
     （OAuth 2.0 Token Exchange（RFC 8693）や IdP の on-behalf-of）。上流の認可がそのまま効く。
  2. サービス資格情報とサーバ側の認可: 上流が委任に対応しなければ、読み取り専用の
     サービス資格情報を使い、主体ごとの行・項目の認可をサーバで実装する。サーバが認可の
     唯一の砦になるので、ポリシーをコードとして書き、主体の越境を試すテストを置く。
- 上流の資格情報はシークレット管理から取り、短命にしてローテーションする。ツールの
  結果・エラー・ログに出さない。
- 静的なクライアント ID で第三者の認可サーバへ OAuth を中継する構成（MCP プロキシ）では、
  動的に登録されたクライアントごとに、第三者の認可へ進む前に利用者の同意を取る（仕様の MUST）。

## 主体とデータ層の認可

- 主体（利用者・テナント）は検証済みのトークンから導き、ツールの引数からは取らない。
  主体のキーは発行者（`iss`）と主体（`sub`）の組にする（`sub` は発行者の中でしか一意でない）。
  テナントで分けるなら、テナントも組に加える。
  facade-overlay の `_principal()` と `_allowed_sensitivity()` を、トークンの主体と
  スコープから導く実装に置き換える。
- 行: 主体が見てよいレコードだけを返す。委任トークンなら上流に任せ、サービス資格情報なら
  サーバで絞る。
- 項目: `FieldSpec.sensitivity`（必須）で区分する。個人情報（`personal`）の項目はビューに
  入れられない（`Catalog` が定義の時点で拒否する）。個人情報は `fields` で明示され、かつ
  スコープがあるときだけ返す。ビューも許された区分で絞る。
- カーソル・ジョブのハンドルは主体に結びつける（facade の `CursorCodec` は、主体・検索条件の
  指紋・ツール名を署名の入力で結びつける）。
- 機微な項目を返したら、主体・ツール・項目・件数を監査ログに残す（値は残さない）。
  facade-overlay の `server.py` は `audit` logger に、個人情報の項目を返したときと
  cursor を拒否したときを、主体の鍵付きの要約で記録する。

## 複数インスタンス

- 全インスタンスで `MCPServer(...)` の名前をそろえる。
- facade のカーソルの鍵 `FACADE_CURSOR_SECRET` を全インスタンスで共有する。
- MRTR を使うなら `RequestStateSecurity(keys=[32 バイトの共有鍵])` を渡す（既定はプロセス
  ごとの鍵で、再送が別のワーカーに届くと復号できない）。
- 認可を実装したうえで実ホスト名で公開するときは、`transport.py` の公開してよいホストと
  `TransportSecuritySettings` を配置に合わせて書き換える（裸のホスト名とポート付きの両方を
  許可リストに入れる。漏れると全リクエストが 421）。リバースプロキシが Host / Origin を
  検証するなら、DNS リバインディング対策をそちらに任せる。
