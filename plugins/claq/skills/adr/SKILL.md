# アーキテクチャ決定記録

## 記録か提案か

- 明示の依頼・決定（「ADRにして」「この決定を記録」「X を採用しよう」「Y ではなく X を使うべき」）→ ワークフローへ進む
- 暗黙の決定（比較の結論、DB スキーマ・アーキテクチャパターンの選択）→ 記録を 1 行で提案するだけにし、ファイルは作らない

## ADR フォーマット

```md
## [決定タイトル]

[状況を 1-2 文]。**[決定を 1-3 文の命令形]**。[決定が成り立つ理由・境界条件を、別案を
却下する根拠として 1-3 文]。必要なら箇条書きで適用範囲・具体的な数値・既知の残存リスクを
続ける。
```

現行の状態と、現在も有効な判断基準だけを書く。経緯・改訂履歴・バージョン番号・採番 ID は書かない。「代替案 X を検討したが却下した」という経緯の形は採らず、別案への現行の回答は決定文の中に理由として織り込む。他のトピックファイルへの参照は作らず、前提が要るなら自分の言葉でその節に書く。

## ワークフロー

1. 初回だけ: `docs/adr/` ディレクトリ・インデックス（`README.md`）・テンプレートを作る（判断を含まないので確認は挟まない）
2. 決定を特定し、コンテキストを集め、現行の判断基準として書く
3. 書き込み先のトピックファイルを決めてドラフトを示し、明示的な承認を得てから書き込む（ADR は以後の判断の根拠になる永続的な記録なので、誤った ADR は以後の判断を汚す。ここは意図した停止点）
4. 扱う問いに最も近いトピックファイルへ追記する。どのトピックにも属さないときだけ、新しいトピックファイル（連番なしの `<slug>.md`）を作り、`docs/adr/README.md` の「トピック」表に 1 行足す

書き込んだ結果は次を満たすようにする: README のトピック表とディスク上のファイルが一致する / 各トピックファイルに「共通原則」と決定の節がある / 他のトピックファイル名に言及しない。

既存の決定を撤回するときは、本文を現行の規則へ書き換え、撤回前の記述は残さない。

## ディレクトリ構造

1 決定 = 1 ファイルではない。役割（トピック）ごとの 1 ファイルに、h2 見出しの節として収める。ファイル名に連番は振らない。繰り返される前提は各ファイル冒頭の「共通原則」に自分の言葉で書く（他ファイルの共通原則と文言が重なってもよい。参照では済ませない）。

```
docs/adr/
├── README.md    ← インデックス（トピック表）
├── <slug>.md    ← トピックファイル（h2 見出しの決定節を複数持つ。他ファイルへの参照は無し）
└── template.md
```

## 永続メモリ

- search: `claq_run claq.mem.cli search "..."`（`. "$HOME/.claq/env.sh"` 前提）— クエリ例 `ADR architecture decision {topic}` / `{technology} vs alternative decision`。返るのは `- [kind] title (key)` の 1 行だけなので、本文が要る key だけ `claq_run claq.mem.cli show <key>` に渡す
- record: 再利用可能な学びだけ `claq_mem_learn` で登録する。基準は `../learn/SKILL.md` の「記録する / しない」
