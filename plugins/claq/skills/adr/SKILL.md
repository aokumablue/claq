# アーキテクチャ決定記録

## 発動タイミング

- 「ADRにして」「この決定を記録」
- 重要な選択肢間で選択（フレームワーク/ライブラリ/パターン/DB/API設計）
- 「Xすることに決めた」「YではなくXの理由は」
- 計画フェーズでアーキテクチャトレードオフが議論される

## ADR フォーマット

```md
## [決定タイトル]

[状況を 1-2 文]。**[決定を 1-3 文の命令形]**。[決定が成り立つ理由・境界条件を、別案を
却下する根拠として 1-3 文]。必要なら箇条書きで適用範囲・具体的な数値・既知の残存リスクを
続ける。
```

現行の状態と、現在も有効な判断基準だけを書く。経緯・改訂履歴・バージョン番号・採番 ID は
書かない。「代替案 X を検討したが却下した」という経緯の形は採らず、別案への現行の回答は
決定文そのものの中に理由として織り込む。他のトピックファイルへの参照は作らない——前提が
要るなら自分の言葉でこの節に書く。

## ワークフロー

1. **初回のみ**: `docs/adr/` ディレクトリ・インデックス(`README.md`)・テンプレート作成（判断を含まないため確認は挟まない）
2. 決定特定→コンテキスト収集→現行の判断基準として記述
3. 書き込み先トピックファイルを決める→ドラフト提示→**明示的承認後のみ**書き込み（ADR は永続的な意思決定記録であり、誤った ADR は以後の全判断を汚染する。設計判断の論拠は ADR に置く以上、その ADR が自動生成物であってはならない。意図して残している停止点）
4. 扱う問いに最も近いトピックファイルへ追記する。どのトピックにも属さないときだけ新規
   トピックファイル（連番なしの `<slug>.md`）を作り、`docs/adr/README.md` の「トピック」表に
   1 行追加する
5. 書き込み後に、README のトピック表とディスク上のファイルが一致すること・「共通原則」と
   決定節が空でないこと・他のトピックファイル名へ言及していないことを確認する。未確認は
   『未検証』と明示

既存の決定を撤回する場合は現行の規則へ本文を書き換え、撤回前の記述は残さない。

## ディレクトリ構造

**1 決定 = 1 ファイルではない。** 役割（トピック）ごとの 1 ファイルに、h2 見出しの節として
収める。ファイル名に連番は振らない。繰り返される前提は各ファイル冒頭の「共通原則」に自分の
言葉で書く（他ファイルの共通原則と文言が重複してもよい。参照では済ませない）。

```
docs/adr/
├── README.md    ← インデックス（トピック表）
├── <slug>.md    ← トピックファイル（h2 見出しの決定節を複数持つ。他ファイルへの参照は無し）
└── template.md
```

## 決定検出シグナル

**明示的**: "Xを採用しよう" / "YではなくXを使うべき" / "これをADRとして記録"

**暗黙的**（提案のみ・自動作成しない）: フレームワーク比較→結論 / DBスキーマ設計選択 / アーキテクチャパターン選択

## 永続メモリ

search: `claq_run claq.mem.cli search "..."`（`. "$HOME/.claq/env.sh"` 前提）— クエリ例 `ADR architecture decision {topic}` / `{technology} vs alternative decision`。返るのは `- [kind] title (key)` の 1 行だけなので、本文が要る key だけ `claq_run claq.mem.cli show <key>` に渡す
record: 再利用可能な学びだけ `claq_mem_learn` で登録する。基準は `../learn/SKILL.md` の「記録する / しない」
