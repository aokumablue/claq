# 機能開発フロー

新機能を発見から納品サマリーまで順に進める。実装は loop-dev skill に委ねる。

## 停止点

ユーザーの応答を待つのは、grillme の質問とステップ2 の分岐確認だけ。それ以外では、次の手順を予告して終わる要約・続けてよいかの伺い・作業を止めない判断事項の列挙・区切りや長さを理由にした報告で応答を終えず、次のステップへ進む。報告や未決事項への推奨は次のツール呼び出しと同じ応答に書く。

## grillme（条件付き）

要件が曖昧で複数の読み方が成立するときだけ、開始直後に grillme スキルで共通理解を固める。依頼が明確なら省いて着手する。起動したら完了まで他の処理に進まず、合意した方針を 1 行で書き留めてから次へ進む（ここで再確認は求めない）。

## 永続メモリ

- 参照: SessionStart が `<claq-memory>`（`status='active'` の知識）を注入済み。追加で要るときは `. "$HOME/.claq/env.sh"` のあと `claq_run claq.mem.cli search "..."`（クエリ例 `feat-dev workflow {feature}` / `phase blocker feature`）→ 本文が要る key だけ `claq_run claq.mem.cli show <key>`
- 記録: ステップ4 の基準で `claq_mem_learn` を使う

## ステップ1: 発見 + 探索

要求を抽出し、成功条件を明確にする（曖昧さが残れば、ここでは止まらずステップ2 の分岐確認でまとめて聞く）。そのうえで、既存構造・命名規約・類似実装・影響範囲・依存・現行テストの実態を、依頼に書かれていない関連箇所（呼び出し元・設定・既存テスト）も含めて調べてから着手する。数回の読み取りと検索で終わる規模なら自分で読む。広い範囲を調べるときだけ Explore agent に委ね、1 回の調査で洗い出させる（breadth は調査範囲に応じて `medium`〜`very thorough`）。複数を並列起動するのは、対象領域が明確に独立していて並列化の価値がある大規模調査のときだけ。

探索で得た情報は再取得しない。

## ステップ2: 残分岐確認

grillme を起動した場合はその結果を、省いた場合は依頼時点の要件を前提にする。探索で新たに生じた分岐だけを、推奨回答付きで確認する。新しい分岐が無ければ本ステップは省く。

## ステップ3: loop-dev 反復実装

Skill ツールで `loop-dev` skill を起動し、plan→generate→evaluate を最大 2 反復で収束させる。入力:

- `task` = 合意済み要件
- `task_type` = `feature`
- `converge_extra` = ステップ1 の成功条件から導く

loop-dev の収束または停止の報告を受け取ったら次へ進む。

## ステップ4: 学びの記録（毎回実行・記録は該当時のみ）

探索で「調べないと分からなかった」ことと実装中に選んだ設計は、次に同じ領域を触るときの探索コストを削る。サマリーの前に残す。

| 見つけたもの | kind | title に書くこと |
|---|---|---|
| 探索に 2 手以上かかったエントリポイント・呼び出し関係 | `fact` | 事実そのもの（「hook は launcher.py 経由で起動する」） |
| 採用した設計と却下した案 | `decision` | 選択と理由（「FTS5 を使わず Python 側で採点する」） |
| 新機能を足すときの定型手順（登録先・テスト配置・生成物） | `howto` | 手順の目的 |
| 実装中に踏んだ環境・ビルド・テストの罠 | `pitfall` | 回避条件 |
| 既存コードから読み取った、明文化されていない規約 | `convention` | 守るべきルール |

記録しないもの: 機能仕様そのもの（コードと README が正。二重管理すると食い違う）、リポジトリを読めば分かること、進捗・作業ログ（SessionEnd の `handoff` が残す）、探索の過程（分かった結論だけを書く）、そのセッション限りの事情。

```bash
. "$HOME/.claq/env.sh" || exit 127
claq_mem_learn --kind fact --scope repo --domain <domain> \
  --title "<分かった結論を 1 行で>" \
  --body "<根拠と、次に同じ領域を触るときの入口>"
```

該当が無ければ 1 件も記録しない（0 件は正しい結果）。登録は常に `status=pending` になり、採否は `/instinct` のレビューで決まる。重複確認とシークレットのマスクは `../skills/learn/SKILL.md` に従う。

## ステップ5: サマリー

変更ファイル・追加テスト・残課題を一覧にし、loop-dev の箱形出力（Loop-Dev Result）を転記する。報告は loop-dev の箱形出力などの一次証跡だけに基づけ、未確認の事項を完了として書かない。

```
### 変更ファイル
- path — 変更内容

### 追加テスト
- path:fn — カバー範囲

### 残課題
- ...

### 記録した知識
- key — title（ステップ4。記録が無ければ「なし」）
```

## 制約

- ステップ1 の探索を飛ばさない（飛ばすと既存パターンを見落として重複実装が生まれる）
- 新規作成より既存の拡張を優先する
- 後方互換フォールバックは置かず、古いコードは削除する

- 位置 #1: `[機能説明]`（省略時: 直前の会話文脈から要件を抽出）
