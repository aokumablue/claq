# テストコード生成フロー

## 停止点

止まるのは、ステップ2 の `BLOCKED`（テストコマンドを検出できない）と、loop-dev から戻った後の外部ライブラリの追加の確認だけ。それ以外のステップの区切りでは報告だけして応答を終えず、ステップ5 の要約まで進む（途中の報告は次のツール呼び出しと同じ応答に書く）。

## 永続メモリ

- 参照: SessionStart が `<claq-memory>`（`status='active'` の知識）を注入済み。追加で要るときは `. "$HOME/.claq/env.sh"` のあと `claq_run claq.mem.cli search "..."`（クエリ例 `test test-gen coverage decision-table {対象ファイルパス}`）→ 本文が要る key だけ `claq_run claq.mem.cli show <key>`
- 記録: 再利用可能な学びだけ `claq_mem_learn` で登録する。基準は `../skills/learn/SKILL.md` の「記録する / しない」

## ステップ1: スコープ確定

スコープは次の優先順で決める: 引数パス（ディレクトリ = 配下の全ソースファイル / ファイル = そのファイル）→ `git diff --name-only HEAD`。テストファイル自身と言語の設定ファイルは除く。

## ステップ2: プロジェクト検出 + ベースライン取得

1. プロジェクトルートのマニフェストからテストコマンドを決める。`pyproject.toml` / `setup.cfg` → `python3 -m pytest -q`、`package.json` → `scripts.test`（無ければ検出失敗）、`go.mod` → `go test ./...`、`Cargo.toml` → `cargo test`。複数当たれば対象ファイルの拡張子で選ぶ。どれにも当たらなければ推測でコマンドを組まず、`BLOCKED: テストコマンドを検出できません（探索したマニフェスト={列挙}）` として止まる
2. 言語に応じたカバレッジコマンドを選ぶ
3. 未到達のブランチを記録する
4. 既存のテスト失敗は `red_baseline` として記録して続行する（生成テストの収束判定から外れる。`../skills/loop-dev/SKILL.md` の red_baseline の扱い）

## ステップ3: デシジョンテーブル設計（ファイル単位）

対象ファイルごとに:

1. ソースコードを読み、関数・メソッドを列挙する
2. 各関数のブランチ条件（if/elif/else、例外・エラー、ループ境界、null/None/Optional）を洗い出す
3. 関数単位でデシジョンテーブルを作る

```
関数: {function_name}
──────────────────────────────────────────
| # | 条件1 | 条件2 | ... | 期待値 | 備考 |
|---|-------|-------|-----|--------|------|
| 1 | ...   | ...   | ... | ...    |      |
...
```

- ベースラインで未到達のブランチを優先してカバーする
- 最小のテスト数で 100% ブランチカバレッジを目指す
- 組み合わせが爆発するときは境界値分析で減らし、全ブランチをカバーする最小セットを選ぶ

4. 全関数のテーブルをまとめて示し、応答を待たずにステップ4へ進む

## ステップ4: loop-dev 反復実装

デシジョンテーブルの実装対象行が 0 行なら loop-dev を起動しない（ベースラインが全ブランチに到達済みで、起動しても重複テストしか生まれないため）。この場合はステップ5 へ直行し、`Iterations` に `0/2 (loop-dev 未起動: 未到達ブランチ 0)`、`Commits` に `none (変更なし)` と注記する。`Gate` は `PASS`（成果物ゼロでの正常完了）。`BLOCKED` になるのは、ステップ2 のテストコマンド検出失敗と、下の外部ライブラリ追加の確認待ちの 2 つだけ。

実装対象行が 1 行以上あれば、Skill ツールで `loop-dev` skill を起動する。`approved_plan` で plan 段を縮退させ（planner を起動しない）、generate→evaluate を最大 2 反復で収束させる。入力:

- `task` = テーブルの各行を 1 テストケースとして実装する（下の実装ルールを含めて渡す）
- `approved_plan` = 設計済みのデシジョンテーブル
- `task_type` = `test`
- `converge_extra` = 「テーブル全行実装 + カバレッジ目標。生成テストの失敗はプロダクトコードの修正で解消しない — 失敗はそのまま残してユーザーに報告する（収束条件から除外）」

task に含めて渡す実装ルール:

- 既存のテストファイルがあれば、ベースラインの未到達ブランチに対応するテストだけを追記する（重複させない）。無ければ言語の慣習に従ったパス・命名で新規作成する
- 言語標準のモック・スタブ機能を優先する（Python: unittest.mock/monkeypatch, JS: jest.mock, Go: interface-based, etc.）
- 外部ライブラリは追加しない。必要なら、そのライブラリと理由を出力の Assumptions に書き、それを要するテストは実装せずに残す（依存の追加は「テストを書く」依頼の範囲を超える永続的な変更で、fork の loop-dev からはユーザーに確認できないため）
- フィクスチャ・ヘルパーはテストファイル内のローカルに定義する。共有が必要なときだけ共有ファイルへ移す
- テスト関数名にはデシジョンテーブルの条件を反映する
- 言語に応じた linter を通るスタイルにする
- カバレッジの検証はテストファイルを個別に指定して実行する（全テストの実行は時間がかかる）

loop-dev の収束または停止の報告を受け取ったら要約へ進む。報告の Assumptions に外部ライブラリの必要が書かれていれば、要約の前にユーザーへ追加してよいかを確認する（意図した停止点）。承認されたら追加して、残したテストを実装する。

## ステップ5: 要約

```
Test Generation
──────────────────────────────
Scope:      {n} files  ({language})
Tables:     {table_count} (functions)
Tests added:{tests_added}
Coverage:   {cov_before}% → {cov_after}%
Iterations: {n}/2
Commits:    {hashes or "none (理由)"}
──────────────────────────────
Gate: PASS / BLOCKED ({reason})
```

Iterations / Commits は loop-dev の箱形出力（Loop-Dev Result）から転記する。

## 判別力の実証（保護・ゲート系テストでは必須）

壊れているものを赤くできると実証していないテストは、緑でも保護の証拠にならない。テストが通っていることは、そのテストが守りたい軸を検査していることを意味しない。

対象は、入力の同値類を列挙して守るテスト（保護フックのバイパス面・権限ゲート・バリデーション）。通常の機能テストには求めない。手順:

1. 実装へその軸だけを壊す変異を入れる（先勝ちへ戻す・別名を 1 つ足す・分岐を反転する）
2. 追加したテストが赤くなることを確かめる。赤くならなければ、そのテストはその軸を検査していない
3. 変異を戻し、緑に戻ることを確かめる
4. 赤くなった範囲が実装の到達関係と一致することも見る（無関係なテストまで赤いなら変異が広すぎる）

報告には変異の内容と赤くなったテスト名を書く。「実証した」とだけ書かない。

## ルール

- テストファイル・設定ファイルは対象外
- 重複テストを作らない（既存でカバー済みのブランチは飛ばす）
- テストの失敗を自動で直さない（仕様の不明点を示すため）
- 外部ライブラリの追加はユーザーに確認する
- 保護・ゲート系のテストは、判別力の実証まで済ませて完了とする

## 引数

- 位置 #1: `[ファイルパス or ディレクトリ]`（省略時: 変更差分のソースファイル）
