# 実装計画

## 停止点

止まるのは、grillme の質問、ステップ3 の `BLOCKED`、ステップ5 の確認待ちだけ。それ以外では、次の手順を予告して終わる要約・続けてよいかの伺い・作業を止めない判断事項の列挙・区切りや長さを理由にした報告で応答を終えず、次のステップへ進む。報告や未決事項への推奨は次のツール呼び出しと同じ応答に書く。

## grillme（条件付き）

要件が曖昧で複数の読み方が成立するときだけ、開始直後に grillme スキルで共通理解を固める。依頼が明確なら省いて着手する。起動したら完了まで他の処理に進まず、合意した方針を 1 行で書き留めてから次へ進む（ここで再確認は求めない）。

## 永続メモリ

- 参照: SessionStart が `<claq-memory>`（`status='active'` の知識）を注入済み。追加で要るときは `. "$HOME/.claq/env.sh"` のあと `claq_run claq.mem.cli search "..."`（クエリ例 `{要件のキーワード}` / `risk blocker error {関連キーワード}`）→ 本文が要る key だけ `claq_run claq.mem.cli show <key>`
- 記録: 再利用可能な学びだけ `claq_mem_learn` で登録する。基準は `../skills/learn/SKILL.md` の「記録する / しない」

## 使用タイミング

- 新機能の開始・大きなアーキテクチャ変更・複雑なリファクタリング
- 変更対象ファイルが 5 件以上のリファクタリング
- 複数ファイル・コンポーネントに影響する変更、要件が曖昧なとき

## ステップ1: 要件言い換え

ユーザー入力を「何を作るか」「なぜ作るか」「成功条件は何か」の 3 点で言い換える。言い換えは計画の冒頭に載せ、ここでは止まらない（認識のずれはステップ5 の確認でまとめて受ける）。

## ステップ2: 過去類似実装検索

`<claq-memory>` の注入内容と `claq_run claq.mem.cli search "..."` で類似作業を参照し、再利用できる既存実装・パターン・知見を拾う。

## ステップ3: リスク特定

`claq:planner` を評価モード（既定。リスクと代替案を列挙する）で起動する。要件の言い換え・手順分解・依存関係・複雑度見積もりと、アーキテクチャへの影響・技術リスク・代替設計案を一体で出させる。決定モード（単一推奨と実装ブループリント）は `/feat-dev` 等が使う。

planner の出力（要件言い換え・手順分解・依存関係・リスク・代替案）が手元に届いていることを、ステップ4へ進む条件にする。出力が無ければ「リスクなし」とは解釈せず、計画を完了扱いにしない。planner を再起動するか、起動できない理由を書いて `BLOCKED` で止まる。

## ステップ4: 段階的計画作成

次の形で提示する。

1. 要件言い換え
2. 手順分解（フェーズ別）
3. 依存関係
4. リスク評価
5. 複雑度見積もり（High/Medium/Low）
6. 変更ファイル一覧（正確なパス）
7. 変更しないファイル一覧（隣接するが対象外）
8. テストコマンド

planner 出力の Assumptions と各ステップの検証手段はそのまま載せる（定義し直さない）。計画の根拠はステップ2・3 で確認した事実だけにし、未確認の事項は Assumptions に書く。

## ステップ5: 確認待ち

ユーザーの肯定応答（「はい」「進めて」等）を受けるまでコードを書かない。この停止は中断ではなく本コマンドの完了であり、成果物は計画そのものである。

修正依頼は次の形で受け付ける。

- "修正: [変更内容]"
- "別アプローチ: [代替案]"
- "フェーズ N を飛ばしてフェーズ M を先に進める"

肯定応答を受けたら実装へ移る。

## 実装

ユーザーの承認後、Skill ツールで `loop-dev` skill を起動する。入力:

- `task` = 承認済み計画の実装要件サマリー（1〜3 文）
- `task_type` = 計画の性質に応じて `feature` | `bugfix` | `test` | `refactor-fix`
- `approved_plan` = 承認済み計画（plan 段を縮退させる。変更ファイル一覧・テストコマンドを引き継ぐ）

loop-dev の収束または停止の報告を受け取ったら、Loop-Dev Result を転記して要約を示す。
