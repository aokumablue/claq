# 実装計画

## grillme 起動（条件付き）

要件が曖昧で複数の読み方が成立するときのみ、開始直後に grillme スキルで共通理解を固める。依頼が明確なら省略して着手する。起動した場合は完了まで他処理に進まず、完了時は合意方針を1行サマリで確認する。

## 永続メモリ

- 注入: SessionStart の `mem context` が `<ple4-memory>` を自動投入（`status='active'` のみ）
- 参照: `ple4_run ple4.mem.cli search "..."`（`. "$HOME/.ple4/env.sh"` 前提。クエリ例 `{要件のキーワード}` / `risk blocker error {関連キーワード}`）→ 本文が要る key だけ `ple4_run ple4.mem.cli show <key>`
- 記録: 再利用可能な学びだけ `ple4_mem_learn` で登録する。基準は `../skills/learn/SKILL.md` の「記録する / しない」

## skill 起動メカニズム

`loop-dev` は `user-invocable: false` の skill。本文で「loop-dev skill を起動」と明示することで Skill ツール経由の fork 実行で発火する。

## 使用タイミング

- 新機能開始・大きなアーキテクチャ変更・複雑なリファクタリング
- **変更対象ファイルが5件以上のリファクタリング**
- 複数ファイル/コンポーネントに影響する変更・要件が曖昧な時

## ステップ1: 要件言い換え

ユーザー入力を「何を作るか」「なぜ作るか」「成功条件は何か」の3点で言い換え、ユーザーに認識合わせ。

## ステップ2: 過去類似実装検索

`<ple4-memory>` の注入内容と `ple4_run ple4.mem.cli search "..."` で類似作業を参照。再利用可能な既存実装・パターン・知見を抽出。

## ステップ3: リスク特定

**`ple4:planner`（評価モード）** を起動する。要件言い換え・手順分解・依存関係特定・複雑度見積もりと、アーキテクチャ影響調査・技術的リスク洗い出し・代替設計案提示を一体で行う。

planner の動作モード:
- 評価モード（既定）= リスクと代替案を列挙
- 決定モード = 単一推奨と実装ブループリントを確定（`/feat-dev` 等で使用）

**dispatch receipt を必須とする**: planner の出力（要件言い換え・手順分解・依存関係・リスク・代替案）が実際に手元にあることを、ステップ4へ進む前提とする。出力が無い場合は「リスクなし」と解釈せず、**計画を完了扱いにしない** — planner を再起動するか、起動できない理由を明示して `BLOCKED` で停止する。散文で「起動する」と書くだけでは起動されないことがある（`../skills/loop-dev/SKILL.md` の「判定行の存在を収束の前提とする」と同じ形の要求）。

## ステップ4: 段階的計画作成

統合結果を以下の形式で提示:

1. 要件言い換え
2. 手順分解（フェーズ別）
3. 依存関係特定
4. リスク評価
5. 複雑度見積もり（High/Medium/Low）
6. 変更ファイル一覧（正確なパス）
7. 変更しないファイル一覧（隣接するが対象外）
8. テストコマンド

planner 出力の Assumptions / 各ステップ検証手段をそのまま提示（二重定義しない）。

計画の根拠はステップ2/3 で確認した事実のみを用い、未確認事項は完了扱いにせず Assumptions として明示する。

## ステップ5: 確認待ち

ユーザーの肯定応答（「はい」「進めて」等）まで**コードを書かない**。

この停止は「作業の中断」ではなく**本コマンドの完遂**である。`/plan` の成果物は計画そのものであり、停止を外すと `/feat-dev` と同一のコマンドになって存在理由が消える。他コマンドの承認待ちを撤去した回でも、ここは意図して残している。

計画の修正依頼は以下の形式で受け付ける:
- "修正: [変更内容]"
- "別アプローチ: [代替案]"
- "フェーズ N を飛ばしてフェーズ M を先に進める"

肯定応答受領 → loop-dev へ移行。

## 連携

- 実装: ユーザー承認後、`loop-dev` skill を起動（入力: `task` = 承認済み計画の実装要件サマリー（1〜3 文） / `task_type` = 計画の性質に応じて `feature` | `bugfix` | `test` | `refactor-fix` から選択 / `approved_plan` = 承認済み計画で plan 段縮退。変更ファイル一覧・テストコマンドを引き継ぐ）
- loop-dev から収束 or 停止報告を受領後、Loop-Dev Result を転記して要約を提示

## 引数

- 位置 #1: `[要件説明]`（省略時: 直前の会話文脈から要件抽出）
