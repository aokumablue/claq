# 即時ハンドオフ実装

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | コードを書く / 既存ファイルを書き換える / バグを直す / 何を変えたかを短く述べる |
| 人間 | 実行する / テストする / ログを読む / 失敗を貼り戻す |

このモードは**検証を省くもの**ではない。検証を**人間の手に移すもの**である。
省かれるのは「自分で走らせて自分で確かめる」工程だけで、確認そのものは省かれない。

## ルール1: 正しさの確認を目的としたコマンドを自分で実行しない

**やらないこと** — 自分の変更が正しいと確かめるために次を実行すること。

- テストスイートの実行
- ビルド / コンパイル
- リンタ / フォーマッタ / 型検査
- 対象プログラムやスクリプトの試走

**必ずやること** — 読解には制限をかけない。ファイルの読み取り、ディレクトリの一覧、
文字列検索、定義や呼び出し元の追跡は続ける。むしろ増やす。ルール2 の「最も確率の高い
修正」は現物を読まなければ出てこない。**抑制するのは実行であって、調査ではない。**

**例外** — 人間が明示的に実行を頼んだ場合は従う。「テストを走らせて」「動かしてみて」
「ビルドが通るか見て」と言われたら実行する。抑えているのは**頼まれてもいない自己検証**
であって、直接の指示ではない。実行しても返し方は変えず、結果は「実行済み」行に入れる。

## ルール2: 熟考より先に書き換える

- 現在のコードベースから推測できる**最も確率の高い**修正を、即座にファイルへ適用する
- 候補が複数あるなら、一番ありそうな1つを書く。両方は書かない
- 「A案とB案があります、どちらにしますか」で止まらない。1つ選んで書いてから、選ばなかった案を「前提」に1行で添える
- 提案で終わらせない。差分を適用済みの状態で返す。人間はコピペ要員ではない
- 迷いは実装を止める理由にならない。迷いは**1行の前提表明**に変換してハンドオフに載せる

**書く前に止まってよい唯一の場合**は、元に戻せない操作が要るときだけ。ファイルやデータの
削除、履歴の書き換え、外部への送信がそれにあたる。それ以外は書く。

## ルール3: 解説は差分と意図だけ

書くもの: 何を変えたか、なぜそれで直るはずか。

書かないもの:

- 変更していない箇所の説明
- コード全文の再掲（変更行だけで足りる）
- 一般論・設計論・前置き・締めの挨拶
- 検討したが採らなかった案の詳細（採らなかったことは1行で足りる）

目安は、人間が数秒で読み終えて次の実行に移れる長さ。

## 制御を返すときの形

毎回この構造で返す。順番も変えない。

```text
変更:
- <ファイルパス>: <1行で何をしたか>
- <ファイルパス>: <1行で何をしたか>

意図: <なぜこの変更で直るはずか。1〜2文>

前提: <断定できず推測で埋めた箇所。候補から1つ選んだ・テスト名や変数名から仕様を読み取った・呼び出し側を見ずに引数の意味を決めた類も推測に入る。無ければ「なし」と書く>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと結果を1行。頼まれていなければ行ごと省く>

次に実行: <そのまま貼れるコマンド1行。自分で走らせて通った後も、人間が自分の環境で叩き直すコマンドをそのまま書く>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  通れば: <何が見えれば成功と判断できるか>
  落ちたら: <どの出力のどの部分を貼り戻してほしいか>
```

「次に実行」「落ちたら」を欠いたハンドオフは失敗である。次に何をすればいいか、落ちたときに
何を貼ればいいかが分からなければ、往復はそこで止まる。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る。パッケージ定義のスクリプト欄、
タスクランナーの設定、テスト設定ファイル、CI の定義、リポジトリの開発手順書。

**書く前にリポジトリ直下のファイル一覧を見て、宣言ファイルを実際に開く。** この種の宣言は
ほぼ例外なくルートに置かれていて、バグ箇所を追ってソースを読んでいる限り目に入らない。
一覧に出た宣言ファイルを開き、そこにある文字列をそのまま渡す。ソースの import 文やテストの
記法から実行系を言い当てるのは、宣言を読んだことにならない。

「特定できず」と書いてよいのは、その一覧を実際に見たうえで宣言ファイルが1つも無かったとき
だけである。読み取れないときも「次に実行」の行は省かず、コマンドの代わりに動かしてほしい
対象と、何が見えれば通ったかを書く。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・エラーは**一次情報**である。「このコードはこう動くはず」という
  自分の推論より常に優先する。食い違ったら捨てるのは推論のほうであって、観測ではない
- 直したら**同じ形**で返す。往復のたびに書式を変えない
- 同じ箇所で2回続けて外しても書く手は止めない。何を誤解していたかを1〜2行で述べ、確認したい
  事実を**1つだけ**、適用済みの差分と一緒にハンドオフへ載せる

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- 原因が分からず、調査自体が依頼の中心にある
- 実行して初めて得られる情報が無ければ1行も書けない

これらに当たるときは、このモードを離れて通常どおり自分で実行し確かめる。
