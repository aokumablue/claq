# 即時ハンドオフ実装

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | コードを書く / 既存ファイルを書き換える / バグを直す / 何を変えたかを短く述べる |
| 人間 | 実行する / テストする / ログを読む / 失敗を貼り戻す |

このモードは**検証を省くもの**ではない。検証を**人間の手に移すもの**である。
省かれるのは「自分で走らせて自分で確かめる」工程だけで、確認そのものは省かれない。

なぜ移すか。人間はすでに実行環境の前に座っている。実機・実データ・実ログを持っているのは
人間の側であり、こちらが別環境で回す自己検証は二重実行にしかならない。往復1回あたりの
待ち時間を削ることが、この分担そのものの目的である。

## ルール1: 正しさの確認を目的としたコマンドを自分で実行しない

**やらないこと** — 自分の変更が正しいと確かめるために次を実行すること。

- テストスイートの実行
- ビルド / コンパイル
- リンタ / フォーマッタ / 型検査
- 対象プログラムやスクリプトの試走

**必ずやること** — ファイルを読むこと。読解には一切の制限をかけない。

ファイルの読み取り、ディレクトリの一覧、文字列検索、定義や呼び出し元の追跡は
すべて続ける。むしろ増やす。ルール2 の「最も確率の高い修正」は現物を読まなければ
出てこない。読まずに書くのは速いのではなく、当てずっぽうの代金を人間の実行時間で
払わせているだけである。**抑制するのは実行であって、調査ではない。**

**例外** — 人間が明示的に実行を頼んだ場合は従う。「テストを走らせて」「動かしてみて」
「ビルドが通るか見て」と言われたら実行する。抑えているのは**頼まれてもいない自己検証**
であって、直接の指示ではない。指示に従わないスキルになっては本末転倒である。

実行しても**返し方は変えない**。走らせて分かったことは「制御を返すときの形」の
「実行済み」行に入れる。結果はそこに収まるのだから、構造を離れて報告を書き起こす必要は
ない。「次に実行」も省かない — こちらの環境で通ったことは人間の実機で通ったことの
代わりにならないので、人間が叩き直すコマンドを引き続き書く。

## ルール2: 熟考より先に書き換える

- 現在のコードベースから推測できる**最も確率の高い**修正を、即座にファイルへ適用する
- 候補が複数あるなら、一番ありそうな1つを書く。両方は書かない
- 「A案とB案があります、どちらにしますか」で止まらない。1つ選んで書いてから、選ばなかった案を「前提」に1行で添える
- 提案で終わらせない。差分を適用済みの状態で返す。人間はコピペ要員ではない
- 迷いは実装を止める理由にならない。迷いは**1行の前提表明**に変換してハンドオフに載せる

推測で埋めた箇所があっても手を止めない。埋めた事実を書いて返せば、人間は次の往復で
訂正できる。質問して待つより、書いて訂正してもらうほうが速い — それがこのモードの
賭けである。

**書く前に止まってよい唯一の場合**は、元に戻せない操作が要るときだけ。ファイルやデータの
削除、履歴の書き換え、外部への送信がそれにあたる。それ以外は書く。

## ルール3: 解説は差分と意図だけ

書くもの: 何を変えたか、なぜそれで直るはずか。

書かないもの:

- 変更していない箇所の説明
- コード全文の再掲（変更行だけで足りる）
- 一般論・設計論・前置き・締めの挨拶
- 検討したが採らなかった案の詳細（採らなかったことは1行で足りる）

目安は、人間が数秒で読み終えて次の実行に移れる長さ。長い解説は、人間が実行を始めるまでの
時間をそのまま延ばす。

## 制御を返すときの形

毎回この構造で返す。順番も変えない。人間が同じ位置に同じ情報を探せることが、往復の速さに
直結する。

```text
変更:
- <ファイルパス>: <1行で何をしたか>
- <ファイルパス>: <1行で何をしたか>

意図: <なぜこの変更で直るはずか。1〜2文>

前提: <断定できず推測で埋めた箇所。無ければ「なし」と書く>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと結果を1行。頼まれていなければ行ごと省く>

次に実行: <そのまま貼れるコマンド1行。自分で走らせて通った後も、人間が自分の環境で叩き直すコマンドをそのまま書く>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  通れば: <何が見えれば成功と判断できるか>
  落ちたら: <どの出力のどの部分を貼り戻してほしいか>
```

「次に実行」を欠いたハンドオフは失敗である。人間が次に何をすればいいか分からなければ
往復は止まり、この分担の前提そのものが崩れる。「落ちたら」も同様に必須 — 何を貼れば
いいかを書かないと、人間は出力全体を貼るか、要点を落として貼るかのどちらかになる。

「前提」を空にしてよいのは、**書いた内容がすべて読んだ現物から確定できるとき**だけである。
候補が複数あって1つを選んだ、テスト名や変数名から仕様を読み取った、呼び出し側を見ずに
引数の意味を決めた — どれも推測であって「なし」ではない。選ばなかった案があるなら、その
1行もここに書く。自分では気づかないまま埋めた箇所こそ、人間が次の往復で最初に潰すべき
場所である。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る。パッケージ定義のスクリプト欄、
タスクランナーの設定、テスト設定ファイル、CI の定義、リポジトリの開発手順書。

**書く前に、その宣言ファイルを実際に開く。** 開いていないなら、まだコマンドを書ける状態に
ない。ソースの import 文やテストの記法から実行系を言い当てるのは、宣言を読んだことには
ならない。名前が合っていても、必要なフラグ・設定ファイルの指定・前段の準備コマンドまでは
出てこないからである。しかも推測が当たっていたかどうかは、当てた本人には区別がつかない。
だから「出どころ」に開いたファイル名を書く。書けないなら読んでいない。

宣言ファイルは**探さないと見つからない**。まずリポジトリ直下のファイル一覧を見る。この種の
宣言はほぼ例外なくルートに置かれていて、バグ箇所を追ってソースを読んでいる限り目に入らない。
一覧に出た宣言ファイルを開き、そこにある文字列をそのまま渡す。

「特定できず」と書いてよいのは、**その一覧を実際に見たうえで宣言ファイルが1つも無かった
とき**だけである。探さずに「見当たらない」と書くのは、推測コマンドを書くより悪い。人間は
「探したうえで無かった」と読むので、ルートに置かれた設定を見落としたまま往復が続く。

読み取れないときも「次に実行」の行は**省かない**。コマンドの代わりに、動かしてほしい対象
（どのファイル・どの入口・どの画面）と、何が見えれば通ったかを書き、「プロジェクトの設定から
実行コマンドを特定できなかった」と添える。人間はコマンドだけ補えば動ける。
コマンドが分からないことは、ハンドオフを不完全なまま返してよい理由にはならない。

「たぶん `npm test` です」と埋めてはいけない。別のテストランナーを使うリポジトリに他所の
コマンドを渡すのは、自分でテストを走らせるのと同じだけ往復を止める。むしろ悪い — 人間が
エラーの原因をコードの側に探しに行くぶん、時間を余計に奪う。

全体スイートより、変更に対応する**最小の実行単位**を優先する。単一のテスト関数、単一の
ファイル、単一の画面。人間の待ち時間が短いほど往復は速く回る。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・エラーは**一次情報**である。「このコードはこう動くはず」という
  自分の推論より常に優先する。食い違ったら捨てるのは推論のほうであって、観測ではない
- 直したら**同じ形**で返す。往復のたびに書式を変えない
- 同じ箇所で2回続けて外したら、3回目も**書く手は止めない**。止まって聞くのはルール2 を折る。
  かわりに、自分が何を誤解していたかを1〜2行で述べ、確認したい事実を**1つだけ**、適用済みの
  差分と一緒にハンドオフへ載せる。推測を無言で3回上塗りすると往復は無限に伸びる。
  書く、そして同時に聞く

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- 原因が分からず、調査自体が依頼の中心にある
- 実行して初めて得られる情報が無ければ1行も書けない

これらに当たるときは、このモードを離れて通常どおり自分で実行し確かめる。
往復の速さが価値になるのは、人間がすでに実行環境の前に座っているときだけである。
