# 即時ハンドオフ切り分け

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | 仮説を並べる / 仮説を落とす観測を計装として適用する / 観測の読み方を渡す / 返ってきた観測で仮説を落とす |
| 人間 | 再現する / 走らせる / ログと数値を貼り戻す / 本番や手元でしか見えない事実を持ち込む |

このモードは**切り分けを省くもの**ではない。観測を**人間の手に移すもの**である。
省かれるのは「自分で走らせて自分でログを見る」工程だけで、切り分けそのものは省かれない。

## ルール1: 確認を目的としたコマンドを自分で実行しない

**やらないこと** — 原因を確かめるために次を実行すること。

- 再現手順の実行・対象プログラムの試走
- テストスイートの実行 / ビルド / コンパイル
- プロファイラ・ベンチマークの採取
- リンタ / 型検査

**必ずやること** — 読解には制限をかけない。スタックトレースの追跡、該当行の読み取り、
呼び出し元の全探索、同種の既存バグの検索は続ける。むしろ増やす。走らせずに正しい仮説を
立てる唯一の手段が現物の読解である。**抑制するのは実行であって、調査ではない。**

**例外** — 人間が明示的に実行を頼んだ場合は従う。実行しても返し方は変えず、
結果は「実行済み」行に入れる。抑えているのは**頼まれてもいない自己検証**である。

## ルール2: 修正を当てない。入れるのは観測である

**ここが quick-code との分岐点である。** quick-code は「最も確率の高い修正を即座に適用する」
が、このモードでは適用しない。原因が確定していない段階で修正を当てると、

- 当たれば、なぜ直ったか分からないまま直る。同じバグが別の形で戻ってくる
- 外れれば、元の症状に自分が入れた変更が重なり、切り分けが一段難しくなる

だから適用するのは**観測**である。ログ行、assert、仮説を写した失敗するテスト、
区間タイマ。これらは差分として適用済みで返せるうえ、人間の1回の実行で仮説が落ちる。
**提案で終わらせない。計装を入れた状態で返す。人間はコピペ要員ではない。**

計装は**消せる形**で入れる。1 か所にまとめ、消す行がどれかをハンドオフに書く。
調査が終わったあと人間が探し回ることになるものは、計装ではなく汚染である。

## ルール3: 仮説は絞らず並べる

**ここも quick-code の反転である。** quick-code は候補が複数あれば一番ありそうな1つを
書くが、このモードでは**落とせていない仮説を消さない**。読んだだけで消えた仮説は挙げる
必要がないが、実行しないと決まらない仮説を「たぶん違う」で消すのは切り分けではなく省略
である。

- 仮説は**上限3件**。4 件目が要るなら、観測が粗すぎて絞り切れていない
- 各仮説に「**これが真なら観測はこう出る**」を必ず添える。これが無い仮説は、観測が
  返ってきても落とせない
- 再現していない症状では仮説を立てない。**再現手順の確定を先に人間へ返す**

## ルール4: 1回の実行で最も多く落ちる観測を1つ選ぶ

仮説ごとに計装を撒かない。3 件の仮説に 3 か所のログを入れると、人間は 3 行を貼り戻す
うえ、1 回の実行で全経路が通るとは限らない。

選ぶのは、**真でも偽でも仮説が減る観測**である。経路の中間点を 1 つ測り、前半なら A と B
が落ち、後半なら C が落ちる、という形に組む。どちらに転んでも減らない観測は入れない。

## ルール5: 観測が数値のとき

症状が「遅い / 重い / メモリを食う」なら、仮説は「**どこが支配的か**」の形になり、
観測は真偽ではなく内訳になる。区間タイマ、呼び出し回数のカウンタ、プロファイラの出力。

**ベースラインが返ってくる前に最適化を当てない。** 測らずに入れた最適化は、効いたのか、
効かなかったのか、別の何かが変わったのかを永久に区別できない。数値の仮説が落ちるのは
前後 2 つの数値が揃ったときだけで、「速くなったはず」は観測ではない。

内訳が返ってきたら、占有率が小さい仮説から落とす。**支配的な 1 件に絞り切るまで最適化の
差分は出さない。**

## ルール6: 解説は仮説と観測だけ

書くもの: 何を疑っているか、何を見れば決まるか。

書かないもの:

- 症状の言い換え（人間は自分が踏んだ症状を知っている）
- 読んだコードの説明・一般的なデバッグ手法の解説
- 落とした仮説の詳細な検討過程（落ちたことと根拠の1行で足りる）
- 前置き・締めの挨拶

## 制御を返すときの形

毎回この構造で返す。順番も変えない。

```text
残っている仮説:
- <仮説。1行> / 真なら: <観測がどう出るか。1行>
- <仮説。1行> / 真なら: <観測がどう出るか。1行>

落とした仮説: <落ちた仮説と、落とした根拠。読解で落ちたのか観測で落ちたのかを書く。無ければ「なし」>

入れた観測:
- <ファイルパス>: <何を出す計装か。1行>

消し方: <調査後に消す行。ファイルパスと目印。計装を入れていなければ「計装なし」>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと結果を1行。頼まれていなければ行ごと省く>

次に実行: <そのまま貼れるコマンド1行。再現手順が宣言ファイルから読めないなら人間の再現手順をそのまま書く>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  読み方: <出力のどこを見ると、どの仮説が落ちるか>
  貼り戻すもの: <出力のどの部分が要るか。全文か、特定の行か>
```

**「落とした仮説」「消し方」はブロックごと省かない。** 該当が無ければ見出しの下に1行で
無いと書く。ブロックが消えると、人間は「無かった」のか「書き忘れた」のかを区別できない。

「次に実行」「読み方」「貼り戻すもの」を欠いたハンドオフは失敗である。何を叩けばいいか、
出力の何を見ればいいか、何を貼ればいいかが分からなければ、往復はそこで止まる。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る。パッケージ定義のスクリプト欄、
タスクランナーの設定、テスト設定ファイル、CI の定義、リポジトリの開発手順書。

**書く前にリポジトリ直下のファイル一覧を見て、宣言ファイルを実際に開く。** この種の宣言は
ほぼ例外なくルートに置かれていて、スタックトレースを追ってソースを読んでいる限り目に
入らない。一覧に出た宣言ファイルを開き、そこにある文字列をそのまま渡す。

**ログの出し方も同じ扱いにする。** ログレベルの上げ方、詳細出力のフラグ、プロファイラの
起動方法は、その言語の一般論ではなくプロジェクトの設定に従う。ロギング設定・起動
スクリプト・開発手順書に書かれた形を写す。写せる形が無ければ、素の実行コマンドに
「この出力が見えるはず」を添える。

「特定できず」と書いてよいのは、その一覧を実際に見たうえで宣言ファイルが1つも無かったとき
だけである。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・スタックトレース・数値は**一次情報**である。「このコードは
  こう動くはず」という自分の推論より常に優先する。食い違ったら捨てるのは推論のほうであって、
  観測ではない
- まず**仮説を落とす**。観測と食い違う仮説を残したまま次の計装を足さない
- **仮説が1件だけ残ったときに限り、修正へ進んでよい。** そのときは quick-code の形
  （変更 / 意図 / 前提 / 次に実行）で返す。2 件以上残っていれば次の観測を出す。
  「たぶんこれだろう」で修正へ渡らない
- 観測がどの仮説とも合わなければ、**仮説の立て方を変える**。同じ前提のまま計装を細かく
  しても落ちない。何を誤解していたかを1〜2行で述べ、仮説を作り直して返す
- 直したら**同じ形**で返す。往復のたびに書式を変えない

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- 原因が既に分かっていて、修正だけが要る（quick-code）
- 振る舞いを変えずに構造だけ整えたい（quick-refactor）
- 症状が再現しておらず、再現条件の特定そのものが依頼の中心にある

再現から修正・回帰防止・レビューまで通しでほしい場合は /bugfix を使う。
