# アーキテクチャ決定記録

## 発動タイミング

- 「ADRにして」「この決定を記録」
- 重要な代替案間で選択（フレームワーク/ライブラリ/パターン/DB/API設計）
- 「Xすることに決めた」「YではなくXの理由は」
- 計画フェーズでアーキテクチャトレードオフが議論される

## ADR フォーマット

```md
## ADR-NNNN: [決定タイトル]

**日付**: YYYY-MM-DD  **ステータス**: proposed | accepted | deprecated | superseded by ADR-NNNN

### コンテキスト
[状況・制約・関与する力を 2-5 文]

### 決定
[決定 1-3 文]

### 検討した代替案
#### 代替案 1: [名前]
- 長所 / 短所 / 却下理由

### 結果
**肯定的** / **否定的** / **リスク**
```

## ワークフロー

1. **初回のみ**: `docs/adr/` ディレクトリ・インデックス(`README.md`)・テンプレート作成（判断を含まないため確認は挟まない）
2. 決定特定→コンテキスト収集→代替案記録→結果記述
3. `README.md` の「ADR 一覧」をスキャン→最大値 + 1 を採番（既存番号の再利用・再割り当てはしない。`ADR-NNNN` はリポジトリ全体から参照される識別子）
4. 書き込み先トピックファイルを決める→ドラフト提示→**明示的承認後のみ**書き込み（ADR は永続的な意思決定記録であり、誤った ADR は以後の全判断を汚染する。ADR-0011 が「設計判断の論拠は ADR に置く」と定める以上、その ADR が自動生成物であってはならない。意図して残している停止点）
5. `docs/adr/README.md` の「ADR 一覧」へ 1 行追加。新トピックファイルを作った場合は「トピック」表にも 1 行追加
6. 書き込み後に、割当番号が既存と重複しないこと・README にインデックス行が追加されたこと・全必須セクションを空のまま残さない。未確認は『未検証』と明示

**既存の決定を撤回・supersede する場合は、撤回された記述を消さない。** 撤回の事実と経緯、および棄却した代替案を残す。同じ提案が繰り返し来るため、その記録が再提案への回答になる。

## ディレクトリ構造

**1 決定 = 1 ファイルではない。** 要点（トピック）ごとの 1 ファイルに、h2 見出し `ADR-NNNN: <タイトル>` の節として収める。番号を跨いで繰り返される前提は各ファイル冒頭の「共通原則」に 1 回だけ書き、各節はそこを参照する。

```
docs/adr/
├── README.md        ← インデックス（トピック表 + | ADR | Title | Status | Date | ファイル |）
├── NN-<slug>.md     ← トピックファイル（h2 見出しの ADR 節を複数持つ）
└── template.md
```

## 決定検出シグナル

**明示的**: "Xを採用しよう" / "YではなくXを使うべき" / "これをADRとして記録"

**暗黙的**（提案のみ・自動作成しない）: フレームワーク比較→結論 / DBスキーマ設計選択 / アーキテクチャパターン選択

## ADRライフサイクル

`proposed → accepted → [deprecated | superseded by ADR-NNNN]`

## 永続メモリ

search: `ple4_run ple4.mem.cli search "..."`（`. "$HOME/.ple4/env.sh"` 前提）— クエリ例 `ADR architecture decision {topic}` / `{technology} vs alternative decision`。返るのは `- [kind] title (key)` の 1 行だけなので、本文が要る key だけ `ple4_run ple4.mem.cli show <key>` に渡す
record: 再利用可能な学びだけ `ple4_mem_learn` で登録する。基準は `../learn/SKILL.md` の「記録する / しない」
