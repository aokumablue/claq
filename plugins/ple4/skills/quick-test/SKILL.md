# 即時ハンドオフテスト実装

## 役割分担

| 担い手 | やること |
|---|---|
| こちら（AI） | テストコードを書く / 既存テストを直す / テストごとに期待する色を宣言する / 判別力を確かめる変異手順を添える |
| 人間 | テストを走らせる / カバレッジを測る / 色を読む / 結果を貼り戻す / 仕様の不明点に答える |

このモードは**検証を省くもの**ではない。検証を**人間の手に移すもの**である。
省かれるのは「自分で走らせて自分で色を見る」工程だけで、確認そのものは省かれない。

## ルール1: テストを自分で走らせない

**やらないこと** — 書いたテストが通るか確かめるために次を実行すること。

- テストスイートや個別テストの実行
- カバレッジ計測
- ビルド / コンパイル
- リンタ / フォーマッタ / 型検査

**必ずやること** — 読解には制限をかけない。対象コードの読み取り、既存テストの一覧、
命名規約やフィクスチャの検索、呼び出し元の追跡は続ける。むしろ増やす。走らせずに
正しいテストを書く唯一の手段が現物の読解である。**抑制するのは実行であって、調査ではない。**

**例外** — 人間が明示的に実行を頼んだ場合は従う。実行しても返し方は変えない。
宣言した色は消さず、宣言色と観測色を並べて「一致したか」を示す。観測できたからといって
宣言を省くと、次の往復で何を期待していたかが失われる。

## ルール2: 走らせていないテストには期待する色を宣言する

走らせていないテストの色は未知である。未知のまま渡すと、人間は赤を見たときにそれが
**想定どおりの赤**なのか**書き損じの赤**なのか判別できない。だからテスト1件ごとに
期待する色を書く。

- バグ再現テスト → **RED が正解**（修正が入るまで赤いことがそのテストの仕事）
- 修正後の回帰防止テスト → **GREEN が正解**
- 既存挙動を固定する特性化テスト → **GREEN が正解**

**宣言色と観測色が一致していれば、そのテストは成功している。** 正しく RED のテストを
次のターンで緑にしにいかない。赤を消す作業に入ってよいのは、人間が「修正を入れた」と
告げた後だけである。

宣言できるのは1テストにつき1色だけ。「たぶん緑、環境によっては赤」は宣言ではない。
どちらか一方を選び、揺れる理由は前提に1行で書く。

## ルール3: 判別力の確認は人間に委譲する

そのテストが**本当に壊れたときに落ちるか**は、実際に壊してみないと分からない。
走らせない以上、自分で変異を入れて確かめることはできない。だから確かめる手順を渡す。

変異手順はテスト1件ごとに1行。どこを触れば色が反転するかを、行が特定できる粒度で書く。

- GREEN 宣言 → 「この行をこう戻すと赤くなるはず」
- RED 宣言 → 「この修正を入れると緑になるはず」

「テストを消せば赤は消える」のような、対象コードに触れない手順は変異手順ではない。
指すのは常に**プロダクトコード側の1行**である。

## ルール4: テストが落ちてもプロダクトコードを直さない

**ここが quick-code との分岐点である。** quick-code は「最も確率の高い修正を即座に適用する」
が、このモードでは適用しない。書き換えてよいのはテストコードだけで、プロダクトコードは
読むだけに留める。

テストの失敗は、直すべきバグではなく**仕様の不明点**として扱う。人間が貼り戻した赤に対して
やることは次の2つだけ。

1. テスト側の書き損じ（記法・フィクスチャ・アサーションの取り違え）なら、テストを直して返す
2. プロダクトコードの挙動と期待値が食い違うなら、**どちらが正しいかを人間に問う**。
   質問は1つだけに絞り、その答えで分岐する2案を1行ずつ添える

「テストが赤いのでプロダクトコードを直しておきました」は、このモードの失敗である。
テストが仕様を映しているのか、実装が仕様を映しているのかを決める権限は人間にある。

修正まで一気に進めてほしいと言われたら、このモードを離れて quick-code か通常の実装として扱う。

## ルール5: 解説は差分と意図だけ

書くもの: どのテストを足したか、それが何を守るか。

書かないもの:

- テスト対象コードの説明
- テスト全文の再掲（追加したテスト名と要点だけで足りる）
- 一般論・テスト設計論・前置き・締めの挨拶
- 網羅率の自己申告（測っていないものを述べない）

## 制御を返すときの形

毎回この構造で返す。順番も変えない。

```text
追加したテスト:
- <ファイルパス> / <テスト名>: <何を確かめるか。1行> / 期待する色: RED または GREEN
- <ファイルパス> / <テスト名>: <何を確かめるか。1行> / 期待する色: RED または GREEN

意図: <このテスト群で何が守られるか。1〜2文>

変異手順:
- <テスト名>: <プロダクトコードのどの1行をどう変えると色が反転するか>

実行済み: <頼まれて自分で走らせた場合だけ、コマンドと宣言色/観測色を1行。頼まれていなければ行ごと省く>

前提: <仕様を推測で埋めた箇所。既存テストの命名から期待値を読み取った・境界値を呼び出し側を見ずに決めた類も推測に入る。無ければ「なし」と書く>

次に実行: <そのまま貼れるコマンド1行。追加したテストだけを指定して走らせる形にする>
  出どころ: <このコマンドを読み取った宣言ファイル名。読めなかったなら「特定できず」>
  期待する色: <宣言色の総和。例: 2 RED / 1 GREEN>
  食い違ったら: <どの出力のどの部分を貼り戻してほしいか>
```

「次に実行」「期待する色」「食い違ったら」を欠いたハンドオフは失敗である。何を叩けば
いいか、何色なら成功か、食い違ったとき何を貼ればいいかが分からなければ、往復は止まる。

## 実行コマンドは推測で書かない

コマンドの出どころは、プロジェクト自身の宣言ファイルに限る。パッケージ定義のスクリプト欄、
テストランナーの設定ファイル、CI の定義、リポジトリの開発手順書。

**書く前にリポジトリ直下のファイル一覧を見て、宣言ファイルを実際に開く。** この種の宣言は
ほぼ例外なくルートに置かれていて、テスト対象を追ってソースを読んでいる限り目に入らない。
一覧に出た宣言ファイルを開き、そこにある文字列をそのまま渡す。

**単体指定の記法も同じ扱いにする。** 追加した1件だけを走らせるためのファイル指定・
テスト名指定・タグ絞り込みの書き方は、ランナーごとに違う。テストファイルの import 文や
既存テストの記法から実行系を言い当てるのは、宣言を読んだことにならない。宣言ファイルか
テスト設定に書かれた形を写す。写せる形が無ければスイート全体を走らせるコマンドを書き、
絞り込めなかったことを1行添える。

「特定できず」と書いてよいのは、その一覧を実際に見たうえで宣言ファイルが1つも無かったとき
だけである。読み取れないときも「次に実行」の行は省かず、コマンドの代わりに走らせてほしい
対象と、何色なら成功かを書く。

## 結果が返ってきたら

- 人間が貼った実行結果・ログ・スタックトレースは**一次情報**である。「このテストはこう動くはず」
  という自分の推論より常に優先する。食い違ったら捨てるのは推論のほうであって、観測ではない
- **宣言色と観測色が一致したテストには触らない。** RED 宣言の赤は成功報告であって作業指示ではない
- 食い違ったテストだけを見る。原因がテスト側ならルール4の1、実装側ならルール4の2に倒す
- 直したら**同じ形**で返す。往復のたびに書式を変えない
- 同じテストで2回続けて色を外したら、書く手は止めないまま何を誤解していたかを1〜2行で述べ、
  確認したい事実を**1つだけ**ハンドオフへ載せる

## このモードを使わない場面

- 人間が実行環境の前にいない（実行の代行そのものが依頼されている）
- どこが壊れているか分からず、失敗の切り分け自体が依頼の中心にある
- 実行して初めて得られる情報（実際の例外メッセージ、実測値）が無ければ1行も書けない
- テストと修正をまとめて仕上げてほしい（quick-code か通常の実装として扱う）

デシジョンテーブル設計から実装・検証まで通しでほしい場合は /test-gen を使う。
